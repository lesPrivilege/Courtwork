## Adjustments to the rulings

| Ruling | Adjustment | Reason |
|---|---|---|
| ATT-02 · the rail Attention entry opens the item queue; the assistant is one action inside it | **Adjusted; the question deferred to Astra.** The rail entry still opens the assistant. It carries the item count, and the assistant's "Attention items" button carries the same count, so the queue is one visible step from the entry. | The [Attention agent decision](../../design/attention-agent-2026-09-10/README.md) (Astra, status rule) makes Attention the single resident assistant with "one stable glyph+text Attention entry" and items as "a separate inspection destination". The [sidebar product model](../../design/sidebar-product-model-2026-09-12/README.md) keeps the assistant's entry and treats the list as one of its views. `attention.agent` names the rail control and its glyph is single-purpose. The audit's ruling would redefine a product role, which is not a UX-lane decision. |
| ATT-04/OBJ-06 · project-scoped tools default to the working project, "All projects" explicit | **Adjusted.** The Attention queue, the count and Spark's maintenance view start in the working project. Usage keeps "All retained work", because its only entry is Home's Activity block, which counts every project. The Attention queue has no "All projects" choice: the registry is read one project at a time. | A tool opens at the scope of the place that opened it. A cross-project Attention read needs a Host/Core query that does not exist. |
| ATT-01 · count and marks "from the same owner facts Home already reads" | As ruled. Marks come from the waiting set Home reads (all projects), the count from the registry Home's Attention block reads (one project). | — |

## Review dispositions

A Sonnet non-author review of the uncommitted diff found five defects, none high.

| Finding | Disposition | Landing |
|---|---|---|
| 1 · with only the example workspace, the count's fallback scope was the example project, whose sample answers every Attention query ("1 needs you") | **Adopt**: the fallback is the first real project; an example project is never read for a count | `app.mjs` `attentionScope`; test |
| 2 · with no run open, the count stayed stale after items were handled in the queue | **Adopt**: leaving the item queue and closing the assistant re-read both facts. A failed count read is retried on the next navigation or visibility change, not polled: a Host that is down is not polled every 15 seconds for a badge | `app.mjs`; test |
| 3 · a change of marks redrew the whole Chat page: focus fell to the page, "About chats" closed, an open object menu lost its anchor | **Adopt**: the Chat page changes marks in place (`updateWaiting`); rows, focus and open sections stay | `chat-page.mjs`, `shell-signals.mjs` (`data-kind`); test with the same row node before and after |
| 4 · runs started by Spark or the Attention assistant do not start the 15s read | **Reject**: the Host runs one active run at a time, so no other chat can come to wait while such a run is open, and the next run in a chat is admitted through the hook that reads again. The assistant's tools cannot change an item's status (attention-agent decision AG-4). A Spark child chat is not a rail row | — |
| 5 · a chat with no project shows Home's project count | **Accept** as ruled (J: the open chat's project, else Home's); the accessible name names the project | — |
| Tests pin source text | **Accept** in part: the reader, the helpers and the Chat page update are behaviour tests; app.mjs wiring has no DOM harness, and the captures and their report show the composed behaviour | — |
