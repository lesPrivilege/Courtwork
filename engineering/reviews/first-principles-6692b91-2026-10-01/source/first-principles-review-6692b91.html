结论

架构的主要责任已经落到真实实现；本轮施工确实补上了上轮多处断点。但现在还不能把“可接续的工作场”视为完整闭环，更不能签署整体验收。

最值得优先处理的不是再增加运行时或扩展数量，而是三个贯穿现有产品的条件：

  • 结束必须真正封口：Host 释放数据目录锁前，所有已进入的写请求必须被结算或拒绝；目前仍有迟到 HTTP 写入越过锁交接的静态窗口
  • 留下的成果必须能被发现：file-memo 的确切文件字节保留了，但新 Session 的模型没有从 Artifact 身份发现文件清单的入口
  • 恢复必须识别原意图及已知事实：Core 幂等回执、Host 准入拒绝、前端“未知”状态没有在所有路径上贯通，部分重试因此被错当作新提议或持续未知

本轮整合为 1项P1、7项P2，以及2项P3维护项。严重度表示建议处理顺序，不表示发生频率；P1/P2中除README生成分歧获得现有CI佐证，其余均为静态代码路径判断，未动态复现。没有P0结论，也不提供虚假的“架构完成百分比”。

这轮并非原地踏步：正式决定仍由单一Core事务管理；补证据理由已进入接续Context；Chat与Attention共用批准依据；手动compaction已纳入close；取消意图与终态写入的旧排序窗口已修；human mutation与Run admission已有共同排序。新的问题集中在这些正确局部机制之间尚未覆盖的消费者和生命周期边缘。

N1 · P1：关闭的结束条件尚未覆盖全部写者

目标与不变量。 用户停止旧Host、启动新Host后，数据目录只能有一个有权发布状态的写者。正确的关闭条件应是“以后不会再接纳mutation，且已接纳mutation全部结束”，不能只是等待某一刻看见的队列尾。

断裂。 HTTP入口只在handler进入时检查closing；已通过检查的请求仍可等待body。HTTP关闭顺序先调用server.close，随后await runtime.close，最后才等已有连接结束。createProject与createSession既不检查closing，也不进入service关闭集合。

Store close与persist只await当时的_queue，release完成才清lockHandle；_mutate没有关闭准入，_persist仅在开始检查锁，跨异步write/chmod后直接rename。Python实际解锁发生在发送release回执之前。

静态反例。 已认证的旧POST正在等body → shutdown排空当时队尾并开始放锁 → body到齐，旧createProject追加mutation并通过尚未清空的lockHandle检查 → Python放锁 → 另一Host合法取得锁并载入/更新状态 → 旧mutation稍后rename其旧全量快照。此序列允许新旧状态发布交错。

后果与限定。 可能覆盖新Host更新，涉及持久状态单写者基础，因此列P1。没有观察到实际覆盖；必须有旧handler尚未结束、写入进入该窗口，且另一Host在旧HTTP排空前接管。若所有调用者都等完整HTTP close结束才启动下一Host，该特定交错被避开；但目录锁自身不应允许提前接管后仍有旧写者。

最小修复与退出条件。 在原Store owner内原子关闭mutation准入，drain所有已接受写入后再release；HTTP未结束请求统一drain或在mutation前拒绝。不宜只给一个route补if。后续用独立合成数据验证迟到body、写入等待和锁移交，证明放锁后旧Host不能再rename；本轮没有执行这些验证。

N2 · P2：成果字节留下了，文件集合却不能被新模型发现

不变量。 新Session只要绑定同一Matter，就应从正式记录找到已接受文件，不能要求前一个执行者记住path。

Context提供Artifact ID、文本摘要与分页reader，不提供bundle kind、文件数或manifest引用。file-memo工具集仅增加candidate/artifact file reader，而两个reader都要求已知path；se_read_artifact只读文字。Core已有file-manifest能力和human查询入口，但bound Work Session被governance fallback排除。

反例与后果。 合法接受一个文件bundle，正文仅写“已核对的备忘录”而未列文件名。新Session的模型只得到Artifact ID；读正文也不能推导任意合法文件名，文件reader又先要path。只能让人抄路径、猜测或重回旧会话。不是字节丢失，也不影响普通文本Artifact或已知路径读取。

现有continuity测试直接向新Run给定旧path，测试设计覆盖“已知可读”，没有覆盖“从实际Context自主发现”；本轮未运行测试。

修复方向。 复用已有Core manifest查询，暴露受相同scope/admission约束的只读发现入口，或让有界Context指向exact manifest。后续验收只给新消费者Matter身份，不预先注入文件名。

N3 · P2：旧修订已保存，正常HTTP重试却会被当前来源否决

不变量。 同一已提交请求的回查，应按原身份和原内容回答结果；新提议的当前来源验证不能先把旧回执挡住。

Work adapter在进入Core前总是snapshot当前Matter并normalize proposal；generic evidence验证要求证据的source id/version存在于当前source set。Core本来有原revision重放分支，可先找到existing new_candidate_id、恢复其原来源/合同版本，再比较完整内容。

反例。 S@1下修订C2已保存但HTTP响应丢失 → 用户合法将来源改成S@2 → 原样重发C2请求 → adapter找不到当前集合内的S@1，提前BINDING_MISMATCH → Core原回执分支不可达。至少generic evidence-memo成立；file-memo本来不支持这一generic revise路径，不列入影响范围。

后果与修复。 用户得到“输入无效”，无法按原请求确认已保存的修订，可能另造一次修订。Core记录未丢失，也未发生重复接受。应先由原owner比较已提交意图，再对真正新请求执行当前来源校验，不能放宽所有历史证据检查。Core层测试已有source变化后重放的设计，但绕过了HTTP adapter；下一验收需覆盖完整入口。

N4 · P2：一次配置请求可以校验A、保存B、却审计为A

不变量。 对选中Session的配置，应校验实际写入资源的scope；返回范围、持久化归属与审计应相同。

service优先用顶层input.scope校验目标；control.change允许scope与resource同时存在，put实际保存resource.scope，audit却又优先记顶层scope。类型合同中的put本应以resource自带scope为目标；HTTP合同要求所选Session的scope chain。

非执行性静态反例。 同一local-user拥有A、B两个Session；合法put除双scope外一致，顶层写A、resource写B。service校验A通过，control保存B，返回A的catalog并审计A，B的下一Run却可能继承资源。本轮没有构造或发送该请求。

后果与限定。 配置归属与可解释审计失配；没有证据表明现有普通UI自动产生该输入，也不是跨用户提权，因此不列P1。

修复方向。 按operation校验精确字段；put以resource.scope作为唯一目标，同时用于scope-chain验证和审计。拒绝冲突输入后，revision、resources、audit应均不变。

N5 · P2：只读“已有工作”请求会抹掉正在填写的Matter

打开动作先renderBindingPanel、聚焦字段，再异步loadProjectWork。读取完成无论结果成功或失败，只要面板还开就再次render；重建表单先clear全部节点，新input/textarea没有从草稿恢复值。

反例。 打开Continue in Matter → 列表GET稍慢 → 人在已聚焦字段粘贴标题、来源或facts → GET回执落回 → 表单被换成空节点。普通读延迟即可，不需要极端竞态。

后果。 未提交工作丢失，首次NDA指南中的大段输入尤其受影响；不是持久化Matter被删除。违背保存/恢复语义。

修复方向。 按Session＋extension＋draft身份持有输入；只刷新existing-work区域，或在重建前后保留值与选择。后续用延迟GET以及binding失败回读验证，不以“表单最终能提交”代替输入不丢失。

N6 · P2：Host已明确拒绝，旧Send却跨刷新保持“未确认”

不变量。 真正未知时保留exact request；已知未准入时应结清旧operation、保留草稿并允许纠正。

初次Send先保存command及runtimeSelection。recoverRunReceipt重发旧选择，对所有错误均说仍未解决，不清unconfirmedRuns；Send锁和reload恢复让锁持续。

反例。 首POST未到Host → 客户端记录网络未知 → 另一窗口改变有效Agent配置revision → “check receipt”重发旧请求。Host在同一配置序列中先查原command，查无后才返回runtime_selection_conflict，因此这是旧意图未准入的明确证据。恢复UI仍保存旧revision，每次再试都得到相同拒绝，刷新也重装同一锁。

后果与修复。 该窗口无法恢复正常发送，用户需换Chat/窗口或清客户端状态。Host没有重复执行，原receipt保护正确。恢复与首次发送catch应共用outcome分类：明确拒绝时结清旧operation、保留输入、刷新选择；真正未知仍不能随意清除。

N7 · P2：候选已创建，原地“再试”却变成另一意图

现有Chat的Start private candidate每次点击都生成新requestId/candidateId；只有成功响应更新Session，失败只解锁显示错误。Host候选命令支持原payload原ID回放，但新ID＋旧expectedRevision应被拒绝。

反例。 Host已创建candidate，响应丢失 → 卡片仍显示未创建 → 人再次Start → 新ID与旧revision产生409 → 卡片仍不回读，原地继续失败。

后果与消除条件。 已准备的工作不能在当前卡片被正确发现，反复操作无法推进。但重开卡片会GET Session，整页重载或跨Session返回也可恢复，不是永久锁死或重复worktree创建；Home preparation已有稳定身份＋reconcile，不在此缺口内。

修复方向。 普通卡片复用同一command owner，未知时保留payload并读回；至少提供卡片内的显式reconcile，不能将Retry实现为无条件生成新ID。

N8 · P2：README更新了支持条件，编辑源仍会把它抹掉

根README已列Linux sandbox前提；生成模板仍只有Node/Python/Git。构建检查全文不等就抛错；若直接按报错用--write-readme，却会以旧模板覆盖新增说明。site维护合同要求改编辑源，Pages构建步骤运行普通build。

后果。 固定版本的Pages构建被阻断；盲目重新生成还会让新用户丢掉Linux检查依赖说明。现有Pages job日志直接记录site/build.mjs:184的README out-of-step错误，因此此处不仅是静态推断。该push并未获得自动部署授权，deploy为skipped；不称“线上部署失败”。

修复方向。 先更新生成模板，保留新增安装条件，再生成并检查中英文README；不能删除一致性检查或只回退文档。

4. 次级维护项与保留边界

M1 · P3：依赖来源账本落后于锁文件

当前docs入口仍指向dependency-ledger。对固定版本JSON元数据比较，当前lockfile中有而ledger缺少五个package path：sandbox-runtime、其嵌套zod、socks5-server、commander、node-forge；锁文件新增条目可定位。

已有sandbox来源卡记录版本、完整性与许可证，所以不是完全无来源，更不推导许可证违规。问题是正常“Dependency ledger”入口并非完整当前集合。更新同一ledger/hash，或明确标注旧快照并路由当前集合即可。

M2 · P3：MCP“已收到错误”不等于“已知无副作用”

架构合同把已知错误结果写成failure；MCP实现对收到的isError也调用onUnknown，Host回调关闭admission。

保守实现有理由：远端返回业务错误并不能证明没有先产生副作用。这里建议统一合同与恢复预期，不建议为了符合旧措辞放松fence。

不计入确认缺陷的事项

  • compaction同ID不同focus：service仅凭requestId回旧记录，Store有内容hash冲突检查，但对外合同目前只明确同ID回同记录。它是上轮已知、当前仍保留的层间语义不一致，需owner裁决；本轮不重新命名为新增P2。service捷径；Store意图检查；外部合同
  • Core/Host取消结算：finish与close可能重入；Core completed、Host cancelled/unknown可以是不同时间观察的事实，不等于Artifact accepted。当前跨层语义不足以将纯状态差异判为完整性bug，保留诊断/协调项。Host顺序；Work finish/close
  • 源字节损坏后的digest校验：generic memo读取/证据检查不重算源全文hash，而governance reader会重算。未找到受支持写路径能制造“text变、digest不变”的状态，故列损坏恢复加固而不是权限漏洞。Core源读取；证据检查；治理对照
  • Context容量与历史候选正文：v3预算会显式省略整条旧决定并记录数量；closed candidate正文目前没有普适的模型exact reader。可称“有界接续”，不称任意历史长度的完整召回
  • Review未提交理由跨Session、Attention入口先到助手还是队列：保留产品裁决边界，不以审美或一项未明确承诺的持久化偏好当bug
  • setup期间compaction取消、真实OS隔离、所有Runtime等价性：没有足够的新动态证据，不作通过或失败结论
