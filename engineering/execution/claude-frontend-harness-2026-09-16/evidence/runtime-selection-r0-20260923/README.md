# Runtime selection R0 · concrete Host contract proposal

Fixed source: `abcd30e4965fe3d1fd5258a362718ba2835315e9`, branch `codex/runtime-selection-r0-20260923`. **No product code, schema, service, user data or live adapter was changed by R0.**

## Responsibility and decision boundary

The Host must let two ordinary Chats in one process use different *explicitly eligible* executors while each Session keeps one native lineage. RuntimeStore owns the Session choice and immutable Run identity. The composition root owns the finite configured factory allowlist and derives current availability. Runtime Control continues to own Role/profile/Kit composition; Models continues to own Provider/Model and credentials; the Runtime Port describes and executes native operations. Core and its acceptance state do not change. The nearest implemented precedents are `createRuntime`'s injected Pi port, `RuntimeService.#createRun/#executeRun`, RuntimeStore's serialized `createRun`, the P03-C remote action/binding owner, and K3's frozen `runtime.bound`/Kit context.

Pi is the product default. `agents-api` is the sole proposed managed alternate under its original P03 live gate. `pi-local-print` stays a Spark child adapter and cannot be chosen for an ordinary Chat. The already accepted P03-C/D/E native create/root/action/reconciliation records remain authoritative; R1 must not replace them. A test-injected Agents port proves offline behavior only. The current production composition has no verified live Agents configuration, so its public choice remains unavailable until that separate gate is met.

An ordinary Session means `scope: project|unassigned`, no professional `extensionBinding`, and no Spark child assignment. Choice is writable only when that Session has **no Runs, no `hostSession`, no `remoteBinding`, no remote actions, and no child/native execution history**. The first admitted Run freezes its executor lineage, even if it failed before opening a native session. A historical or active Chat cannot hot-swap through this selector. Global Attention, extension Sessions and child dispatch retain their current paths.

## Typed facts and public DTO

| Owner | Proposed schema-22 field or derived fact | Meaning and validation |
| --- | --- | --- |
| Session in RuntimeStore | `executorChoice: { revision: number, adapterId: string|null, configurationRef: string|null }` | Revision starts at 0 and is independent of Runtime Control. A new ordinary Session starts at the Pi adapter ID with the configured Pi factory's non-secret ref. An explicit choice changes ID/ref and increments revision under CAS. `null` ID is reserved for a migrated ambiguous/child lineage and always blocks ordinary Run admission. An old known lineage may have `configurationRef:null` because schema 21 did not record the executor factory's identity. |
| Run in RuntimeStore | Existing `adapterId` plus `executorBinding: { recording:'bound', revision:string, configurationRef:string, capabilities:CapabilitySnapshot } | { recording:'legacy', revision:null, configurationRef:null, capabilities:null }` | New Runs always use `bound`; exact adapter ID remains the dispatch key, so the new field does not duplicate it. The capability snapshot is the closed set of port `describe().capabilities` rows (`start, continue, steer, cancel, compact, recover, submitToolResult` with support and bounded reason). It records what was admitted, not a permission grant or current availability. `legacy` says the old bytes lacked this fact; no revision/ref is invented. |
| Existing Run/Session owners | `run.provider`, `credentialGeneration`, `runtime.bound`, `kitBinding`, `session.hostSession`, `session.remoteBinding/remoteActions` | Stay exactly where they are. The Run's provider/config and the remote binding's connection hash/version/generation are separate from executor factory identity. Validate any repeated native/provider reference for consistency; do not put a remote locator in Pi's `hostSession` or a Kit pin in executor choice. |
| Composition root, derived per read | `ExecutorDescriptor { adapterId, revision:string|null, configurationRef:string|null, capabilities:CapabilitySnapshot|null, availability:{status:'available'|'unavailable',reason:string|null} }` | Only fixed Pi and one explicitly configured managed Agents factory may appear. An unconfigured option may be listed with null details and a reason; only an available descriptor has all three details. `configurationRef` is a stable opaque digest/version of an explicit factory configuration and credential *reference/generation*, never a key, user data path, or Provider/model selection. Agents' current port lacks `revision`; R1 must add a pinned revision before admission. No dynamic executable registry or second credential store. |

`CapabilitySnapshot` is an exact-key object for the seven operations named above, each `{supported:boolean, reason?:string}`; unsupported rows require a bounded reason. New bound revisions are nonempty bounded strings, and new configuration refs have the form `sha256:<64 lowercase hex>` over a canonical, explicitly supplied factory identity (adapter revision, protocol/endpoint identity and credential reference generation, with no secret material). The composition root rejects duplicate IDs. A different ref denotes a different configured executor instance, never an implicit update of a Session with history. The existing single-port test injection may keep its sole injected port as that test Host's default; the product path always defaults to Pi.

Use a new authenticated `GET /sessions/:id/executor-choice` for `{sessionId, choice, locked, lockReason, options}` and `PUT /sessions/:id/executor-choice` with exactly `{expectedRevision, adapterId}`. The Host derives the ref and availability; the caller never submits them. A stale revision returns 409 with no mutation; a lost PUT reply is recovered by GET of the same Session. `locked` is derived from Store history, not a second persistent boolean. The option list reports unavailable reasons; unknown historical IDs remain readable in `choice` but cannot be reselected or silently mapped to Pi. No 06c synthetic field becomes an owner fact through this route.

The existing Run request's `runtimeSelection:{revision,profileId,sourceHash}` remains the **profile/Kit expectation**. Add a separately named optional `executorExpectation:{revision,adapterId}` for a page that read the executor choice. A mismatch is `executor_selection_conflict` before Kit retention or Run/native/provider dispatch. Existing callers without that field continue against the persisted choice; they do not request another executor. The frontend consumer should send both independent expectations. A future UI can present requested Session choice, currently available configured option, and bound Run identity separately; R0 grants no frontend source lease.

## Atomic choice, admission and refusal

1. `PUT executor-choice` resolves an allowlisted, eligible configured descriptor, then performs revision, ordinary-scope and **no-history** checks inside one RuntimeStore `_mutate`. A same-ID update after any history still refuses; the reader may GET without mutation. Different Sessions may choose while another Session's Run is active because this action changes no running port or global provider config.
2. `#createRun` first returns the existing `commandId` receipt, before current executor/profile/provider availability checks. A changed input under the same command ID keeps `command_conflict`. For new work, resolve the saved choice through the configured factory, check ref/revision/capabilities, profile compatibility and Kit eligibility, and pass the choice revision and bound descriptor to Store. `store.createRun` repeats the choice/ref/no-cross-lineage checks **after its receipt lookup and inside its serialized mutation**, before appending a Run/event. If choice wins a race, the Run either binds that exact choice or returns stale; if admission wins, the later choice sees history and refuses.
3. Existing K3 `retainKitContext` receives the selected port's descriptor. Its verified in-process Pi `reference-only-pi-unchecked-v1` policy remains valid; a nonempty Kit on managed Agents refuses before a provider/native request. A concurrent CAS loss after immutable Kit payload retention may leave an unreferenced retained object under today's K3 ordering, but must create no Run, native session, provider request, permission or visible binding.
4. The active Run entry keeps the exact selected port object and `executorBinding`. Execution uses it for native open/start/observations; cancel uses the entry's existing abort handle. Compaction and explicit remote reconciliation resolve the Session's **pinned** port and native shape, never the process default. A post-restart missing or changed factory produces an unavailable refusal without Pi fallback, while historical Run and unknown/action records remain readable. P03-D reconciliation is observation only and keeps lost-create/no-locator and no-result effects fenced.
5. Once a new `bound` Run exists, later Runs require the same adapter ID, revision and configuration ref. A changed factory ref, credential generation or remote connection mismatch refuses rather than rebinding a native history. For schema-21 legacy Runs, the absent factory ref remains honestly unknown: the old Pi locator and remote binding's existing connection checks govern continuation with an explicitly configured matching port, and the first schema-22 Run records the new ref. Thereafter the new ref is fixed. No proof of historical transport configuration is claimed.

| Trigger | Result before new execution |
| --- | --- |
| Unknown ID, child-only ID, nonordinary scope, extension-bound Session | 409 `executor_ineligible`; no saved choice |
| Configured descriptor absent/unverified, ref/revision changed before admission | 409 `executor_unavailable` or `executor_configuration_changed`; no fallback |
| Stale choice PUT or Run `executorExpectation` | 409 `executor_selection_conflict`; no new Run |
| Any Run/native/remote/child history when PUT attempts a change | 409 `executor_lineage_locked` (active history may use `active_run`); existing history unchanged |
| Saved executor differs from native locator or Run lineage | 409 `runtime_mismatch`; no cross-adapter open |
| Port lacks start/continue/recover/compact, or Kit cannot bind to that port | Existing `runtime_capability_unsupported` / Kit typed refusal; no alternate routing |
| Unknown remote create/effect/root after restart | Existing unresolved/unknown fences and P03-D report; zero automatic create, local tool repeat or result resend |

## Legacy 21 → proposed 22

R1 needs a typed Session choice and Run binding, so propose RuntimeStore **21→22**. Validate all schema-21 bytes first; write an exact, exclusive `runtime-state.schema21.<sha256>.json` backup; persist the new state atomically. The pinned schema-21 reader must refuse schema 22 byte-for-byte. Core user schema 4 and bridge app schema 5 do not change. Update only the current schema entry points under `engineering/verification.md` in the later implementation lease; R0 changes no version.

Migration keeps every old Run, event, native locator, remote action, Kit summary and Provider field unchanged except adding `executorBinding:{recording:'legacy',...nulls}`. Derive each Session choice from its *actual* history: one distinct ordinary Run `adapterId` wins even if native create was lost; otherwise a Pi `hostSession` pins Pi; otherwise a remote binding pins its recorded remote adapter; an empty Session gets the Pi default. A Spark child or contradictory mixed adapter history gets `adapterId:null` and stays readable but cannot enter the ordinary selector or admit another ordinary Run. Unknown single historical IDs remain exact strings and fail unavailable when their factory is absent. Never repair old bytes by assuming the current process default. Schema-22 validation cross-checks nonchild Run IDs against a non-null chosen lineage, `bound` Run ref/revision consistency, Pi versus remote locator separation, and all existing action/Kit invariants; a migrated null choice is accepted only for child or contradictory historical lineage and is permanently fenced from ordinary admission.

## Decisive R1 evidence, offline first

1. Schema-21 Pi Session with actual SDK journal and Run upgrades with an exact backup, continues the same locator on Pi, preserves events/Kit context, and old reader refuses 22.
2. One Host with two ordinary Sessions runs Pi/local fake and injected managed Agents/loopback respectively; each has its own frozen adapter, capability and non-secret ref, and no native locator crosses shapes.
3. Two concurrent first-choice PUT/admission orders exercise Store CAS: exactly one winning choice/Run lineage; stale choice and stale `executorExpectation` produce no extra Run/native/provider request.
4. Selected Agents factory missing, unverified or ref changed at restart refuses with its reason and zero execution; Pi does not take over.
5. A nonempty v2 Kit admitted on verified Pi retains today's unchecked policy and exact context; the same declaration on managed Agents refuses with zero provider/native requests. Profile `runtimeSelection` still guards its own revision/hash independently.
6. After a Run, changes to profile/Provider, factory revision/ref or credentials never rewrite historical binding. An attempted Session switch is locked; later admission uses only eligible matching configuration or refuses.
7. Lost Run POST reply and identical `commandId` replay return the same Run/binding before current configuration checks; changed input conflicts; one native create/one provider request at most.
8. Reopen with unresolved remote create or retained effect: explicit observation returns only P03-D evidence, no second create/governed `repo_read`/result send; existing unknown fences remain. Synthetic loopback cannot certify account-authorized live Agents operation.
