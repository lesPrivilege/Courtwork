## What the Viking article establishes

The [Viking article](https://vikingz.me/ai-e2e/) is a dated practitioner account (2026-06-06) of one TinyShip monorepo with three frontend stacks and two databases. Its author describes a Spec → Code → browser Verify → Playwright Test → Green workflow, targets full coverage of that project’s critical journeys, and runs E2E locally for feature, release, and large-refactor checks. That is useful as one team’s workflow, but the six framework/database combinations and local CI constraints are specific to that product; the page does not establish a universal “100% E2E” rule for CourtWork.

The author reports that `agent-browser`’s compact accessibility output saves “80%+” of tokens. The article gives no baseline, sample, prompt, or measurement method, so the percentage is not reproducible evidence and is not carried into CourtWork policy. The example’s `data-slot` and placeholder selectors are also not a default selector recommendation: [Playwright’s current guidance](https://playwright.dev/docs/best-practices) prioritizes user-facing roles/names and explicit contracts over CSS or DOM-structure selectors. A browser pre-run can help expose interaction and UX problems; it does not itself certify the expected state or turn the resulting selectors into a durable contract.

## Primary-source cross-check

- [Google’s *Larger Testing* chapter](https://abseil.io/resources/swe-book/html/ch14.html) says larger tests mainly address fidelity gaps that smaller tests cannot cover, while added fidelity brings cost and failure risk. It discusses real multi-process/API combinations and browser/device tests as one form of functional test. This supports selecting a higher-fidelity check for a specific uncovered seam, not duplicating unit or contract assertions in a browser.
- Ham Vocke’s [*Practical Test Pyramid*](https://martinfowler.com/articles/practical-test-pyramid.html) says acceptance checks can run below the UI when the design permits, and recommends adding a lower-level regression when a higher-level test finds a defect, then pushing checks down when they add no unique confidence. This supports promoting a stable browser-discovered defect to the cheapest owner-level regression while keeping an end-to-end check only for a remaining integration risk.
- [Playwright Test Agents](https://playwright.dev/docs/test-agents) documents planner, generator, and healer agents that explore, produce plans/tests, and retry repairs; its stated outputs include a passing or skipped test. These are test-authoring aids. Their output still needs a human-selected charter, assertion review, and adjudication; a generated or healed test is not release authority.
- [Anthropic’s agent-evaluation guide](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) defines an agent result as the model working with its harness, separates transcript from final environment outcome, and notes that variable model output calls for multiple trials. It supports inspecting the durable artifact/state for a real capability task and keeping that evidence distinct from a deterministic UI check. It does not prescribe a CourtWork trial count.
- [Stately’s current test documentation](https://stately.ai/docs/xstate-test) says the older `@xstate/test@beta` examples are superseded by utilities in `@xstate/graph`, whose testing documentation is still forthcoming. The transcript’s XState/model-based suggestion is therefore a possible later selection, not a settled package choice or reason to add another state model now.

## CourtWork fit and evidence boundary

The current local runner is already lower-layer and deterministic: [`app/package.json`](../../../app/package.json) runs Node’s `node:test` suite at concurrency four and checks historical fixtures first; `test:load` is a separate concurrency-eight entry. [`check:product.mjs`](../../../app/scripts/product-check.mjs) composes that suite, a local runtime smoke, and documentation links. [`runtime-smoke.mjs`](../../../app/scripts/runtime-smoke.mjs) uses a loopback fake provider, calls the public runtime service, closes/reopens the runtime, and checks persisted artifact bytes; it explicitly has no HTTP server, UI, or real-provider call. The root [README](../../../README.md) likewise says the default provider is deterministic and the product check uses synthetic fixtures. No committed Playwright test dependency or configuration was found in the app package or tracked file inventory; browser visual checks are recorded by affected UI work rather than by this package script.

That setup can establish selected Host/runtime contracts and known synthetic outcomes. It cannot prove real-model capability, complete browser interaction, or full visual/accessibility acceptance. Conversely, a real-model run should not be required for deterministic copy, serializer, or service rules. The parent-owned policy already separates these questions, asks why a lower-cost check cannot cover a proposed E2E risk, records a fixed repro and cost, and keeps real-harness evidence outcome-based. The source review supports retaining that local-context selection: one fault tied to one invariant when recovery risk warrants it; a small, deterministic GUI path only when browser wiring or visible behavior adds unique evidence; a separately authorized real-harness task only for a model-capability question. It does not support a fixed number of browser cases, trial runs, or token savings for this repository.
