## Finding — bounded merge blocker at the reviewed source

`PROVIDER_DEFINITIONS` explicitly declares the local fixture’s only protocol as `reasoningFormat: "none"` (`app/runtime/provider-definitions.mjs:27-29`), but `declaredProtocolCompatibility` maps every non-DeepSeek format—including `none`—to OpenAI reasoning and sets `supportsReasoningEffort: true` (`:50-58`). `registrationExtras` applies that helper to catalog extras (`app/server/provider-connections.mjs:165-176`). The saved-model validator accepts an exact `reasoningEfforts` list and derives `reasoning: true` from a non-empty list (`app/server/provider-fields.mjs:107-130`); catalog updates accept model extras (`app/server/provider-connections.mjs:180-189`). Pi’s installed OpenAI Completions encoder sends `reasoning_effort` when `model.reasoning` and `compat.supportsReasoningEffort` are true (`app/node_modules/@earendil-works/pi-ai/dist/api/openai-completions.js:727-735`; the option is documented as defaulting true in its `README.md:1203-1217`).

Minimal counterexample: submit one fixture catalog extra with `reasoningEfforts: ["high"]`, then resolve/register it through `registrationExtras` as `openai-completions`. The registered model becomes reasoning-capable and receives OpenAI `reasoning_effort` serialization despite the fixture protocol declaration saying `none`. The visible Models form hides the reasoning declaration for the local path, but the service input accepts it; this is enough to make the central registry internally inconsistent. `provider-registration.test.mjs:8-28` covers OpenAI and DeepSeek mappings but does not exercise the `none` declaration.

The specific defect was that `reasoningFormat: "none"` could still admit a native reasoning-effort field. No product edit was made in this review.

## Other reviewed boundaries

The centralization itself is coherent across installed declarations, field validation, runtime registration, endpoint admission, and Models rendering. `provider-definitions.mjs` owns API formats, per-provider protocols, endpoint requirements and reasoning format; `pi-session-runtime.mjs:184-207` builds native transport maps from those declarations, while the two concrete SDK modules remain the installed encoder implementations. `service.mjs:20,369-375,940-965` derives allowed catalog identities and publishes the declarations; `providerRouteError` is called both when saving config (`service.mjs:1257-1289`) and when admitting a Run (`:1727-1738`). `#admissibleModel` still requires an actual runtime model and, for compatible connections, membership in that connection’s saved list (`service.mjs:863-877`). Unknown/missing definitions do not produce selectable protocols. The UI labels these as installed protocol handlers and says model support is checked separately (`settings-view.mjs:99-106,1166-1204`); the declaration is not evidence of a remote model’s live support.

Credential identity remains connection-scoped. Catalog IDs are derived as `catalog-<provider>` and map to one installed provider identity (`provider-connections.mjs:25-57`); compatible records require `id === providerIdentity` with a `conn-` prefix (`service.mjs:940-949`). File credentials use the connection ID, while the Pi runtime slot uses that connection’s provider identity (`service.mjs:952-964,967-972`); legacy provider-ID keys migrate only onto matching catalog connections (`provider-connections.mjs:194-207`). The integration test added for the registry confirms that two compatible IDs use different key slots and do not replace the catalog fixture key (`provider-connections.test.mjs`, PV-26 case).

Endpoint selection is enforced at both boundaries. A compatible connection’s API and endpoint must match its own saved record at `/provider-config` (`service.mjs:1269-1274`); explicit-endpoint protocol declarations require a base URL in the shared route check (`provider-definitions.mjs:41-47`). In Models, selecting another provider or compatible connection clears/replaces the old endpoint and API state, and missing explicit endpoints disable save (`settings-view.mjs:1044-1080,1166-1204,1248-1260`). Editing an existing compatible connection preserves its identity and, if no replacement key is entered, reuses that connection’s saved key for discovery at the new endpoint (`service.mjs:1082-1104`). That follows the existing “one connection = endpoint, wire format, key and model list” contract; it is also a credential-transmission consequence that the UI currently describes only as a key saved “for this connection” (`settings-view.mjs:1221-1226`). This review does not treat it as an independent regression, but it should remain explicit in product wording.

Existing Run freezing remains in force: provider/connection/credential changes reject while a Run is active (`service.mjs:1070,1137,1260,1294+`), and Run admission is serialized with configuration writes. The run record receives the selected provider/model/API/base URL, `connectionId`, `credentialSource`, and reasoning binding/config version (`service.mjs:1677-1715`); execution resolves from that captured provider snapshot. Runtime tool exposure and permission policy remain Host-owned: provider definitions carry no tools or permission fields (`provider-definitions.mjs:12-34`), the Runtime summary links to the existing Tools/Permissions owners (`runtime-view.mjs` in the reviewed commit), and the service’s tool/policy execution paths are untouched by this change.

One provenance limit remains explicit in the delivery note: `PROVIDER_DEFINITION_VERSION` is returned publicly but is not copied into a Run binding, nor is the derived `definitionId` frozen into the Run. The Run still records the route and existing reasoning/config version; the provider registry is build-installed and has no hot reload. This is not a regression to the current freeze behavior, but durable interpretation across future definition revisions is not covered by this slice. Do not claim versioned provider-definition replay from this commit.
