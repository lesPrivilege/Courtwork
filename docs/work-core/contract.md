# Work Core v1 / frontend seam

Construction baseline: `43e3dc058b77cb38d295b261b977469accc18478`. This document freezes the backend semantics for Fable; implementation/independent evidence is recorded in `evidence/harness-core-20260908/`. No frontend completion is implied.

## Ownership and compatibility

`app/core/core.py` owns transactional Matter/Candidate/Decision/Artifact state (B0 SQLite state + audit). `bridge.py` owns the private typed transport and Run admission. `client.mjs` is the sole worker client implementation. The host owns one client; extension lifecycle does not close it. The old evidence-memo client path only re-exports it. Existing data stays at `extensions/evidence-memo/state.db` under the private runtime data directory; the name is a compatibility coordinate, not a second domain owner.

Current persistence is Core user schema **4** / bridge app schema **5**; [BG-01 governance](governance.md) adds Matter disclosure policy/event/receipt and owner-backed directory reads. Runtime JSON is **8** (validated schema 3–7 upgrade; see [runtime persistence](../runtime-control/architecture.md#persistence-upgrade)). The [Attention contract](attention.md) specifies the same-owner Attention domain, scoped HTTP/Runtime seams and the migration from final ES Core2/app3. The file-candidate section below records the preceding ES migration and its unchanged file semantics. The earlier Core1/app2 delivery added source history and project ownership; historical backup names and receipts for that delivery remain historical. Migration never invents previously deleted source membership.

Generic envelope fields: `schemaVersion:1`, `contractVersion`, `matter` (id/version/source_version/contract_version/active_artifact/obligations), `candidates`, `artifact`, `sources`, `decisions`, `runs`, `stateVersion`, `humanActions`, `readOnly`, `compatibility`. A candidate is immutable and may carry versioned `domain` payload, `supersedes`, and host-derived human revision `provenance`. Core interprets identity/version/evidence/authority, while the domain adapter interprets rules. Run records freeze public provider identity/executionMode; old simulation records retain their original descriptors.

## Queries

All HTTP routes below have `/api/v5` prefix and use existing local host authentication.

- `GET /sessions/:id/surface`: `{extension,projection}`. Inline/detail consume the same packet and version. If the producer is absent, extension is null and Core history remains available with `readOnly:true`, no humanActions. Unloaded/invalidated producer also exposes no legal mutations. Unsupported contract versions are read-only.
- `GET /sessions/:id/work-query?kind=request&requestId=...`: `{schemaVersion:1,result}`; null means no committed receipt. A receipt from another Matter is rejected.
- `GET /sessions/:id/work-query?kind=source&candidateId=...&sourceId=...&version=1`: historical source bytes from the candidate's frozen source-set revision. Both candidate and source membership are checked against the Session's Matter. This remains available without a producer.
- `DELETE /sessions/:id`: logical deletion of execution catalog records after preserving work ownership; Core work survives. Workspace/journal bytes remain private on disk. This is not secure erasure.
- `GET /projects/:id/work`: durable project-owned Matter identities and extension IDs for continuation. No automatic Matter is created for plain Chat.

## Binding and actions

`POST /sessions/:id/extension` keeps `{extensionId,input}`. New evidence-memo input remains `{title,sourceText}`. Existing work uses `{existingMatterId}`; backend checks durable project + extension ownership. Optional `fromSessionId` supports explicit legacy binding migration, with same-project and exact Matter/extension checks. Bare unowned IDs fail. `{detach:true}` releases the current execution binding after preserving project ownership; formal work survives and plain Chat resumes.

`POST /sessions/:id/actions` keeps `{extensionId,generation,action,payload}`. Actor is host-owned; any actor field is rejected. Mutations require loaded producer, current generation, and no active Run.

| Action | Payload / effect |
|---|---|
| `decide` | `{request_id,candidate_id,base_version,action:'accept'|'reject'|'request_evidence',reason}`. Request ID binds full content. Accept alone atomically creates Artifact, advances version, updates obligations, and appends Decision/audit/receipt. |
| `revise_candidate` | `{candidate_id,new_candidate_id,base_version,proposal:{artifact_text,evidence,obligations}}`. Saves a new candidate, points to parent, preserves old bytes/decisions. Reusing new_candidate_id with changed content is rejected. NDA adds a verified domain payload to proposal. |
| `replace_sources` | `{sources:[{id,version,text,digest}],revision}`. Revision must increase; source id/version bytes are immutable. Old candidates remain readable but stale for subsequent decisions. |
| `save_draft` | `{text}`; draft has no formal effect. |

Legacy action queries `query_request` and `read_source_history` are retained for adapter consumers; frontend should use the GET routes, which work without producer activation.

Legacy memo/NDA `humanActions` descriptors have `schemaVersion:1`, an `action` name, a display label, and `payloadSchema`. The Work envelope and domain contract versions remain unchanged; this is an additive action descriptor. Unknown action versions/names must remain non-executable to the consumer.

`decide` is advertised only for pending candidates whose base/contract/source still match current Matter. Its allowed decisions are `payloadSchema.properties.action.enum`, not separate top-level action entries. `revise_candidate` is advertised for readable candidates of the supported current contract, including accepted/rejected or source-stale parents: `candidate_id.const` binds the parent, `base_version.const` binds the current Matter version, and the client supplies a fresh `new_candidate_id` plus `proposal`. The NDA adapter supplies exactly `{domain}` as the proposal schema; generic memo revisions use `{artifact_text,evidence,obligations}`. Proposal validity is still verified by the server against current sources/facts. A revision never revokes an earlier Decision or Artifact.

The host returns `readOnly:true` and no actions while any host Run is active, just as it already refuses human actions during that Run. Producer absence/unload and unsupported contracts also expose no mutations. Clients never infer authority from Run completed, tool permission, or a visible button; server revalidates. Domain completion may further restrict accept. Refresh surface after mutation or a conflict; retry decisions with the original request ID and content after losing the acknowledgement.

## Errors and fixtures

Core errors are HTTP 409 with `{error:{code,message}}`; host errors keep existing status/code. Important codes: `VERSION_CONFLICT`, `STALE_INPUT`, `IDEMPOTENCY_CONFLICT`, `BINDING_MISMATCH`, `CANDIDATE_CLOSED`, `EVIDENCE_INVALID`, `OBLIGATION_OPEN`, `OBLIGATION_INVALID`, `CONTRACT_UNSUPPORTED`, `SCHEMA_INVALID`, `SCHEMA_NEWER`, `DB_IN_USE`, `CONTEXT_BUDGET`. Host admission includes `generation_mismatch`, `active_run`, `binding_mismatch`, `binding_exists`, `unknown_field`.

Executable synthetic fixtures: `app/tests/work-core.test.mjs` (Core independent of runtime/provider/UI), `work-continuity.test.mjs` (actual service/Pi loopback), and `fixtures/work-core/crash.py` (real SIGKILL around commit). Source anchors use Unicode code-point offsets and UTF-8 SHA-256; no personal data or paid provider is used.

## Context projection v2 and bounded Artifact reads

New Run Context uses `schemaVersion:2` inside the stored `workContext.text`; existing v1 Run snapshots remain immutable. The Work envelope, database and domain contract versions are unchanged. The active Artifact projection contains ID, originating candidate, accepted version when known, content digest/length, source/contract baseline and basis reasons. It does not inline the body or replace it with an unverified summary. `se_read_artifact` retrieves exact immutable text in pages. Pending candidates carry base/source/contract versions plus `basis.current/reasons`; this describes input applicability, not permission or domain completion. Source/contract changes can mark an active historical Artifact's basis stale without undoing its historical acceptance.

`se_read_artifact({artifactId,offset?:0,limit?:4000})` is a read-only, namespaced tool on a loaded compatible Work Extension. Offsets and limits are Unicode code points; limit is 1..4000. The private Core bridge verifies an open Run bound to the Matter, and joins Artifact to its owning candidate/Matter. ID is never interpreted as a path or URL. Cross-Matter IDs fail `BINDING_MISMATCH`; late calls fail `CANDIDATE_CLOSED`; invalid ranges fail `INVALID` (adapter shape errors use `INVALID_INPUT`). The response carries `artifactId`, `candidateId`, `contentDigest`, `offset/end`, `lengthCodePoints`, `text`, and nullable `nextOffset`. Reads verify the persisted content digest. Immutable historical artifacts in the bound Matter remain readable by ID; their text does not confer current authority.

Required obligations/domain constraints remain complete in Context. If this metadata exceeds the 24,000 JavaScript string-length budget, `CONTEXT_BUDGET` still refuses explicitly before creating a Run. Artifact body size alone no longer consumes that budget. This does not solve arbitrarily large obligation sets or domain payloads. Human projection still includes the full Artifact.

`artifact_text` is literal content. URLs and path-like text are allowed without dereferencing them; NUL remains invalid. Filesystem/network tools retain their own access rules. New tests cover supported 100/25,000/100,000-character artifacts and new-Session continuation, scoped reads, and literal URL content. See [Pro dispositions and evidence](../../evidence/pro-review-remediation-20260908/README.md).

## Validation boundaries and frozen delivery

Code baseline `133269184468f1adf3b38acfc59091818daeb8e8`. Generic pending proposals may retain unverified evidence for review; only accept validates evidence and confers formal effect. Reject/request_evidence do not certify that evidence. The NDA adapter verifies domain evidence before saving any proposal. Terminal Core Run fields are immutable except exact replay; candidate references must belong to that Run and Matter. Missing or partial existing application schema metadata fails closed.

The host requests globally serialized admission atomically in RuntimeStore; standalone Store callers retain per-Session admission semantics. Work Context freezes selected/omitted inputs and host runtime profile provenance in the Core Run. See [NDA seam](nda.md) and [frozen packets](../../app/tests/fixtures/work-core/nda-packets.json) for pending, accepted and producer-unloaded examples.

A failed extension settlement keeps host status `unknown` with `extension_finish_failed`. The work adapter queries durable Core state: an existing terminal result is preserved; an active orphan is closed `unknown` before a new command proceeds. No finisher/tool effect is replayed. If reconciliation itself fails, a separate `extension_reconcile_failed` event records the need for recovery; host restart remains the recovery path when Core is unavailable. Partial tool events use `tool.update`, with only `tool.result` terminal.

## ES-01: opt-in recorded file memo

This B0-only capability uses the existing Core, Matter, Candidate, Artifact and Decision owners. Create via `POST /sessions/:id/extension` with `extensionId:"evidence-memo"` and `input:{title,sourceText,profile:"file-memo-v1"}`. The new Matter stores `se-file-memo-v1`; omitted profile retains legacy memo. Existing Matter bindings retain their stored contract. NDA, ordinary Chat and read_only tool policy are unchanged.

Only this profile installs `se_read_candidate_file` and `se_read_artifact_file`, and extends `se_submit_candidate` to `{artifact_text,evidence,obligations,recordedFiles:[{path,sha256}],supersedes?}`. No actor, coverage, verifier or PASS is accepted from model JSON. A successful `ws_write` adds a model-visible `recordedFile:{path,bytes,sha256}` receipt after persistent append; permission alone is not a receipt. The host selects the earliest matching current Run record, imports full verified ArtifactHistory bytes, and rechecks admission. It never imports mutable workspace text, HTTP previews, another Run's records or orphan blobs. Duplicate logical paths, duplicate append indices, missing Session identity and invalid/non-timezone ISO timestamps are rejected.

The selected-recorded-versions-v1 manifest contains `path,bytes,sha256,sessionId,runId,recordIndex,kind:"content-version",writtenAt`, sorted by ASCII path. It does not describe a simultaneous directory snapshot, deleted files, renames or all Run outputs. Core stores the manifest, UTF-8 BLOBs, frozen basis and immutable verification with a complete-record checksum in the Candidate save transaction. Identity covers all legacy fields, manifest digest, basis and trusted policy requirement. Old hashes are not rewritten. Closed-Run exact save replay uses the original candidate ID and complete identity; changed content conflicts.

Limits: 1–16 files, 65,536 UTF-8 bytes per file, 131,072 per bundle; portable relative ASCII paths up to 240 bytes, without empty/dot/dot-dot segments or case-fold duplicates. Empty files are valid; NUL, invalid UTF-8 and isolated surrogates are not. BOM and newlines are preserved. Complete non-file Candidate identity metadata is limited to 32,768 UTF-8 bytes. New request lines and all response lines, including envelope/newline, are limited to 1,000,000 UTF-8 bytes and JS UTF-16 code units; excess fails explicitly. Whole snapshots remain bounded responses, not an unlimited-history capacity guarantee.

`file-memo-fixed-basis-v1` means closed **declared work inputs**, not all model knowledge. It freezes full source membership/revision fingerprint, current base Artifact or null, Run instruction, actual Pi system prompt (including its cwd suffix), emitted host-context message, admitted tool schemas and runtime revision/hash. The private Run input descriptor remains in Core; only bounded hashes/references enter projection. A fresh Session with no persisted entries and no actual Pi messages can be complete. Existing history remains unknown. Host compaction-enabled mode is conservatively unknown from admission, before any summary can reach a model; complete first-path consumers use compaction disabled (the loopback default). This is not a claim of tracked compaction provenance.

All admitted tools pass the awaited input observer. Source reads, submission, writes and reads of the frozen base are allowed inputs; workspace read/list/grep, ask_user, MCP, runtime_load, other candidate/artifact reads and host steering/follow-up/custom input mark coverage unknown before execution/delivery. Permission decisions introduce no new material. Pending coverage writes are drained before save; a failed marker permanently blocks further file submissions in that Run. A later input does not rewrite an already-frozen Candidate. Missing/mismatched sources, base or policy prevent acceptance. `file-memo-structure-v1` requires source evidence and valid quotes/obligations; semantic failures persist as failed diagnostics, incomplete coverage as unknown. A structural PASS is not professional-quality approval.

The generic Work envelope stays v1 and adds `fileCapability:{schemaVersion:1,contractVersion,queries}`. Each file Candidate has bounded `files` summary: digest/count/bytes, coverage, verification, basis references/fingerprint, verifier and reasons/acceptable. File decision descriptors use **action schemaVersion 2**, with `fileCapabilityVersion:1`; legacy consumers must not execute them. Every file-profile HTTP human action additionally requires top-level `fileCapabilityVersion:1`. Omitting it fails 409 `CONTRACT_UNSUPPORTED`, including on old-client retries; recognized clients preserve exact request IDs for replay. The pure-text memo renderer is suppressed (`surface.module:null`) for this contract, leaving the current GUI's read-only fallback. No file GUI is claimed. Generic `revise_candidate` is forbidden; use a new Run with explicit supersedes.

Read through `GET /sessions/:id/work-query`: `kind=file-manifest|file-content|file-diff`, exactly one of `candidateId` / `artifactId`, plus `path` for content/diff, `offset` and `limit`. Ownership is derived from Session binding; producer absence is supported. Manifest offsets count entries, limit 1–16; content offsets count Unicode code points, limit 1–4000. Pages carry Candidate/Artifact and bundle/file identities, offset/end/nextOffset, byteLength and codePointLength. Every content read checks complete stored bytes before slicing. File model readers take `{candidateId|artifactId,path,offset?,limit?}` and require an open bound Run. Unknown file schemas expose scoped metadata only, never decoded content or acceptance.

Diff requires a Candidate and the same path in its frozen base Artifact. `codepoint-prefix-suffix-v1` returns a deterministic linear-time replacement (`offset,removed,inserted`) and both final-newline flags; it is not a filesystem patch. Missing correspondence yields `unavailable:no_corresponding_record`; legacy text bases yield `base_not_file_bundle`. An unmatched selected path may say `only_in_selected_candidate`, never infer deletion. Combined input limit is 131,072 bytes; output JSON limit is 32,768 bytes. Oversized results say `unavailable:too_large`; no truncation is represented as a complete diff.

New refusal codes include `FILE_LIMIT`, `DEPENDENCY_INCOMPLETE`, `VERIFICATION_REQUIRED`, `POLICY_STALE`, alongside `INVALID`, `INTEGRITY_REFUSAL` and existing binding/CAS/admission errors. Private Core errors remain HTTP409; malformed host envelopes retain host400 codes. Tool errors remain tool results and do not create candidates. Decide rechecks identity, complete basis/current policy, required source evidence and obligations in the existing transaction, then writes the Artifact bundle relation, version, Decision, audit and request receipt together. Accept never exports or overwrites workspace files.

Migration supports validated Core1/app1 and Core1/app2. Under the existing POSIX DB lock, all owned table columns, PK/unique/FK/CHECK constraints and membership trigger are validated before backup. SQLite backup creates `.pre-file-core-v2-app-v3.bak`; any existing backup is refused without replacement. File DDL, source-history backfill and both version updates commit together, with full schema revalidation before commit. Current-schema missing/malformed tables are refused, not repaired silently. Old Store and old bridge refuse Core2. Restore a backup only into a separate directory with its matching old host; never hand upgraded runtime4 data to an old binary. B1 experiment file imports are explicitly unsupported.

Executable evidence: `app/tests/execution-file-candidates.test.mjs`, `execution-file-continuity.test.mjs`, and `fixtures/work-core/file-candidate-crash.py`. `node app/scripts/file-candidate-fixture.mjs` regenerates actual synthetic HTTP/Pi/Core packets in `file-candidate-packets.json` (consumerFixtures): ready, unknown, failed, stale, accepted, rejected, producer-absent, unsupported and missing-bytes. Pending-unchecked is deliberately unrepresentable because verification commits with Candidate bytes. Corruption/unknown-schema examples explicitly label their isolated fault injection. These fixtures do not close real-provider, GUI or product acceptance gates.
