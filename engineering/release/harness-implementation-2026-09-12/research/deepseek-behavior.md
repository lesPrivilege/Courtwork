# DeepSeek model and Pi replay behavior

**As of 2026-09-12.** This is a protocol and observability review of the hosted DeepSeek Chat Completions path with the installed Pi 0.85.1 SDK. It is research evidence, not product acceptance.

## Decision

The live path now has direct evidence that the requested legacy model name routes to DeepSeek’s new V4.1-Flash service and that the current same-session replay path works across the tested turns. Keep the focused telemetry change that records provider response metadata beside the configured model. The evidence does not justify a broad adapter rewrite.

The remaining adapter risks are narrower: mixed histories where a tool-only assistant turn was produced with thinking disabled and later replayed with thinking enabled, and cross-provider history replay into DeepSeek. The community reports for these cases are older, user-authored, and not confirmed against this harness’s current path. Reproduce them with the pinned SDK before changing request serialization.

## Current route and identity

DeepSeek’s 2026-09-10 release announcement says V4.1-Flash is live at the canonical route name **deepseek-flash**; the retired V4-Flash name **deepseek-v4-flash** temporarily routes to V4.1-Flash. The announcement schedules **deepseek-v4-pro** to route to V4.1-Flash starting 2026-09-14 at 04:00 UTC. The release announcement is the current source for routing: the API changelog and Chat Completions schema still show the older V4 names and are stale relative to the release note. See [DeepSeek’s API release note](https://api-docs.deepseek.com/news/news260910), [DeepSeek’s news page](https://www.deepseek.com/en/news/deepseek-v4-1-flash/), [the older changelog](https://api-docs.deepseek.com/updates/), and [the Chat Completions schema](https://api-docs.deepseek.com/api/create-chat-completion).

The parent’s live trace requested deepseek-v4-flash and received provider response model deepseek-flash plus a response ID. Across five successful Runs and eight model turns, the last tested turn continued the same native session after a host restart and returned the expected marker. This verifies the alias route and the tested continuity path; it does not identify an immutable weights or deployment revision. The resulting trace is linked at [live DeepSeek evidence](../evidence/live-deepseek/trace.json) and [the post-identity-fix trace](../evidence/live-deepseek/after-identity-fix.json).

The focused telemetry patch keeps the configured model identity separate from the SDK’s provider response metadata in [request-telemetry.mjs](../../../../app/runtime/request-telemetry.mjs). In Pi 0.85.1, the OpenAI Completions adapter records the response ID and records responseModel when the streamed chunk’s model differs from the configured ID; it initializes message.model to the configured ID. Therefore a normalized message model is not proof of the served route, and a null responseModel means only that Pi did not observe a mismatch. The DeepSeek response schema also lists system_fingerprint, but Pi 0.85.1 does not retain it in this adapter. If exact deployment tracking becomes a requirement, a small allowlisted metadata extension could capture that field when returned; a response ID identifies a completion, not a model build (an inference from the API schema’s per-completion ID and absence of a published build field). Relevant local sources: `app/node_modules/@earendil-works/pi-ai/dist/api/openai-completions.js` (openai-completions.js) and [the response telemetry code](../../../../app/runtime/request-telemetry.mjs).

## Protocol contract and installed adapter

DeepSeek’s [thinking-mode guide](https://api-docs.deepseek.com/guides/thinking_mode/) says thinking is enabled by default at high effort. When a request includes the tools parameter, prior assistant reasoning_content must be replayed on every subsequent user turn, even if that assistant turn did not invoke a tool. Omitting it can produce HTTP 400. The guide also says temperature and top_p have no effect in thinking mode. For controlled checks, keep effort fixed at high and avoid treating sampling settings as meaningful controls. The official guide and API schema disagree on how xhigh maps, so do not use xhigh to compare runs until that documentation is reconciled.

The installed `app/node_modules/@earendil-works/pi-ai/dist/providers/data/deepseek.json` (Pi DeepSeek catalog) still names the model deepseek-v4-flash and marks it as a reasoning model with DeepSeek-specific thinking compatibility. In `app/node_modules/@earendil-works/pi-ai/dist/api/openai-completions.js` (the installed completions serializer), a signed thinking block is serialized into its matching reasoning field, including reasoning_content, and the serializer supplies an empty reasoning_content field when a required field is absent. The same-model history path preserves signed thinking. In contrast, `app/node_modules/@earendil-works/pi-ai/dist/api/transform-messages.js` (transform-messages.js) downgrades cross-model thinking blocks to plain text. This makes provider switching within a persistent session a distinct risk from ordinary same-model continuation.

DeepSeek’s official V4.1 [model card](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash) and [encoding reference](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/blob/main/encoding/README.md) describe changes to the native model prompt format, including DSML tag spelling and numeric reasoning effort. They also point to deepseek-recipe for mapping Chat Completions, Responses, and Messages into that native format. These are relevant to direct model hosting or a native encoder. They do not establish a need to change this harness’s hosted Chat Completions JSON adapter.

The project’s [DRT-02 synthetic probe](../evidence/DRT02.md) already passes four cases with Pi 0.85.1, including high-effort replay, tool-call IDs, a synthetic missing-reasoning 400, and denial/approval followed by a new Run after graceful reopen. The current live trace adds provider evidence, GUI permission/readback, and wrapper/focus verification. Neither result establishes crash recovery for DeepSeek or model quality. The latest telemetry-focused checks are recorded in [identity-tests.txt](../evidence/live-deepseek/identity-tests.txt).

## Community reports and their limits

Pi issue [#8838](https://github.com/earendil-works/pi/issues/8838) reports a second-turn 400 with Pi 0.84.4 when actual reasoning_content was not echoed. Pi issue [#8779](https://github.com/earendil-works/pi/issues/8779) reports a narrower mixed-history failure: a tool-only turn was sent with thinking disabled, then later replayed with thinking enabled; isolated message-set tests passed, while the mixed session failed. Both were auto-closed as untriaged reports. They are useful repro hypotheses, not current-path proof. This harness fixes effort at high, and its live eight-turn trace succeeded.

OpenCode issues [#24104](https://github.com/anomalyco/opencode/issues/24104) and [#24190](https://github.com/anomalyco/opencode/issues/24190) contain firsthand 2026-04 reports of reasoning_content being stripped during resumed or tool-call history replay. They are useful evidence that adapter history normalization can trigger this provider error, but they predate V4.1 and the current Pi version. Pi PR [#8732](https://github.com/earendil-works/pi/pull/8732) proposes preserving reasoning blocks when replaying cross-model history into DeepSeek. Its timeline says the PR was auto-closed under the repository contribution policy; treat it as a proposed fix, not an accepted upstream change. The installed transform code still lacks that DeepSeek-specific cross-model branch.

## Focused experiment matrix

| Case | Status and setup | Evidence to capture and interpretation |
| --- | --- | --- |
| Same-session live baseline | **Completed:** request deepseek-v4-flash at high effort, exercise normal turns and tool/permission flow, then continue the same native session after host restart. Record the marker, completion state, permission result, and artifact readback; do not infer immutable model revision. |
| Tools supplied, no tool invoked, then follow-up | **Covered by the current trace:** first two Runs answered without invoking tools, then the third Run invoked a tool in the same native session; tools were supplied throughout at high effort. | The tested boundary completed without HTTP 400; native structural evidence records signed thinking presence. This is bounded protocol evidence, not exhaustive replay coverage. |
| Thinking-disabled tool-only turn, then thinking enabled | **Conditional hypothesis from Pi #8779:** run only if the harness can change effort/thinking state mid-session. Create a pure tool-call assistant turn with thinking disabled, then replay the mixed history with thinking enabled. | Compare the actual outbound message shape for that turn with the provider error. An empty fallback alone may be insufficient in this mixed case; do not add a fallback policy unless the pinned 0.85.1 path reproduces it. |
| Cross-provider replay | **Conditional:** only if the product supports switching provider/model while keeping the same SessionManager history. Create a signed reasoning-plus-tool-call turn on another OpenAI-compatible provider, switch to DeepSeek, and continue. | Check whether the transformed assistant message retains actual reasoning. The current transform converts cross-model thinking to text; the DeepSeek serializer can then add only empty reasoning_content, which may still fail the documented replay contract. If this supported path fails, a targeted DeepSeek-aware history transform is more appropriate than a broad adapter rewrite. |
| Alias comparison | **Optional routing check:** in separate clean sessions send the same minimal prompt at high effort once with deepseek-v4-flash and once with deepseek-flash. | Compare requested ID, provider response model, response ID, and system_fingerprint if available. This verifies route compatibility; because both names currently route to V4.1-Flash, it is not a model A/B quality test. |

For any real trace, keep the observability allowlist to requested provider/model/API, requested and effective effort, provider response model/ID and fingerprint when available, SDK version, UTC timestamps, status/retry/finish reason, usage, tool-schema or fixture hashes, session identity, and artifact/permission outcomes. Record reasoning-field presence, length, or a digest where needed; do not log API credentials, full prompts, or chain-of-thought text.

## Research coverage and source quality

The review used 11 targeted Exa searches with a requested-result count of 82 and 51 unique returned URLs. Primary DeepSeek release/docs/model-card sources and the installed Pi source were used for technical conclusions. GitHub issues and pull requests are clearly treated as individual reports or proposals; their statuses and version/date limits are called out above. Third-party blog summaries were excluded where first-party documentation was available.


Installed-source coordinates above are reproducible with `npm ci` in `app/` using the committed lockfile (Pi 0.85.1); node_modules is not a versioned repository artifact.
