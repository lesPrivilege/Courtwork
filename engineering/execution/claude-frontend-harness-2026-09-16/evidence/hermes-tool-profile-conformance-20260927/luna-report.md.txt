The probe installed fail-fast guards before Hermes imports for `subprocess.Popen/run/check_call/check_output`, `os.system/popen`, `socket.socket`, and asyncio subprocess creation. The JSON result reports no calls and no `AIAgent`, gateway, `MCPServerTask`, provider, socket, or subprocess execution. The temporary Hermes home contained no files after the run.

Import-side-effect inspection found that `model_tools` calls `discover_builtin_tools()` and `discover_plugins()` at module import (`model_tools.py:147-161`), while MCP discovery is deliberately not run there (`:150-152`). The probe replaced those two discovery edges before importing `model_tools`. This keeps the actual resolver/selection code under test while avoiding bundled/entry-point plugin imports and builtin tool-module imports. MCP SDK readiness, config loading, cross-process discovery locking, and registration were replaced only at their I/O edges; `discover_mcp_tools` itself was executed.

## Observed results

The JSON result is `status: pass`.

- Missing or `null` `platform_toolsets.api_server` resolved the actual broad API set, including representative native toolsets `file`, `skills`, `terminal`, and `web`, plus both enabled MCP names.
- Explicit `platform_toolsets.api_server: []` resolved exactly `cw_attention` and `other_server`: no native toolsets, but all globally enabled MCP names.
- Explicit `platform_toolsets.api_server: ["cw_attention"]` resolved exactly `cw_attention` even when `other_server` was also configured.
- The actual resolver exposed `rogue_plugin` when plugin keys were unrecorded, and exposed `context_engine` for a non-default context engine. Both are recorded as expected negative leakage fixtures.
- The actual `_make_tool_filter` admitted all three CW names (`attention_list`, `attention_inspect`, `attention_record_signal`) and rejected undeclared `terminal`.
- The actual `model_tools.get_tool_definitions(enabled_toolsets=["cw_attention"])` returned exactly:

  ```text
  mcp__cw_attention__attention_inspect
  mcp__cw_attention__attention_list
  mcp__cw_attention__attention_record_signal
  ```

  Eight synthetic forbidden builtins had `check_fn=always_true`; none appeared in the final definitions. Their absence therefore proves selection exclusion rather than an unavailable-provider check.
- The actual unfiltered `discover_mcp_tools()` captured both configured servers, while the same function with `allowed_mcp_names=["cw_attention"]` captured only `cw_attention`. This confirms API-style unfiltered startup discovery versus explicit caller filtering.

## Limitations

This is a provider-free source conformance probe, not live transport acceptance. It does not import builtin tool modules, discover plugins, start an MCP process, perform an MCP handshake, call a provider, build an `AIAgent`, or exercise `/v1/runs`. The MCP `register_mcp_servers` edge is stubbed, while resolver, tool selection, MCP include filtering, registry definition retrieval, and `discover_mcp_tools` control flow are real pinned code.

Hermes logged `Tool search assembly skipped: No module named 'snowballstemmer'`; the optional assembly failed closed and the exact three-definition assertion still passed. No dependency was installed. The result therefore supports the configuration/selection and startup-discovery claims only; it does not prove native profile startup, transport cancellation, or Host capability enforcement.
