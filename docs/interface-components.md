# Interface component contract

2026-09-07, revised 2026-09-08 (WK-72 / WK-74, WO-WK10b 第一段 and 第二段). This consolidates the composer, message flow and workspace hierarchy after the user's latest screenshot and request. Earlier reading-mark color experiments are superseded.

**Composition.** The main area holds one working surface — the Chat Flow, or the Settings page in its place — and one header band. **What the work surface is depends on the viewport (WK-113 / WK-116, CC-W; this replaces the earlier flat "the work surface is not a third column").** From **1680** up it is a real third column: navigation, chat and document stand side by side and run top to bottom, each scrolls on its own, and their top chromes share one baseline — `--nav` 256, chat at least 640, document at least `--doc-min` 688. Between **1024 and 1679** the collapsed / expanded reading stands: collapsed, the surface is a floating layer of module cards anchored in the main area's right gutter (L2, `--float` + `--shadow-float` + a 1px `--line-strong`), above the thread and above the composer's top edge, with no header and no title of its own; where the main area is too narrow for the 740 reading column and a 360 layer to coexist, the cards collapse to a strip of module glyphs at the right edge. Expanded in that range the surface is a **view switch inside the main area**, not an overlay over it: it takes the main column (1136 at 1440), the chat column keeps its DOM but leaves the screen and the focus order (`hidden` + `inert`), and no scrim and no modal card frame is drawn for it — the sidebar and the header band stay operable. Below **1024** the expanded surface is the whole area, as before. The surface's own band carries one tab strip — the module types as standing places, plus at most one closable document tab (BE-2 is not delivered, so there is one trusted active document and no client-side pretence of more) — and, from 1024 to 1679, a return control that sits on the strip's row, to its left, outside the tablist. The panel's width is not the reading measure: prose inside the document pane keeps `--doc-measure` 740, while a wide table or a code block scrolls horizontally inside itself (WK-117 (b)). This replaces the earlier "Navigator / Work / Inspector" three-column reading and the rail header that went with it; the module registry, the renderer identity, the DOM ids, the ARIA roles and the two-step Escape order are unchanged.

## Shell layout contract (WK-94, 2026-09-09)

Three owners, in this order, and none of them takes another's row:

| Owner | Holds | Never holds |
| ----- | ----- | ----------- |
| The OS or the desktop shell | The window controls — close, minimise, zoom | Anything the product drew |
| The app shell | The sidebar toggle (`panel-left`, in the chrome row) and navigation | The brand, project creation |
| The brand | Identity, in the sidebar header, once | Any action |

**The window-control safe area.** The top-left `--window-safe-area` × `--band-top` zone of the shell — 80 × 52 under a desktop shell — holds no control of the product's own, ever. Two signals turn the reservation on: a desktop shell (Tauri Overlay) sets `html[data-shell="desktop"]`, and a Window Controls Overlay host (Chromium PWA, Electron `titleBarOverlay`) overrides the numbers through `env(titlebar-area-height)` / `env(titlebar-area-x)`. Under either, `.shell-strip` spans the window above all three columns as an inert drag region with nothing inside it, and the band beneath it is one line across the three columns. A plain browser tab reserves nothing. The rule is checked, not only stated: `evidence/fe01/composition-checks.mjs` asserts that no focusable element intersects that zone when the shell signal is present.

**The header band's left slot holds one leaving action (WK-121 ②, re-decided by CC-W).** That slot — after the safe area — is the sidebar toggle in the app, and `Back to app` while Settings is open, because Settings does not render a sidebar to toggle. The work surface does not take it: its `Chat` return control lives on the tab strip's own row, at the left, outside the `tablist` and visually unlike a tab — a return is navigation, a tab is object organisation (WK-117 (b)), and one slot keeps one leaving action. The two-step Escape order is unchanged: the layer first, then the page.

**The sidebar header holds two things: the safe area and the brand.** `+ New project` belongs to the PROJECTS heading, because creating a project is not an app-global chrome action. Collapse and expand are the same control in the chrome row (`panel-left`) in both directions. `x` closes a floating layer, so it exists only while the sidebar is one — the overlay below 1024. Without this rule a future native shell ends up with traffic lights, a brand, a `+`, an `x` and a toggle crowded into the top-left 120px.

## Shape and controls

| Token            | Value | Responsibility                                     |
| ---------------- | ----- | -------------------------------------------------- |
| radius-small     | 4px   | Inline code, compact tooltip                       |
| radius-control   | 8px   | Buttons, inputs, navigation selection              |
| radius-card      | 12px  | Independent workspace and overview modules         |
| radius-container | 16px  | Composer, message bubble, dialog, overview popover |
| radius-pill      | 999px | Compact floating return-to-latest control          |

The round send control remains a circle because it is square. Desktop controls have 32px hit regions; below the navigation breakpoint they have 44px hit regions. Glyphs are separately sized: ordinary controls 18px, response copy 16px, message copy/edit and run disclosure 14px. Visual glyph size must not shrink the hit region. Primary actions use fill, secondary actions a border, repeatable local utilities flat buttons. Focus visibility and accessible names remain mandatory; an icon's appearance is not its accessible name.

## Chat composition

User input is an immutable message record aligned right, sized to its content with an 82% desktop / 88% narrow maximum. Its bubble encloses only the text. A quiet footer contains recorded run-start time and always-available copy/edit utilities. The backend has no separate message timestamp; the time's accessible label and full-date title explicitly identify it as run start. No current-clock or inferred message time is fabricated.

Each agent run is a semantic section containing its tools, permission requests, answers, output and completion footer. The section is visually open so prose remains a continuous reading surface. Cards are reserved for actionable requests and independent workspace modules, not every runtime row.

**One row anatomy (WK-57).** A tool action, an ask-user question, a decided request and a recorded output are the same primitive in the flow: a 16px type glyph, the object's own name, at most one metadata word, and at most one action — which for a disclosure is the disclosure itself. The glyph is decorative and states the kind of act, never the authorisation; the metadata word is a state word in grey, and only a failed row colours it. A row that would need a second action is not this primitive. Pending permission requests stay whole cards, with the exact call's path, bytes, hash and recorded source visible and their scope words spelled out.

**Home's composition (WK-32 / 46 / 56, revised by WK-94 / 96 / 97).** Home reads from the centre downwards, not from a band of numbers at the top: orientation (one sentence, no digits, ≤120), the composer as the page's one L1 anchor, its standing context row, and then the modules that hang off it. The three counts read straight from `/work-summary`'s three sets are the head of the Today module *below* the composer — one strip of three numbers with no card frame, each with its own one-line definition, scope and window. The day-by-day reading is not drawn and is no longer announced on Home: no endpoint returns per-day counts and no day boundary is declared, and an implementation state is not production copy. A count that the answer did not carry reads as words, never as 0. Each tile is a control, and the only thing it does is filter the list below to its own set; the sets may overlap. The module list is one primitive in two states: a row while the three sets are listed together, and a card — the rail's anatomy of a 16px glyph, the object's name, one state word and one trailing action — while the band is filtered to the session set alone, where the recorded run time and an explicit Open have room to be stated. A failed read, an empty set and a truncated page are three different sentences, and none of them is a silent empty list.

**One list keyboard (WK-4).** Home's lower band and the pending cards inside a session are one list: `j` / `k` and the up and down arrows move the focus, `Enter` and `o` open what is focused. There is no `a` / `e` / `d` / `x` and no batch key — this product has no batch decision and no risk field, so a one-key allow would authorise something the person had not read. Opening a pending card moves the focus into it, exactly where a click lands; it never presses Allow or Deny. The keyboard yields to text entry: it is silent while the caret is in an input, a textarea, a select or contenteditable, and during input-method composition, and it takes the arrow keys only when a list item already holds the focus.

`Edit as new message` opens a native dialog and prepares a new draft. Original message and run remain intact. Cancel preserves the composer. `Use as draft` replaces it explicitly, queues the existing draft persistence and returns focus to the composer; it never sends. An existing composer draft is disclosed before replacement. A stale editor cannot write into another session or a readonly submission. Unconfirmed command IDs and their original input are preserved.

## Workspace composition

The workspace file view groups paths by their actual parent directory. Folder cards have one heading/count and simple file rows; directory names are not reinterpreted as review states. Add material opens the existing material form. Existing extension-renderer ownership remains intact.

The session overview separates Workspace, Runs and Session settings into modules. Run history exposes recorded runs already loaded for the session and links to the existing authoritative run inspector. It does not claim additional review, fork, history rewrite, search or archive capabilities.

## Settings

Settings is a page, not a modal (WO-WK12, WK-78, frontend-layering-spec FN-26). While it is open the global sidebar is not rendered — removed from the accessibility tree and from the focus order, not merely hidden — and this page's own group navigation is the only navigation there is; `Back to app` and Escape return to the view, the session and the focus that were there on the way in (WK-116). It replaces the main area's content, so changing a setting is not a step that has to be finished before anything else can be reached; the floating work surface is collapsed on the way in rather than left hovering over the page. It carries a left column — a search box and nine groups named after what a person is doing, General, Appearance, Models, Tools & Integrations, Skills, Memory, Permissions, Keyboard, Developer (WK-90) — and a right column of sections; `#settings` and `#settings/<section>` are deep links, `Back to app` — the one leaving action, at the left end of the page title row and after the host's window-control safe area — and Escape return to whatever was behind with the focus handed back to the control that opened it, and walking to a session or to Home closes it. Below the navigation breakpoint the group list collapses into a top dropdown and the right column is single file. The groups are tabs of one container, with manual activation: the arrow keys move through the list and Enter enters a section, so browsing the groups does not repaint the right column at every keystroke. The search box filters this page's own rows by their title and their sentence; a group with no match leaves, a query with no match says so, and the box stays out of an input-method composition — a key pressed while composing raises no command.

One row is the anatomy already used for the connection form: the setting's name, one sentence of scope or consequence, and one control on the right. **General** holds the File-access default new chats start with — the same value Home's own control writes, not a second copy — and a read-only Data block; the host does not report its data directory over the API, so that row says it is not reported instead of naming a path. **Models** holds the connection form and its API key unchanged in fields and requests, and beneath it the read-only reading of what the runtime is bound to for the next run. **Tools & Integrations**, **Skills** and **Permissions** hold the runtime blocks named in the next section. **Memory** is one sentence about this build and carries no control, because no adapter stores or retrieves memory between runs (BE-19); the words `Matter memory`, `Global memory` and `Temporary chat` are frozen in the vocabulary and drawn nowhere. **Appearance** is this device only: theme, text size, code font, reduced motion and — behind an Advanced disclosure — the palette, each written to `localStorage` under a key derived from the workspace's origin, applied by a synchronous script in the head so nothing is painted with the default first, and never sent to the runtime. At the top of the group sits one live preview built from the real product parts — one Chat Flow row and one diff code block — shared by all four rows that change it, so a choice is read on the thing it changes and the comparison happens in one place rather than four (WK-87). A palette swaps Tier S and nothing else: the roles, the state words, the legal actions and the row anatomy are the same afterwards. A person may paste a Tier S scale of their own; it is checked by the rule `tools/lint-colors.mjs` enforces — existing token names, hex colours, nothing else — and a set that fails is refused line by line rather than half applied. A set that passes is then measured against the same role pairs and thresholds `tools/contrast-report.mjs` measures, and a pair below its threshold is named with its ratio. That is a warning, not a gate: the scale is applied, because refusing a legal scale would make "your tokens" mean "tokens we approved". There is no CSS or JavaScript field, no external font, and no switch that removes approval from a write. **Keyboard** is a read-only table of the keys this build already answers to, with rebinding drawn as a Planned row because no command registry records what may be bound. **Developer** holds the Runtime blocks described in the next section, the extension lifecycle list, the runtime-info readout and the planned-capability rows, which carry no controls.

## Runtime Workbench

The runtime is read and configured through six blocks grouped by intent, not by `kind` (WO-WK11, WK-82, frontend-layering-spec §3.1). WK-90 keeps the blocks and moves where each one lives, so that a person configuring their tools is not first asked to understand what a runtime is:

| Block | Settings group |
| ----- | -------------- |
| Overview, Composition | Developer › Runtime |
| Instructions & context | Skills |
| Capabilities & connections | Tools & Integrations |
| Permissions (policy, scopes, explanation) | Permissions |
| Environment (provider, model, sandbox — read-only) | Models |

`kind` stays as a filter chip inside a block and as the word a row is identified by. One controller holds the authoritative snapshot; the blocks are readings of it, and the coarse card in the work-surface rail reads the same summary rather than fetching a second time. The rail card's Open leads to Developer › Runtime; there is no second catalogue anywhere. The scope strip — the precedence sentence, the scope tabs and the revision — is repeated at the head of every group that can be edited, because a group that edits a layer has to say which layer; it is the same control reading and writing one `scopeType`, not a second one, and each instance keeps its own focus key so focus returns to the strip that was used.

**Four layers, kept apart.** Every configurable item states Source, Requested, Effective and Bound (FN-14). Source is the recorded bytes — type, version, hash — read through the local-user inspector. Requested is what you asked for in the scope you are editing: an unsent draft, or an override the server stored; when something outside the chain still decides the value, the line says the request was recorded and names what outranked it. Effective is the server's own answer for the next run, with the revision it was computed at. Bound is what a finished run actually froze, read from that run's own binding — never reconstructed from today's catalogue, and never changed by a later edit. A layer that is absent says it is absent.

**Overview** states the effective next-run runtime — profile, adapter, how many resources are exposed, how many runs are going — with the next-run context sized in characters, not tokens, and an Attention list of what is not healthy, quiet and host-trusted. An empty Attention list is said out loud, because silence would read as "nothing was checked". Recorded bindings are listed there, and opening one fills the Bound layer of every item in the group.

**Composition** selects the agent profile for a scope, shows what it depends on and where it applies. Selecting a profile is not exposing a resource, and saving a runtime configuration is not publishing a verified Work Expert. A profile's `uiSlots` are declared, not executed. A profile that restricts no resource list says so; that is not the same as one that lists none.

**Instructions & context** separates four admissions: an instruction is injected into every run, a skill or a reference is listed in the catalogue while its body loads only on demand, and a prompt template contributes nothing until you invoke it and it returns a draft. The Effective Context Inspector lists one row per `ContextItem` with its source hash, scope, admission and what it admitted and deferred. A historical record that lacks the additive count is shown as partial and is never recomputed from today's sources.

**Capabilities & connections** has two views of the same objects. *Configurable* is what can be changed here — tools, MCP servers, and the tools an installed extension provides, indented under the package that provides them; remote tools sit under their server, marked `remote` with the hash of the configuration they came from. *Inventory* is what is installed and what it declares: trust and isolation for an extension, authentication and transport for a remote server, and how many capabilities each declares. Nothing on Inventory starts or stops anything; extension lifecycle stays in Developer. Configured, connected, exposed and permitted are four separate facts on every row, and the MCP state words are only `configured`, `connected`, `exposed` and `error`.

**Permissions** reads and edits the policy rules of the scope being edited — the whole list is replaced on save, under the contract's own `policy` operation — and shows the rules the other layers set, read-only. A narrower layer can only tighten: where a rule was saved and did not win, the permission trace says so in words rather than leaving two numbers to be compared. A read-only explanation can be asked for any capability, and it says it grants nothing. Model and provider are read in the Models group instead, where the connection that sets them is edited (FN-05: one capability, one editing entry); the sandbox, session history, host mode and the absent budget are facts the host reports, stated as reported or as not reported.

**What is not drawn.** Kinds the contract names and this host has no adapter for — memory providers, workflows, hooks, registries — appear as text rows with no interactive descendant, in the group each would have belonged to, each naming the backend request that would bring a control back (WK-27).

**While a run is going** the whole group is read-only and says so once, in a sentence that promises nothing: the change is not applied, and it will not apply itself later. An edit made anyway stays a local draft. A stale revision returns the server's own snapshot, keeps the unsent edit as a draft, and never resends it; resubmitting is an act of yours. A read that fails leaves the last confirmed snapshot on screen with the revision it was confirmed at.

**Finding.** The page's search finds a runtime object by its title, id, kind, source and admission word alongside the ordinary settings rows; `/` puts the focus there whenever the Settings page is open, because the runtime's own rows now sit in four of its groups. Enter opens the one object still showing — it expands the row and reads its recorded source. It installs nothing and applies nothing, and the key never fires while a text entry, a contenteditable or an input-method composition holds the focus.

## Domain work surface

A bound work extension contributes one reading of one Work packet, and the host and the producer show the same one. The reading is a candidate list; each candidate carries its identity, its base and source versions, its lineage when the packet states one, and — when the payload declares a domain schema this build knows — one row per rule: the rule's own id, the status word the packet spelled, and under the expanded row its reason, its Unicode source anchor and the quote frozen with that candidate. The reconciliation, the playbook version and the recorded facts are stated once per candidate, not once per rule. Status words are grey; only `conflict` takes a colour, and the word is always present, so colour is never the carrier. An unknown status is not a failure and is not coloured.

Actions exist only because the packet advertises them. A decision button is drawn for a value the `decide` descriptor's enum names, with the candidate and base version taken from that descriptor's own constants, and it is named for its object (`Accept this version`). A revision form is drawn only where `revise_candidate` is advertised; it starts from the parent candidate's own bytes and the extension re-verifies the result. Unknown descriptor versions stay non-executable. A committed decision appears once in the conversation as a read-only row after the Run it belongs to, drawn from the request receipt rather than from the local record: an unread or absent receipt draws nothing.

Where the producer is unloaded, absent, or its declared renderer cannot be read, the same reading is shown with no control and the absence sentence that names the actual condition. Where the domain payload declares a schema this build does not know, only the identifiable envelope is shown and it says so; no finding is reconstructed from field names. Historical source bytes are read from the candidate's own frozen revision and are never back-filled from the Matter's current sources; that read works with no producer at all.

Binding a session to a work extension is two acts in one panel: creating new work from the manifest's own fields, and continuing work the project already owns. The list is scoped to the session's project by the route itself. Releasing a binding returns the session to plain chat and leaves the recorded work with the project.

## Ownership

- `settings-view.mjs`: the Settings page's own controller — the nine groups, the row-level search over both settings rows and runtime objects, the device-local appearance preferences with their token validation and contrast warning, the read-only keyboard table, the one Memory sentence, and the six mount points the groups hand to the Workbench. It reads no data of its own: the connection snapshot and the runtime report reach it from the same controller that already fetched them.
- `runtime-view.mjs`: the Runtime Workbench controller — the one reader of `/runtime-control` and `/runtime-context`, the six intent blocks it renders into those mount points, the local drafts, and the summary the rail card and the host's slot resolution both read. It holds no formal state: every value comes from the last snapshot the server returned, and a bound run's binding comes from the host's own per-run cache rather than a second one here.
- `user-message.mjs`: input record presentation and callback-only copy/edit actions.
- `workspace-view.mjs`: file groups, session overview and run-history presentation.
- `thread-projection.mjs`: server-event projection, including recorded run-start time.
- `app.mjs`: sole owner of session state, async generations, run admission/recovery, draft persistence, navigation, dialog/renderer lifetime, and the work-surface slot resolution.
- `surface-modules.mjs`: the module registry, the host's slot declarations, and the single reading of a Work packet (`workPacket` / `renderWorkPacket` / `candidateActions`) that both the host's read-only fallback and a contributed renderer use, so a collapsed card, an expanded pane and a producer's own renderer cannot state one work state three ways. A slot names its id, the input it hands a contribution and that input's version, the intents a contribution may raise, and what the host shows when nothing is mounted. An agent profile's `uiSlots` is a declaration, not a renderer registry: the host mounts only when a loaded producer contributes a renderer module inside the local extension allowlist, and a declared slot with no loaded renderer is a read-only row with no control.

Views do not own a second session store or independently fetch data. Run grouping does not duplicate or reorder the server event projection. Existing renderer and unsaved extension state survive surface close/reopen.
