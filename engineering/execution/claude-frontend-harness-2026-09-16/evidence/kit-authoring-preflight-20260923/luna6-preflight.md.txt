## Recommendation: one Session-scoped Kit-profile edit → preview → CAS save → Run readback slice

Use existing Runtime Control profile-v2 content and K1 Kit bindings for one ordinary project Chat whose selected executor is Pi. Scope the first implementation to editing an existing profile resource selected for that Session; do not create a role/kit/runtime registry or infer profile/runtime compatibility from the synthetic AgentProfiles model. Reuse the current whole-config CAS, Session profile selection, Run expectation and recorded-context readback. Add one small Host-owned, read-only profile/Kit preflight DTO because the current public reads cannot validate an unsaved draft against the exact effective Host binding.

This is an existing-owner contract plus implementation in one finite order; it does not need a global Kit catalog or a separate per-profile revision. The one missing behavior is previewing an edited profile's exact required resource, compatibility, permission and budget readings before save/admission. Actual resource inspection, source syntax resolution, save, Session selection, permission explanation, Run binding and historical readback already have owners/APIs.

## What exists

- GET /api/v5/runtime-control?sessionId=… returns Runtime Control's authoritative whole-config revision, effective composition/hash, scoped resources, policy explanations, context catalog, profile selections and compatibility flags. There is no per-profile revision. PUT /api/v5/runtime-control?sessionId=… accepts one strict operation under that whole-config revision. operation:'put' writes an imported agent_profile JSON resource; operation:'profile' separately selects a profile at a configurable scope (for Kit use, the explicit Session scope). Kind and owning scope stay fixed for an existing imported resource. A profile resource is not exposure-configurable.
- GET /api/v5/runtime-resources?kind=agent_profile&sessionId=… lists effective profile descriptors; GET /api/v5/runtime-resources/:id?sessionId=… reads the allowed imported resource body/source. POST /api/v5/runtime-sources/resolve is stateless/inspect-only: it validates an inline profile envelope/source but does not acquire, persist, select or prove a Kit binding. Its profile-v2 validation is intentionally shallow; full Kit semantics belong to the K1 compiler.
- POST /api/v5/runtime-permissions/evaluate reports an advisory effect/trace for a tool and concrete resource. It remains owned by Runtime Control/Host permission policy; it is not a grant and the frontend must not interpret Kit allowed-tools declarations as permission.
- K1's pure planKitContext({binding,kits,runtime,compatibilityEvidence,budget}) in app/runtime/kit-context.mjs validates Kit pins/references, resource scope/kind/exposure/hashes, requirements/conflicts, explicit compatibility evidence and budget, and returns exact diagnostics/accounting/candidate. Actual Run admission calls retainKitContext() in app/runtime/kit-run-context.mjs, which also persists immutable plan/context payloads in ArtifactHistory. Do not call that retaining function for preview.
- Run POST uses optional runtimeSelection:{revision,profileId,sourceHash} as a whole-config/profile precondition. On admission the Host retains run.kitBinding and an equal runtime.bound Kit projection. GET /api/v5/runtime-context?sessionId=…&runId=… reads the exact historical binding/Kit plan/context, without consulting mutable current configuration. Same-command replay returns the original Run/binding.
- Current profile-v2 JSON is {schemaVersion:2, version, resourceIds, rules, uiSlots, kits}; kits is an inline array of up to eight exact {descriptor,descriptorSha256} declarations. Each descriptor pins imported content with resourceId, contentSha256 and artifactSha256; there is no standalone Kit resource/catalog. resourceIds remains the profile capability ceiling. The K1 compiler is the semantic validator; parseProfile() only validates the outer v2 shape at save time.
- app/web/agent-profiles.mjs, agent-profiles-view.mjs and agent-profiles-contract.d.ts provide a reusable controller/view and synthetic adapter shape. Its roleId, kitIds, runtimeId, per-profile revision and activeRun:{runId,revision} fields are explicitly proposed; the fixture in app/tests/fixtures/agent-profiles/adapter.mjs is not a production API. The runtime-intake UI/API is a nearby import/source-inspection precedent, not an editor for profile-v2 Kit descriptors.

## Smallest missing Host preflight DTO

Add one authenticated read-only Host operation for an unsaved Kit-bearing profile draft (for example POST /api/v5/runtime-control/preview-profile?sessionId=…). It should accept the Session id in the route, the current whole-config expectedRevision, the exact existing profile resource id/scope and proposed profile JSON content. The Host must construct the candidate binding from current Runtime Control state plus an in-memory overlay of that one draft, through the same control-plane resolution/permission/resource path used by Run admission; do not accept a caller-assembled RuntimeBinding.

Return only owner facts needed for the editor: the revision and draft source hash previewed; Session scope and selected executor id/revision/capability; resolved profile composition/status/missing resources; K1 planKitContext status, normalized Kit pins, requirement/reference/compatibility readings, diagnostics and exact byte/character budget/candidate hashes; permission-owner effect/trace for requested actions; and saveAvailable/reason. Do not return a made-up saved/per-profile revision, role/runtime fields, active Run binding, credential/provider fact, or compatibility evidence inferred from a declaration. A capability-unsupported managed runtime should report its typed refusal; the current Kit admission path supports the verified in-process Pi interface only. Keep unchecked distinct from unsupported, and permission deny/ask/allow distinct from runtime support.

The preview must be side-effect free: no runtime-control.json/RuntimeStore write, audit/revision bump, ArtifactHistory save, provider/native call, exposure change, or effect. It should fail with 409 runtime_conflict if expectedRevision is stale and preserve the local draft. It can be read during a Run but must report that save/admission is blocked.

No new save route is needed. Save the existing profile body through PUT /runtime-control operation:'put' with the current whole-config revision; use operation:'profile' only if the Session's selected profile must change. Preserve scope/id and source hashes. Then read GET runtime-control to obtain the authoritative composition id/hash/revision and send those in Run's existing runtimeSelection. Save is currently blocked with 409 active_run while any Host Run is active because RuntimeControl is globally frozen; do not promise editing through an active Run. After it settles, save applies to future Runs and cannot mutate its historical runtime.bound/Kit binding. For this first order, edit the profile already selected for the target ordinary Session so the flow uses one profile-resource CAS and avoids widening selection semantics.

## Owners and exclusions

- Runtime Control / RuntimeControlPlane.change: profile source, resource IDs/rules/Kits, exposure and whole-config CAS.
- Host Session/Run / Store: Session profile selection, Run receipt/replay and immutable runtime.bound/Kit binding; R1's executor choice remains its own authority.
- K1 / Harness Extension: Kit descriptor validation, reference-only compile, compatibility/budget and retained exact plan/context.
- Runtime Adapter: reports capability; Kits are currently Pi-only. No Kit declaration grants support or permission.
- Provider/Model and permission controls keep their current owners.
- Role responsibility/name is not part of the current profile-v2 backend schema; keep role/profile IDs or labels from an actual owner. Do not persist the synthetic roleId, runtimeId, kitIds, activeRun, or invented per-profile revision as backend facts in this slice.

## One finite order and decisive cases

Claude owns the existing AgentProfiles consumer for this one ordinary Session-scoped editor journey; Codex owns only the small Host draft preflight method/route and its direct tests. Record UX/visual grammar and nearest precedent in the existing 06e/Runtime Control task record. Reuse the existing UI controller's per-profile draft, stale-reply guards, CAS conflict behavior, and runtime-intake save/source-inspection patterns. Do not start general role management, arbitrary Kit acquisition, marketplace/catalog, non-Pi Kit support or extension lifecycle.

Decisive acceptance:

1. Inspect the selected profile and pinned source refs; preview an unchanged/no-Kit profile as exact legacy passthrough, then a valid v2 Kit profile with exact refs and the expected compiled candidate/budget.
2. Preview missing, changed-digest, wrong-kind/scope/not-exposed, missing-required-resource, budget overflow, conflicting pin, matching unsupported evidence and unchecked evidence; each returns its actual diagnostic. Unchecked stays visibly unchecked; unsupported blocks; no preview path changes exposure or permission.
3. Preview under managed/unknown runtime reports Kit unsupported/unavailable with zero provider/native request. Preview ask and deny permission readings remain separate from runtime support.
4. A stale whole-config revision returns conflict and keeps the draft; an invalid profile save is rejected by existing validation. Save uses the existing CAS once; a concurrent active Run gets active_run and makes no config mutation.
5. After a terminal old Run, save updated profile source and admit a new Run using fresh runtimeSelection. The old Run's runtime.bound, kitBinding and readback remain byte/semantic-identical; the new Run reports the new profile source hash, Kit pins and exact retained context through runtime-context?runId.
6. Replay the old commandId after profile change and get its original Run/binding before current selection checks; a stale new Send refuses without a Run/provider/native request and the editor retains the draft.
