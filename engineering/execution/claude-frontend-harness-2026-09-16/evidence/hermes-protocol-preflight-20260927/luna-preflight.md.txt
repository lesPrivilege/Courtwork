## Recommendation to freeze

**Use Hermes’ authenticated API-server run surface, POST /v1/runs plus GET /v1/runs/{run_id} and /events SSE, for the first provider-free synthetic adapter fixture.** Treat it as the Hermes API-server transport behind a new versioned Runtime Port adapter. Do not start the native Hermes server in this slice; use a deterministic HTTP/SSE loopback fixture that preserves the documented route, identity, status and fault shapes.

This is the smallest transport with a native Run identity and direct mapping to the existing managed Port: create returns run_id immediately; status and SSE carry the same run_id; stop is explicit; approvals and steer are separate endpoints; and the source persists idempotency/status with owner PID/start metadata. The API-server source marks a non-terminal run as interrupted when its owner process is gone (gateway/platforms/api_server_runs.py:267-300). That gives the Host a reconciliation fact while preserving CW’s own Run/effect ledger.

## Why this transport wins the first slice

The official Hermes Programmatic Integration (https://hermes-agent.nousresearch.com/docs/developer-guide/programmatic-integration) lists three external protocols: ACP (JSON-RPC/stdin), TUI Gateway (JSON-RPC/stdin/WebSocket) and API server (HTTP/SSE). It says all drive the same AIAgent core but expose different feature sets. The API server section documents /v1/runs, status, event SSE, approval, steer, stop and capabilities. The pinned source implements the route table and run state in gateway/platforms/api_server_runs.py:115-183,267-300,497-625,840-888,903-1009.

That shape aligns with CW’s existing managed-Port obligations without reopening the accepted Pi extraction:

- app/runtime/agents-host-gateway.mjs:7-47 already defines Host-owned admission, native binding, effect ledger, unknown outcomes and a separate managed Port capability table. Hermes should reuse those invariants and the Port vocabulary, while keeping its own adapter/transport module and identity.
- app/server/runtime.mjs:40-63 admits exactly one reviewed managed executor ID today. A Hermes adapter would be a later architectural dispatch/integration decision; this preflight does not edit that allowlist or claim Hermes is configured.
- The existing synthetic pattern in app/tests/fixtures/agents-host-harness.mjs:23-53 boots the real Host with an injected managed Port and a disposable loopback endpoint. app/tests/fixtures/agents-api-loopback.mjs:1-170 demonstrates the right evidence boundary: real sockets and adapter/Host code, deterministic scripted remote behavior, no provider or credential.
- app/tests/runtime-selection-http.test.mjs:59-105,137-198 is the nearest Host-level precedent for separate Pi/managed sessions, frozen native identity, restart refusal, lost-create unknown and no Pi fallback. app/tests/runtime-selection-construction.test.mjs:11-53 covers descriptor admission and exactly-once disposal.

The API server is preferable here to an editor protocol or a custom gateway stream because its first-class object is already a run and its source has an explicit durable idempotency/status path. This is a construction recommendation, not a claim that Hermes’ API server is currently connected to CW.

## Exact synthetic contract

This is the proposed worker contract for Astra/Claude to freeze before implementation. It is intentionally narrower than the full Hermes API server.

### Transport identity

    adapterId: hermes-api-runs
    adapterRevision: hermes-agent@d7b836ab1c0cddaafc109ed24c9a83b6191cdc88/api-runs-v1
    protocol: hermes-api-server-runs
    endpointIdentity: synthetic-loopback URL or explicit configured endpoint reference

The adapter records separately:

    cwSessionId / cwRunId
    nativeRunId       # API server run_id
    nativeSessionId   # API server/Hermes session_id when returned or retained
    idempotencyKey    # Host intent identity supplied to POST /v1/runs

The Host remains the owner of CW Session/Run, command identity, admission, permissions, effects, receipts and final status. Hermes run_id, session_id, X-Hermes-Session-Key and provider/model strings are native observations/configuration facts. Do not copy Hermes’ state database, reuse RuntimeStore IDs as native IDs, or infer formal Attention/Matter state from a Hermes run.

### Wire subset

1. POST /v1/runs requires a nonempty input string. The fixture accepts only the bounded text subset; it rejects arbitrary tool/environment fields. The request carries Host-owned Idempotency-Key and may carry explicit synthetic session_id only where the test needs continuation.
2. A successful admission returns 202 {run_id,status}. The first accepted response is a receipt of admission, not completion. A repeated idempotency key with identical body returns the same run; changed body conflicts. The Host still retains its own intent receipt and never retries an unresolved create with a replacement key.
3. GET /v1/runs/{run_id} returns status and bounded terminal/error fields. GET /v1/runs/{run_id}/events is a live SSE stream. Normalize only run.started, message.delta, message.complete, approval.request as an unsupported notice, run.stopping, run.completed, run.failed, run.cancelled, run.interrupted, and transport/error frames. Unknown event names become diagnostics; missing run IDs are malformed, not empty success.
4. POST /v1/runs/{run_id}/stop returns a stop intent (stopping). The adapter waits for terminal cancelled; a dropped stream or owner restart remains unresolved/unknown until the Host’s reconciliation rule has evidence. It never treats HTTP 200/202 alone as cancellation.
5. GET after restart may return a durable status. If Hermes reports owner-loss interrupted without a terminal effect receipt, map it to CW unknown or an explicitly named native-interrupted observation; do not silently retry. Event text not observed before stream loss stays a coverage gap.
6. POST /approval, POST /steer, native tool execution, browser control, cron, gateway delivery and session deletion are out of slice 1. The adapter must reject them before sending a request or report them unsupported in describe.

### Synthetic pass/fail cases

The first fixture should reuse the existing managed-Port test shape, without calling Hermes or a provider:

| Case | Required evidence |
|---|---|
| Admission/binding | Correct adapter ID/revision and endpoint identity; unsupported capability is rejected before the Host creates a Run. Wrong revision/configuration refuses new execution without Pi fallback. |
| Create identity | One POST /v1/runs carries exactly the caller’s Idempotency-Key and bounded body. Lost response + same request identity re-reads/reconciles; no replacement run is created. Changed body under the same key conflicts. |
| Event ledger | Fragmented SSE frames, duplicate event IDs/sequence, unknown event types and missing run ID are handled without duplicate assistant projection or false terminal success. A normal run.completed settles only the matching native run. |
| Continuation | A retained nativeSessionId is used for an explicitly requested second run; a different session/endpoint or missing native identity refuses before dispatch. Do not infer identity from title or current active session. |
| Cancel | Stop request is sent once; stopping → run.cancelled settles cancelled. Stop response without terminal, stream drop, and a fixture that ignores stop all settle unknown, with no automatic second stop or new run. |
| Owner restart | Persist a synthetic nonterminal run record, reopen the fixture/adapter and fetch status. Native interrupted is surfaced; no text/effect is invented, and new work is refused while a prior CW effect remains unreconciled. |
| Tool/approval ceiling | Any synthetic approval.request or tool-shaped event is retained as unsupported/diagnostic and never executed. No reply/tool-result call exists in the first Port descriptor. |
| Disposal | Closing the SSE subscription/transport sends no implicit stop/delete and leaves the native binding as historical evidence. Active cancellation is separate. |

Nearest implementation/test precedents are the accepted Agents transport protocol tests: app/tests/drt03-agents-api-protocol.test.mjs:46-409 (identity, event dedupe, root terminal, cancel/unknown, function boundary and recovery) and app/tests/drt03-agents-transport.test.mjs:36-402 (wire identity, fragmented SSE, disposal, malformed pages, exactly-once mutation and strict tool declarations). ## Correction after pinned wire re-read — 2026-09-27

The earlier sections used an illustrative event list and must be narrowed before a worker consumes this report. At Hermes source d7b836ab1c0cddaafc109ed24c9a83b6191cdc88, `api_server_runs.py:_run_event` returns exactly:

    { event, run_id, timestamp, ...optional_fields }

The source does not add `event_id`, `seq`, item IDs or a replay cursor to this envelope. `_execute_run` emits `message.delta` with `delta` only, then emits a terminal `run.<status>` event from `_finish`. There is **no confirmed `message.complete` emission** in this pinned API-run path. Final text is carried on terminal status/event as `output=result.get('final_response','')`; terminal fields also include `completed`, `partial`, `interrupted`, and optional `error`, `usage`, `turn_exit_reason` or `pending_steer`.

The exact source-level event names are:

- `approval.request` from the approval callback, with redacted approval fields and choices;
- `message.delta` from the text callback;
- `run.completed`, `run.failed`, `run.cancelled`, or `run.interrupted` from terminal/shutdown paths;
- `approval.responded` and `run.steered` from their control endpoints;
- `tool.started`, `tool.completed`, `reasoning.available`, `subagent.start` and `subagent.complete` from the generic tool-progress callback, which remain outside slice 1.

There is no `run.started` SSE event in the pinned `_execute_run`; `queued`/`running` are pollable status values. Owner-loss recovery is exact: `_durable_run_status` changes a persisted non-terminal record to `status:'interrupted'`, `error:'The gateway restarted before this run settled.'`, `last_event:'run.interrupted'`, and updates the durable store (`api_server_runs.py:277-300`). This is status evidence, not event replay.

Therefore the standalone provider-free fixture must parse only the exact envelope and names above. It must not invent `message.complete`, `run.started`, event IDs, sequence numbers, message IDs or replay cursors, and it must not claim protocol-level deduplication. A fixture may deliberately repeat an identical raw SSE frame to test parser behavior, but any duplicate handling must be labeled adapter/fixture behavior rather than a Hermes wire guarantee. The first fixture’s terminal text assertion belongs on `run.completed.output`; a missing terminal frame or missing output remains a transport/coverage gap. No Host executor allowlist, RuntimeStore schema, production exposure or Agents identity reuse is implied by this correction.
