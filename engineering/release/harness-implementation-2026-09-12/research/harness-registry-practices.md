# Pi tools, cache behavior, and fixed Expert composition

**As of 2026-09-12.** Bounded primary-source scan for the pinned Pi 0.85.1 harness and the current Courtwork Host/UI composition. This is an implementation-practice note, not a runtime acceptance.

## Findings

Pi can register tools. Its pinned [v0.85.1 extension guide](https://github.com/earendil-works/pi/blob/v0.85.1/packages/coding-agent/docs/extensions.md) documents ExtensionAPI.registerTool, active-tool selection, and dynamic registration during a session. The same guide warns that extensions run with full system permissions; project extensions are loaded only after project trust. Pi also supports extension state entries and a JSONL session tree, as described in its [session documentation](https://pi.dev/docs/latest/sessions). These are capable extension mechanisms, but they do not automatically supply Courtwork’s authorization, resource provenance, or GUI projection.

The pinned Courtwork composition intentionally does not load arbitrary Pi extensions. app/runtime/pi-session-runtime.mjs supplies an empty ResourceLoader, disables Pi built-in tools, and passes Host-composed customTools into each AgentSession. The current Host’s ExtensionRegistry is a trusted domain catalog with version/generation and load/unload/invalidate lifecycle; service validates extension-declared tool names before including them in a Run. The Runtime Control snapshot is already a GUI projection of Host-owned resources, exposure, policy, provenance, and capability status. It is not a view over Pi’s getAllTools(), and it should remain the authority for what the product says is installed, available, exposed, or allowed.

So, Pi tools can be made manageable in Courtwork, but the correct integration is a narrow bridge: fixed Host manifest and version → validated tool definitions for that Expert’s Pi session → current control-plane snapshot → GUI display. Do not treat Pi’s dynamic registration or a tool’s presence in the SDK as permission. Keep execution and approval in the Host tool implementation. A future Runtime wrapper can reuse the existing service/control projection if it reports an explicit capability snapshot and preserves current owners; the second-runtime gate is still separate and unproven. The current contract already requires distinguishing supported, unsupported, and unverified capabilities, and says profile/permission state must remain Host-owned: inputs/courtwork-runtime-composition-v2-2026-09-12/02-RUNTIME-CONTRACT.md.

DeepSeek’s [official Context Caching guide](https://api-docs.deepseek.com/guides/kv_cache/) says caching is enabled automatically, best-effort, and reported in usage as prompt_cache_hit_tokens and prompt_cache_miss_tokens. A request can hit only a fully matching persisted prefix unit. Prefixes are written at request boundaries, when common prefixes are detected, and at fixed token intervals; cache construction takes seconds and unused entries usually expire within hours to days. Cache reuse is input-compute reuse, not response memoization: output remains stochastic. Therefore string similarity, a stable session ID, or one successful request does not prove a hit or a stable model result.

Courtwork’s runtime contract keeps the system prompt and sorted tool schemas stable and appends conversation history; it adds no per-turn timestamp or nonce. Model, protocol, tool permission/schema changes, or compaction can begin a different cache prefix. Pi 0.85.1 maps DeepSeek’s prompt_cache_hit_tokens to usage.cacheRead. Under the Host’s short-retention setting the SDK does not emit prompt_cache_key for DeepSeek; this is compatible with DeepSeek’s automatic cache, but means cache success must be read from provider usage, not inferred from a key or local prefix estimate. The cache usage fields are observations, not a promised hit rate. See app/runtime/pi-session-runtime.mjs, app/runtime/request-telemetry.mjs, app/node_modules/@earendil-works/pi-ai/dist/api/openai-completions.js, and app/docs/runtime-foundation.md.

## Recommendation for bounded dogfooding

Keep this as one fixed, versioned Courtwork Expert composition on Pi 0.85.1 plus the current Host contracts. Do not build a general plugin marketplace or hot-swap platform. Register only its Host-owned tools, show their source/version/scope and actual permission state in Runtime Control, and test the exact GUI-to-Run binding. Start with read/search tools; add writes only through the existing exact-path approval flow, and keep shell, browser, background schedulers, and arbitrary plugin loading out of the initial profile.

Load AGENTS.md and system instructions from explicitly named, trusted project paths. Record which source and version supplied each instruction, the resolved priority/order, and the composition hash; do not silently discover personal/global HOME instructions. The current empty Pi ResourceLoader is an explicit boundary, so this would be a scoped product change rather than a hidden inherited behavior.

Suspending an Expert should stop new admission and follow the existing Run settlement/cancellation rules. It must preserve session history and effect receipts. Suspension is not history deletion, rollback, or proof that an external action was undone; unresolved effects need their existing reconciliation path. Removed or unsupported capabilities should remain explainable in the UI, while the underlying work record stays intact.
