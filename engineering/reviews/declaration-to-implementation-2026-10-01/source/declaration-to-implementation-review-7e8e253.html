总评

核心语义和责任边界已有真实实现，但“可接续的工作场”尚不能按完整架构闭环接受。

单一 Work Core、正式决定的事务提交、版本化来源、Host 执行记录和工具批准的分离都有可追踪代码支撑。最明显的欠缺发生在边界交接：人留下的补证据要求没有接给新 Agent；同一批准动作在不同界面提供的决策依据不一致；Host 的停止、关闭和异步动作没有完全共享同一套收敛规则。

这意味着当前实现并非只有一组架构名词，也不能因 build 全绿就判为架构完成。建议优先补齐已有 owner 的端到端职责，再扩大 Runtime、Kit 或后台能力。当前支持矩阵对多数未完成方向的收窄是诚实的，不宜把未来愿景全部当作现有缺陷。

范围与判定标准

本报告只审查该提交中已跟踪的文档、实现与测试源码。没有修改仓库，没有读取用户电脑、未跟踪文件、真实凭证或私人工作数据，没有运行构建、测试、探针、真实模型或仓库程序。用户已告知本地 build 全绿；本次不重跑，也不把它作为架构接受证据。

每项按“声明 → 用户目标 → 必要不变量 → 实现路径 → 反例或缺口 → 证据边界”展开。已实现的主张、明确尚未实现的产品方向和历史验收记录分别处理。文件存在、函数命名或测试通过均不自动证明语义成立。

  • 静态确认 confirmed-static：固定源码足以证明的结构、字段流或允许的状态路径；不等于已动态复现
  • 设计判断：实现与用户目标之间的取舍或未完成闭环，需要 owner 裁决
  • 证据不足：现有静态材料不足以支持肯定或否定
  • P1：优先补齐核心工作接续或生命周期不变量
  • P2：会造成明确操作语义、决策信息或状态一致性缺口
  • P3：文档发现性与维护问题，不单独推导为产品失败

严重性表示施工优先级，不表示发生概率。本报告中的静态交错分析没有运行复现；实际运行时、操作系统和浏览器行为仍需适当授权后的独立证据。

优先发现

F1 P1 补证据要求保留了 但没有接给新 Agent

判定：遗漏路径 confirmed-static；优先级属于架构目标判断。

宣言要求 Matter 保留决定和未完事项，让新参与者从当前记录继续。正常场景是：人对候选选择 request_evidence，换一个 Chat 绑定同一 Matter，只说“继续补证据”。必要不变量不是内联全部历史，而是让未解决请求留下可定位引用，并有只读入口读取理由和候选。

实现把候选转成 needs_evidence，Decision 保留 reason；非 accept 不更新开放义务。新 Context 却只选 pending，普通 Work tools 只有 source、submit、artifact，没有通用 candidate 或 Decision reader。于是新 Agent 获得的正式接口不足以知道上次为何要求补证据。

具体后果：人必须重述或复制，或者新执行者重做一份与上次要求脱节的提案。没有证据表明记录丢失：UI 与 Core 仍可读这些决定和正文。 已接受 Artifact 的接续路径也确实存在。

依据：README 接续声明、候选状态与决定写入、Context 过滤、实际 Work tools

施工建议：由现有 Core query / Context owner 增加未完人类决定的最小索引与 Matter-scoped exact reader，不复制第二本账。验收看新 Session 能否从正式记录找到原决定、原候选、对应来源，而不靠人重复粘贴。

F2 P1 Attention 的检查批准缺少完整 Chat 已展示的关键依据

判定：confirmed-static；未实测 GUI。

check_run 合同要求批准卡显示 recipe、command、arguments，以及请求绑定版本之前模型写入的候选文件。完整 Chat 已消费这些字段和 Host 写入记录；Attention 弹层仍使用通用许可渲染，仅显示 tool/path/bytes/hash/preview，而 check_run 的 preview 只是 recipeId 参数。

global Attention 可以有同一私有 repository candidate，工具暴露规则没有排除 global，因此这不是不可达死代码。用户可以在信息较少的弹层批准同一个真实检查动作。

具体后果：批准界面未让人看到即将执行什么以及哪些候选文件参与；批准语义没有随呈现入口保持一致。 Host 仍实施精确批准、候选版本与执行前检查，本项不主张取得额外 authority 或任意执行权限。

依据：批准信息合同、Attention 许可卡、preview 形成处、完整 Chat 文件说明、完整 Chat 消费处

施工建议：复用同一 owner-backed permission presentation/检查说明组件；在弹层无法完整呈现时引导完整审阅后再批准。验收需要同一 payload 在两处呈现的动作、对象、版本、文件与风险说明一致，而不是只测按钮能点。

F3 P2 程序化关闭没有收拢正在进行的手动 compaction

判定：confirmed-static；实际 journal 冲突未验证。

程序化 close 是文档给出的受支持清理边界；CMP-01 同时要求 Run/operation 共用 writer admission 并处理 close。手动 compaction 是占用同一独占执行席位、可写 native journal 的 Host operation。其 task 放在 operations Map，configurationQueue 只等到 operation 创建后返回。RuntimeService.close 只等待 admission/configuration/material queues 并取消 Runs，没有 abort/drain operations；Pi Port 没有补充 close 实现，而外层 runtime.close 最后释放 Store 锁。

具体后果：对受支持的程序化 createRuntime.close 调用，关闭 Promise 返回并释放锁时，手动 compaction 仍可能未收敛。 因而“旧写者已停，可以重新打开”的单 writer 前提缺少保障。CLI 最后的进程退出可能直接终止余下工作，重启将 in-flight operation 标 unknown 本身也是合同允许行为；本项不把这两者写成数据损坏。

依据：受支持程序化 close、CMP-01 生命周期合同、operation 异步 task、关闭处理、Pi compact 生命周期、外层关闭顺序

施工建议：Host close 统一封闭 operation 准入，取消并等待每个 active operation 的 task 后再释放数据 owner；不由 UI 代管。验收目标是关闭返回后不再存在原 Host 的 journal writer，不能仅断言 running 字段改成了某个终态。

F4 P2 取消与完成的仲裁决定早于 Store 提交点

判定：静态可行交错；未动态复现。

现行 HTTP 合同明确选择：cancel 先于 Host terminal write 被接受，Host 终态应为 cancelled，已完成的 native answer 仍保留。普通 Run 收尾先等 recordUsage。取消可以在这期间把 stopping 写入 Store 队列；但 cancelRequested 要等 stopping 持久化后才设置。执行协程可能在 stopping 尚在持久化时读到旧状态和 false flag，先算出 completed 再排队。Store 的 updateRunIfActive 只防止覆盖 terminal，stopping 仍非 terminal，因此这份预先决定的 completed 可以排在 stopping 后落地。

具体后果：已进入 stopping 的 Run 可能最终显示 completed，未遵守现行 HTTP 合同明确选择的取消优先于尚未提交终态的规则；原本可用 cancelled 进行 supersedes 接续的请求还可能遭到 supersede_completed 拒绝。 这不是 terminal→terminal 反复改写；现有终态不可变保护仍有效。请求发出与实际进程停止也仍是不同事实。

依据：当前取消仲裁合同、接续状态合同、收尾等待与终态计算、取消写入与晚置 flag、Store 发布点、Store 终态保护

施工建议：把取消意图与最终 outcome 的裁决移入同一权威提交边界，或给完成写入必要的预期状态；保留 native outcome 作为独立证据。不要只扩大 terminal 集合把 stopping 伪装成已经停止。

F5 P2 未确认进程组退出的事实没有进入持久检查结果

判定：confirmed-static；实际 OS 触发未验证。

runner 已显式返回 groupLingered，表示有界等待后无法确认整个进程组退出。check-tools 只按 cancelled/timedOut 生成结果，Store settlement 也没有承载这一事实的字段。结果已经有 settled 记录，重启的“未匹配 started”恢复也不会把它补回来。

具体后果：持久记录无法区分确认停止与未确认停止。 不能据此声称仍有活动进程、仍在写文件或发生安全穿透；残留 OS 状态也可能造成查询无法确认。

依据：停止结果合同、runner 不确定字段、tool 转换遗漏、Store settlement 字段

施工建议：明确“停止请求结果”与“终止确认事实”两个维度，贯通 runner→tool→Store→投影；由 Host 决定 unknown、诊断和后续准入的语义。

F6 P2 正式人类动作的 idle 检查与 Run 准入未共享临界区

判定：confirmed-static 的交错窗口；未动态复现。

具体 Work Core 合同要求 mutations 仅在 no active Run 时发生。createRun 进入 configurationQueue；humanAction 只先检查 busy，之后跨多次 await 访问 Core 和 Registry，没有与 Run admission 同一串行边界。两个正常已认证请求可在检查后交错。

具体后果：运行中工作基础可能被另一页的 decide 或 replace_sources 推进，导致后续 source read、候选基础变旧，浪费执行并需重开。 Core 的版本、来源、pending 和事务检查仍有效，本项不声称旧候选被错误接受或事务损坏。

依据：明确 no active Run 合同、humanAction 检查与 await、Run 串行准入、Core 保留的保护

施工建议：让正式 mutation 在既有 Host 准入 owner 内确定先后顺序，再检查 binding、generation 和 idle；只读查询保持独立，Core CAS 继续保留。

F7 P2 直接切换 Chat 失败后 可见位置与历史失配

判定：行为路径 confirmed-static；未运行 GUI。

从 Home 成功进入 A 后，再从 Recent 直接点击 B。selectSession 在 GET B 成功前已保存 A 的 Chat 草稿、停 polling、卸载 A 的当前视图并清空 session/events/runs，将 activeSessionId 改成 B；只有成功才把 B 放入历史。失败分支仅显示错误，没有恢复旧位置，也没有按现行 navigation owner 的规则标记 unavailable 并落 Home。

具体后果：可见状态停在不可加载的 B，history current 却仍为 A，Back 直接越过 A 到 Home。 A 与草稿没有被删除，用户仍可从 Recent 重开。现行 owner 允许不可用目标回 Home，因此本项不要求只有 rollback A 一种设计；需要统一直接导航与历史 traversal 的失败语义。

依据：当前访问恢复目标、当前 navigation owner 裁定、切换前卸载、成功与失败分支、Back 与现有 unavailable 处理

施工建议：保留旧视图直到新目标读取成功，或统一走已有 unavailable/Home 裁定；可见对象与历史状态应一次性切换。旧 navigation 草案的“失败留原位”文字不作为唯一现行验收标准。

F8 P3 发布状态入口仍指向旧回执

判定：confirmed-static；不是部署失败，也没有查询线上状态。

site README 把“发布状态”直接链接到 2026-09-13 final-preparation，落点的 closeout 给出旧部署 fd4012c；当前 release 索引却已明确以 2026-09-15 的 fe7f317 回执取代该 current wording。

具体后果：沿 site 入口工作的发布维护者容易引用旧 baseline；正确记录仍能从 release/current 找回，因此只定 P3。 历史回执本身不应改写，也不能由此推断线上仍运行旧版。

依据：site 当前入口、旧 closeout、当前路由与取代关系、取代说明、新部署回执

施工建议：只更新当前路由指向的 owner；保留旧历史身份。

单独保留的设计边界

  1. 逻辑授权不等于进程隔离。 check_run 的固定 recipe、最小环境和精确批准确实存在，但执行身份仍是 Host 用户。当前具体合同已经承认“不构成 sandbox”的限制，因此这不是新发现漏洞；它仍是扩大到真实长期个人工作站场景前的架构接受门槛。见检查环境边界
  2. Workspace 聚合读取的授权单位需要裁决。 repository 聚合读取有逐文件严格效果组合，workspace list/grep 当前更多依据调用级资源判断。现有 workspace 合同没有明确承诺完全相同的材料级语义，故不记作已成立的权限 bug；应先明确“限制一个文件”是否约束所有聚合能力，再决定复用准入机制或补说明。详细证据见权限附录
  3. Runtime 可替换性仍是局部 seam。 架构主动承认 service 依赖 Pi-shaped helper/options/outcomes 等耦合。第二 Runtime、跨 Runtime Kits、通用后台 orchestration 仍须各自完整消费者和证据，不以目录或 adapter 数量接受

结论摘要

发现 2 个有具体用户后果的 confirmed-static 生命周期缺口：

  1. R1 / P2（受支持嵌入式 close/reopen 场景）：手动 compaction 没有加入 awaited Host close 的取消/排空集合，数据锁可在原生 journal writer 尚存时释放

  • 有历史的 chat 发起手动 compaction，已返回 running receipt，外部 provider summary 仍在等待
  • 受支持的嵌入式调用者 await runtime.close；无普通 active Run，close 不取消也不等待该 summary，最终释放 lock

实现路径与反例交错

  • natural completion 在 finally 先 await recordUsage，然后读取当前 Run、根据 entry.cancelRequested 在队列外计算 finalStatus，再传入固定 patch：app/server/service.mjs:3335-3343、app/server/service.mjs:3366-3381
  • cancelRun 先 await Store 的 stopping/admissionOpen=false 写，该持久化完成后才把 entry.cancelRequested = true：app/server/service.mjs:3551-3575
  • Store._mutate 使用 clone，await _persist 后才发布 this.state；排队期间的 reader 仍看到旧 snapshot：app/server/store.mjs:979-991
  • updateRunIfActive 只判断当前 status 是否在 terminal 集合；stopping 不在其中，因此会应用先前计算的 completed patch：app/server/store.mjs:34-44、app/server/store.mjs:1727-1736

不需要改源码或假造 SDK outcome，以下交错已经被上述 await/队列允许：

  1. native 正常完成；natural finally 正在等待 usage 写 U
  2. 此时用户 Stop 到达，把 stopping 写 C 排在 U 后
  3. U 完成；C 开始其异步磁盘持久化，但尚未发布 this.state。cancelRun 尚在 await C，cancelRequested 还是 false
  4. natural finally 从 await U 恢复，看见旧 running/false，计算 finalStatus=completed，把完成写 F 排在 C 后
  5. C 持久化成功，取消意图与 stopping 已被接受；cancelRun 才设 cancelRequested=true
  6. F 进入 Store 时当前状态是 stopping；它不是 terminal，故已冻结的 completed patch 被执行
  7. 结果可为 running → stopping → completed，cancelRun 最后返回 completed，且 terminal immutability 现在禁止补回 cancelled

原生结果可以早于 Stop 完成，这不是错误；这里报的是 Host 自己选定的仲裁规则与其序列化实现不一致。不是要求撤销已经产生的结果，也不是声称取消必须回滚外部效果。

4. 有实质支持的实现，不因两个缺口否定全部架构

S1. Run receipt、native writer 和单 active lane 的顺序

宣言：重复请求返原 receipt/原绑定，新 Run 才绑定新配置；同 command 的并发不能开两个 native writer：app/README.md:242-248、docs/runtime-control/INDEX.md:45-49。

实现链：service 先查原 receipt，再做当前配置/能力判定；Store 内重新 commandReceipt、lineage、singleActiveRun；只有 created.idempotent=false 才安装 active entry 并执行 native open。app/server/service.mjs:2760-2772、app/server/store.mjs:720-732、app/server/store.mjs:1603-1646、app/server/service.mjs:2912-2939、app/server/service.mjs:3072-3081。

静态支持结论：普通 Run 重发没有第二次 prompt/工具效果的代码路径；native journal writer 在唯一 admission 之后创建。Store 全局 active gate 也意味着 README 的跨 runtime 并行构想尚不是当前支持，不能反过来把全局串行视为实现 bug。

S2. 重启是保留 unknown/旧 receipt，不自动重放原 prompt

宣言：重启中断 Run 为 unknown，pending questions 全部 expired_restart；相同 commandId 读回 unknown；下次新 Run 重新打开原 JSONL：app/README.md:265-279。

实现：initialize 对 active Runs 关闭 admission并写 unknown，随后 expireQuestionsForRestart；Pi port 以 nativeRef.path reopen；原 receipt lookup 在 provider/extension 当前可用性检查之前。app/server/service.mjs:356-382、app/runtime/pi-runtime-port.mjs:59-65、app/server/service.mjs:2760-2772。

静态支持结论：恢复并不伪造旧 Run completed，也不会因换模型/凭证而自动重发旧 command；与 recover:false 的 in-process Pi capability 一致。这里只证明代码路径，不证明磁盘崩溃原子性或真实 provider 完整终止。

S3. 晚权限答案与已取消 Run 不重新开闸

宣言：晚 reply 返回409，没有静默批准；取消后待审批的工具也拒绝继续：app/README.md:261-264、docs/runtime-control/architecture.md:13-17。

实现：service 比较 question.runId、terminal/admission、pending与live waiter；Store resolveQuestion 在同一 queued mutation 再检查 admission/status；governTools 在 await permission 之后重验 signal/isOpen。app/server/service.mjs:3509-3547、app/server/store.mjs:1806-1826、app/runtime/control-tools.mjs:121-141。

静态支持结论：跨 Run 的 question ID 或取消期间晚 allow 没有复活工具的直接路径；approval不是一次永久授予。审批前后双重 gate 与 Store 内复核均是实质措施。

S4. Host primary event 投影与 Pi per-Run disposal

宣言：Host observation 不等同 native emitter同步完成；primary persistence失败不得成为 completed，per-Run AgentSession在idle后dispose：app/docs/runtime-foundation.md:75-83。

实现：createSessionRun 持有 pending promises，失败置 projectionError并abort，drain 在工具前/终态前检查，finally unsubscribe/dispose/drain；sticky stopped 位阻止后续 provider 请求：app/runtime/pi-session-runtime.mjs:518-574、app/runtime/pi-session-runtime.mjs:653-698。

静态支持结论：不是只依赖 SDK emitter 的一次回调“看起来完成”；Host确实等待普通Run主要投影。informational notice依旧best effort，跨Store/JSONL没有事务，合同已披露。该保障未覆盖 R1 的独立 manual operation。

S5. Async read tasks 的独立身份、晚回结果与不自动消费

宣言：intent在dispatch前、丢ACK后unknown且不重发、晚结果不能覆写timeout；task成功不等于model已消费，更不等于Core接受：app/docs/async-tasks.md:40-58、app/docs/async-tasks.md:68-88。

静态支持结论：late adapter promise不直接调用Store callback，race输掉后不会凭原launch自动盖掉结果；后续explicit query另有身份验证。其“合作式remote cancel、可信in-process adapter、无OS sandbox”限制不能被本结论抹去。默认没有注册adapters。

S6. Local Pi process：process close、native completion、提供来源、读过来源、正式接受分开

宣言：仅显式localPiWorker+owned deterministic route，无live credentials/通用runtime选择；process/native completion并非正式接受；中断dispatch不能凭PID/exit清掉unknown：app/docs/spark-agent.md:76-84。

  • 获准packet先进入ArtifactHistory并保留dispatch receipt，再spawn；publication前再次校验scope/source版本：app/runtime/local-pi-host.mjs:24-79
  • transcript要求native session、message/turn/terminal一致；完成还要求完整结果、exit0且无signal/fault：app/runtime/local-pi-process.mjs:52-101、app/runtime/local-pi-process.mjs:148-172
  • Store校验Run/assignment/attempt唯一归属、typed事件次序、无runtime source-read伪造、Host terminal不可改写：app/runtime/local-pi-state.mjs:122-143
  • unknown记录持续使localPiRunUnresolved为true；新local admission和reconcile/retry守卫保留fence：app/runtime/local-pi-state.mjs:20-25、app/server/store.mjs:1629-1633、app/harness/subagents.mjs:249-265

F-PERM-01 · 检查进程“未确认组退出”的证据丢失

级别：P2 / 中，终止与效果记录语义
结论：confirmed-static；实际 OS 触发条件未验证

宣称 → 用户目标 → 必要不变量

  • Host 拥有执行效果与恢复仲裁：engineering/architecture.md:23–28
  • 取消请求不等于已确认终止；未确定结果不能被描述为成功或取消：engineering/architecture.md:30–32
  • 检查合同明确写出：停止后要确认整个进程组退出；无法确认时 runner 返回 groupLingered:true：app/docs/check-recipes.md:194–204
  • check.settled 应保留独立于普通 tool 结果的终止事实，重启时保留 unknown、不重放：app/docs/check-recipes.md:206–233

用户目标是停止或超时后能从持久记录知道“已确认停止”还是“终止仍未获确认”，以便决定后续检查/人工处理。最低不变量是：下层已经观察到的终止不确定性，不能在上层转换中静默消失。

实现路径与静态反例

  1. runner 在停止路径中调用 reapGroup；它有有界确认过程，并返回确认成功与否：app/runtime/check-runner.mjs:14–29
  2. child.close 后，runner 将未确认结果显式编码成 groupLingered:true：app/runtime/check-runner.mjs:134–155
  3. check-tools 只按 cancelled / timedOut 选 cancelled / timed_out / completed，把选定字段交给 recordSettled，也只把那些字段返回为工具摘要；groupLingered 没有进入两者：app/runtime/check-tools.mjs:113–130
  4. Host 直接将回调送进 Store，没有另一条不确定性处理路径：app/server/service.mjs:3184–3198
  5. Store 的 settlement 参数和事件字段也没有承载该事实：app/server/store.mjs:1467–1486
  6. 重启恢复只处理“有 started、没有 settled”的调用。上述调用已经得到确定标签的 settled，重启不会恢复被丢失的事实：app/server/store.mjs:924–940

因此，只要 runner 走到其明确支持的 groupGone === false 分支，上层持久结果就与“组退出已确认”的同类结果无法区分。这是代码可证的数据损失，无须将其描述成一个已运行的反例。

具体后果与触发场景

  • 触发场景：取消或超时后，runner 的有界查询不能确认进程组已不存在
  • 确认后果：丢失“未确认进程组退出”这一证据，持久结果不能区分确定停止与未确认停止
  • 不声称 该状态必然代表仍有活动进程，更不声称仍在执行写入或发生安全穿透；OS 残留状态也可能影响查询，实际环境尚未验证
  • failure:null、稳定取消 exit tuple 与 unknown-stop evidence 是不同维度；统一取消结果本身不能成为丢弃不确定证据的理由

支持实现成立的证据

  • 正常停止路径确实有进程组级终止和有界确认，不能写成“完全没有清理”：app/runtime/check-runner.mjs:108–120、app/runtime/check-runner.mjs:134–145
  • check admission / candidate revision 在 Store 与 spawn 前再次检查，不能写成“批准后不复验”：app/runtime/check-tools.mjs:60–100、app/server/store.mjs:1436–1464
  • 未匹配 started 的重启恢复确实记录 unknown，并不重跑：app/server/store.mjs:924–940
  • 静态测试入口中有普通 timeout/cancel 清理断言与持久取消结果断言：app/tests/check-recipes.test.mjs:136–172、app/tests/check-recipes.test.mjs:544–589。本次未执行；这些所读用例没有证明上述不确定字段能端到端保留

最小施工方向

由 Host / check owner 定义“请求结果”和“终止确认事实”的数据合同：runner 的未确认结果必须保留到 Store 与用户可读投影，并由 Host 明确裁决是否需要 unknown / 单独诊断及后续准入限制。不要只改 renderer 文案，也不要只在 runner 内保留一个无人消费的布尔值。

后续验收应先用受控的非攻击性返回值覆盖 runner→tool→Store→重启读回的静态分支，再在单独授权下验证真实 OS 行为；本次未创建或运行这些检查。

2. 缺口一：Attention 的 check_run 审批漏掉专属依据

宣称 → 用户目标

3. 缺口二：直接导航失败让屏幕与历史不再指向同一位置

等级：P2；证据：confirmed-static；未运行/未复现

  • Recent 的按钮直接调用 selectSession(B)：app/web/app.mjs:1959–1963。
  • selectSession 在 GET B 前先保存 A 的 Chat 草稿、停止 polling、dispose A 的 surface；随后 activeSessionId 改 B、session/events/runs 清空、renderAll：app/web/app.mjs:1559–1595。

  • GET B 失败的 catch 只记录 sessionLoadError、toast、session=null、renderAll；没有恢复 A，也没有把失败 B 纳入 history：app/web/app.mjs:1632–1643。
  • Back 直接 history.back，再读取该 entry：app/web/app.mjs:1750–1765。history.back 是 index--：app/web/location-history.mjs:64–68。

静态场景推导： 已成功 Home → A，history current 为 A；点击 Recent 的 B；GET B 返回错误。屏幕已卸载 A、activeSessionId 为 B、session=null，但 history current 仍为 A。此时 Back 指向 Home，无法一步回到刚离开的 A。

具体后果： 读失败变成额外的工作中断和不一致的返回行为。A 的已保存 Chat 草稿不因此删除，用户仍可从 Recent 手动重开 A；严重性因此为 P2，而非持久数据破坏。

处置建议： 失败前保留旧视图，成功后再提交导航，或显式恢复旧 location/surface；让直接导航和历史 traversal 共用同一个失败语义。导航文档第3行仍标“未实现”，而本基线已有实际 Shell history，说明状态文字也需回原 owner 核对，但不影响上述代码路径本身。
