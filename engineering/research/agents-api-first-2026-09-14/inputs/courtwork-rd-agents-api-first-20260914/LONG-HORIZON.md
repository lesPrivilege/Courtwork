# 长期线 · 从效果反推的小闭环与选型

2026-09-14 · 初始外部研究快照与架构建议。每一方向只有第一个消费者可以进入近期排单，不把全表视为已授权实现。

## 1. 选型方法

每项先回答：用户做完后应得到什么；哪类失败会使这个结果不成立；谁持有相关事实和写权；已有何种成熟机制；CW 需要补的最小接缝是什么；哪种 GUI 让人能理解并介入。

比较候选时优先看：语义保真、权限与恢复、能否接现有前端、可观察结果、依赖/运营负担、退出成本。价格和延迟必须针对实际任务再测；流行度、单次 demo 与厂商性能数字不直接决定选型。

本轮资料分三类：长期机制（Git、SQLite、浏览器隔离等）；演进中的协议/工具（ACP、AG-UI、Playwright、运行 SDK）；刚发布的 Agents API 及其官方示例。后者有可消费的公开实现，不因此被称为多年验证的生产成熟方案。

## 2. Chat：原生体验与统一 API 是两条独立接法

### 希望达到的效果

普通讨论无需预建 Matter、无需选择代码仓库；人可选合适的交谈对象，保留值得带入工作的片段，再在获准范围内交给另一执行者。切换 provider 不丢出处，也不承诺完整迁移厂商私有记忆。

### 技术选型

**API Chat**：沿现有 Host 连接、原生 GUI 和消息/附件 owner。assistant-ui 的 renderer、conversation runtime、transport、history 分工可作参照；Vercel 的模型能力发现可作目录设计参考。[S22/S29] 不因此换 React、引入第二套会话库，或把能力未知的兼容端点默认当作全部可用。

**厂商网页原生 Chat**：先研究外部原生页面/独立受限容器，与 CW 的资料侧栏和显式交接动作组成体验。Electron WebContentsView 是实际可用的容器候选，但不是现有 Web Host 必须迁移桌面壳的理由。[S20–S21] 首个实验只回答：登录、导航、焦点、文件交接和来源保留能否在允许的边界内成立。provider 接受某种嵌入、导出或自动化仍要单独核实，不能用关闭安全限制、借用凭据或逆向私有接口绕过。

**原生产品内的 CW 工具面**：MCP Apps / OpenAI Apps SDK 可以让工具结果形成 ChatGPT 内嵌 UI；方向是把 CW 能力接入原生产品，不是将 ChatGPT 自身嵌入 CW，也不让网页订阅自动等同任意 API 权限。[S30]

### 第一个小 loop

从一段由用户显式提供或通过受支持导出取得的对话片段开始：保留来源 conversation/turn 或可验证 locator、capture coverage 和内容版本 → 选中片段 → 指明目标工作与披露范围 → 后续 Agent 精确读取。即使原生容器暂时不可行，显式保留/交接仍可先验证。

GUI 首片是消息动作/来源 Inspector/交接预览，不是另建全局“记忆管理中心”。可搜索不等于已使用，可保留不等于 accepted；临时聊天与持久记忆沿各自原合同。回填现有 Chat Memory Broker、BE-19/20/23、RG/LG；已实现的 projectless Chat 不重复施工。

## 3. Runtime 与 Environment：先做两套执行组合，后做通用协议

Agents API 作为第一新增适配，详见专项方案。App Server 保留为本地 Codex 接入：适合较丰富的原生执行控制与 GUI 事件。[S17] ACP 则是跨客户端/agent 的协议候选，不是必须置于每个后端之前的总线。[S23]

先对两个真实消费者抽最小内部 Port，再评估是否用 ACP 降低第三个接入的成本。需要保留原生能力时，使用带 namespace 的原生观察与有界扩展，不把全部后端降到一个误导性的最小公倍数。不能把旧 ACP v1 的 turn 生命周期与 v2 的状态模型拼成一个未定义协议。

AG-UI 的事件、snapshot/delta 与交互中断有 GUI 参考价值；其 run finished with interrupt 不等于 CW 的工作完成，也不应覆盖原 Host 等待与取消语义。[S24] 无第二前端消费者时，可借结构而不安装协议栈。

第一个效果是“同一 GUI 运行/停止/恢复另一执行器”；第二个才是“同一工作合同可继续”；第三个是环境替换。分别回填原 Runtime replacement / P03/P04/DRT-03，不一次性宣称全面可移植。

## 4. 多 Agent：执行器内部的帮手与 CW 的责任分工分开

### 希望达到的效果

用户委托一件复杂工作，不必亲自调度每个模型窗口；必要时能看见谁做了哪一部分、结果依据是什么、哪个问题需要人。增加 Agent 应改善某个已观察到的瓶颈，而不是扩大噪音与共享写入风险。

### 第一阶段：Runtime 内部 delegation

先消费 Agents API 自有 subagent；Claude/OpenCode 的有界角色、独立上下文与父子导航提供对照。[S07/S25] 外部 CLI、SDK、teams 的版本和权限行为并不完全一致，不跨产品抄默认值。一个完成事件、一段结果回传或一张队伍面板都不足以证明通用工作编排。

第一个 loop 是两项只读核查 → 主 Agent 合并发现 → 用户看证据与未决。并发、输入量和成本以实测记录；失败不隐藏，无法调用 root function 工具的 child 不能伪装成调用成功。

### 第二阶段：CW 管理不同执行器的责任

先一个有界 Assignment 给 Pi，另一个给 Agents API；输入精确版本、输出位置、scope、预算、取消、结果消费分别明确。两者可以是两个独立根 session，不能用 API 内部两个 child 冒充跨 Runtime 能力。

GUI 从任务清单和一张可展开的任务卡开始：任务、负责者、状态、来源、结果、需要人的问题。必要关系才用图，不先建拖拽 DAG。已有 Spark 的持久身份/assignment 保留为实际局部实现，不重建另一份 Spark 状态库；工作级义务由原 Work owner 持有。

只读并行最先，独立输出次之；同一文件或同一正式对象的修改必须经明确汇合。Git worktree 有不同工作目录但共享仓库资料，不是 OS 安全隔离，也不是分布式写权限。[S26]

## 5. 工作区介入与接管：接管理解，不先接管进程

### 希望达到的效果

用户带着现有资料开始工作，无需先迁入一个新知识库。新执行者能知道有效版本、已作决定、未决和现有运行，不需重新读完所有历史。

### 第一个小 loop

用户选一个获准目录或资料集合 → 只读 inventory → 显示盘点覆盖与未知 → 明确关联到工作 → 编译有界 handover → 新执行者据此找对版本、继续一件未完事项。

选目录、执行其脚本、索引其全文、把内容交给云模型是不同授权效果。首片不自动运行仓库 hooks、不扫描全部磁盘；遇到符号链接、外部目录、敏感类别、缺件与撤权，必须在相应读取边界处理。隐藏对象不能通过总数或关系边泄露。

先用现有 Intake、Files、ArtifactHistory、Core reader 和 Git 文件身份。确有重复查询收益，再比较 SQLite FTS5、结构索引或其他检索；FTS 索引可重建且必须与原内容保持一致。[S27] 中文语料应实测 tokenizer 与精确查找覆盖，不能从英文代码搜索表现外推。没有测量理由不先建向量数据库或知识图谱。

GUI 首片是资源表/树加按需 Inspector，以及一页“从这里继续”：目标、当前决定、来源版本、未决、活动/未知执行、建议下一步。自然语言摘要只导航，每个承重结论有原 owner 来源。

取消/丢失旧进程后不能直接宣称独占接管。先查活动任务和 unknown effect，必要时让人处理重叠写权；后续确需 lease/fencing 才引入。回填 workspace-governance、recovery-surface、DWB 与 RG/LG/DS/BG，不另造全局治理数据库。

## 6. Resources / Extensions：从“登记可见”到“真的参与运行”

### 希望达到的效果

Agent 或用户创建的 skill、reference、MCP 或专业扩展，能被检索、配置、限制、在一次真实运行里使用，并留下前后端一致的结果。

第一个 loop 选一种已支持的声明式资源：创建 → 验证 → 保存 → 作用域/权限 → Run 固定绑定 → 实际使用 → UI 展示结果/错误 → 停用后历史仍可理解。不要一口气实现插件市场、任意安装和全部 hooks。

Registry 描述“是什么/由谁提供”，admission 决定“本次能否进入”，Runtime 决定“实际如何执行”，Work 决定“结果有什么效力”。未知能力不能因出现名字而启用；Agent 提议新工具不自动安装代码、赋权或替代人审。

配置复用 Settings/Runtime，调用复用工具卡，产物复用 file/diff/structured reader，技术记录进入 Inspector。新 renderer 只有既有通用视图不能支持判断时才增加，并固定输入、action allowlist、返回和恢复。Remote UI 或 MCP Apps 只作以后特定消费者的候选，不执行任意模型生成脚本。[S30]

## 7. 持续跟进与 Computer Use：分别按等待和通道触发

**持续跟进**：先一条真实义务，例如“候选等待补充材料”。外部变化到来后重验权限/版本、更新观察、只推送需要人决定的差额。平台 webhook 只是唤醒与取得状态的通道，不自己关闭 Work。重复事件、逆序事件、重启与远端已变化是首片反例。[S13]

当前没有新的远端事件消费者时，不为了“长期 Agent”先搭通用 scheduler。少量本地活动的短期连接与不间断后台执行是不同承诺。

**Computer Use**：开发时让 Codex 操作 CW 浏览器，与 CW 产品拥有 computer-use 能力分开。产品先消费结构化浏览器通道；只有目标应用需要屏幕/桌面，才接像素或桌面工具。Cua 已提供 Agents API + exec-server + 桌面 MCP 的应用管理示例，可作环境回收与恢复研究，不证明 CourtWork 已拥有 CUA。[S28]

第一个产品 loop 限合成测试页或独立测试 VM：打开一个已授权目标、读/填一个无外发后果的表单、保存证据、停止、重连并确认状态。屏幕快照过期、坐标变化、权限拒绝和输出回收需有明确失败语义。不可逆外发仍经实际 owner，不由像素点击结果推断。

## 8. 研究到实现到发表的回音

网页端交付效果、边界、外部资料、首选/备选、最小失败样本与 GUI 落点。本地 Codex 读取当前代码后给出采用/调整/推迟/不采用及原因，映射到原工单，再生成一个可独立合流的纵切。

同一工单最终回填：实现源、证据、实际支持范围和剩余 unknown。Pages 在新能力真实成立后更新相应使用入口；产品方向叙事无需铺内部缺口。Paper 只接收有工程证据支持的可泛化观察，新 API 的发布不自动修改 Canonical 或产品 Paper pin。

长期研究的完成不是“下载很多文档”，而是每个优先事项已有一个可行动的小实验。某候选不能保持权限、恢复和工作效力时，应明确缩小或放弃，不为已有文档投资强行实施。
