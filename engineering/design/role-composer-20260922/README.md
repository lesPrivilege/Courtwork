## The two alternatives

Both run on **one controller** (`specimen/composer-agent.mjs`), one synthetic adapter and one reading renderer (`reading.mjs`), so they say the same facts and differ only in where and when. Both keep the draft, caret, materials, Work location strip and model control of the product composer.

**A · Anchored chooser (the initial hypothesis).** One Agent control first in the controls row, before the model control and Send. It opens an anchored dialog popover: a listbox of agents (name, purpose, availability/running words) beside the **full reading of the highlighted option** (runtime, model owner, Kits, asks/allowed/unsupported/unreported, scope, when), plus *Edit ⟨agent⟩ in Settings*. Arrow keys preview consequences before commit; Enter/click commits and closes. Outside the popover, only what changes the send is said, in the product's existing `#composer-notice` slot: a blocker, a Run in flight, a revision changed elsewhere, a read failure (with Retry).

**B · Agent line.** A line inside the composer, under the field: Agent control · one-line reading (runtime · model owner · approvals; or the blocker / Run in flight, which wraps rather than being cut) · Details · Settings. The control opens a lean `menuitemradio` menu (name, purpose, availability) that commits on pick; consequences are read on the line afterwards. Details expands the full reading in place.

## Recommendation

**Select A**, the anchored chooser. The handoff asked for a second placement only if it "reduces a demonstrated comprehension/navigation cost". B does not reduce one that A leaves open. Everything that decides whether and how the next send happens (blocker, a Run in flight that keeps its binding, a revision changed in Settings, a failed read) already appears next to Send in A, in the product's existing notice slot. The runtime-owned model is visible on the model control. What B adds permanently is the ordinary reading (runtime name, approvals count). It costs 37 px on desktop and 78 px on narrow for every chat, moves the field when Details opens, and gives up comparison before commit. That trade is not justified without evidence that users misjudge approvals at send time.

Carry into E1 if A is selected: shorten the narrow sheet, since the reading could open on demand under the list, and name the composition (combobox with dialog popup) in the change record. Neither is done here.

| Reading / intent | Consumer shape (this specimen) | Rule |

| Identity / scope | `selectedId` = a profile id from `list()`; scope = **this chat's next run** in its current Work location | Never a second registry; the chat does not change Session identity (Attention stays global elsewhere). A choice needing another work location goes through the Work location owner, not this control. |
| Saved / draft / effective / bound | saved = `open(id).profile` at `revision`; draft = `selectedId` (chat-local, unsaved); effective = what `projectNextRun` reads from that saved record (runtime, model owner/value, Kits, grants); bound = `chat.activeRun {runId, profileId, profileRevision}` | Four readings, never merged. The running Run keeps its bound revision; the draft applies to a run started later. Send is not offered during a Run ("Available after this run ends."); no queue. |
| Compatible / unsupported vs denied / unknown | per Kit: `projectProfile(...).compatibility[kitId]` = `{ result: supported/unsupported/unchecked, reason, evidenceRef, declared }` (06E-R1); per request: `unsupported` (runtime), `allow`/`ask`/`deny` (permission owner), absent effect = **not reported** | A missing effect is not deny and not allow. Only verified `unsupported` blocks; `unchecked` is said and blocks nothing by itself, and never removes another blocker. The declaration is shown, never decisive. |
| Revision / precondition | the reading carries `revision`; a change seen after a Settings visit is said ("Attention changed: revision 2 → 3.") | At send the chosen `profileId` + last-read `revision` are the admission precondition; a mismatch must be refused (`profile_conflict`) and re-read with draft text kept. | Late replies | per-id reading slots with a per-request token | A reply lands only in its own profile's slot and only if newest (tests 6 and 9). |
