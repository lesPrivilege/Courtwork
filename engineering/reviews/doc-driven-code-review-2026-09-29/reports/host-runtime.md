## 3. Findings

### Major

**F1 (major, verified by probe). Terminal Run status is not immutable; cancel can overwrite `completed`.**
- Code: `store.updateRun/updateRunWithEvent` (store.mjs:1696-1711) `Object.assign` any patch, no transition guard (nor does `_mutate` validate run status transitions; only executor/Kit/local-Pi validators run, store.mjs:976-978). `cancelRun` reads the Run and `entry` synchronously (service.mjs:3545-3549), then queues `stopping` (3550). If the Run's own terminal write is already queued/in flight, the queued `stopping` lands after it. Then `#executeRun`'s finally sees a non-terminal status and finalises using `entry.cancelRequested` (3369-3372) -> `cancelled`.
- Scenario (reproduced, `tmp-host/probe-cancel-toctou.mjs`, persist delayed 400 ms to widen the window; the mechanism needs no delay, only that cancel arrives while the completion write is being persisted): status events `["running","completed","stopping","cancelled"]`, `cancelRun` returned `cancelled`, final status `cancelled`. A Run that produced a full answer (and possibly recorded artifacts) is re-labelled cancelled; `run.status` events show a terminal-to-active regression. The existing test T-CANCEL-5 even uses `store.updateRun(... status:"running")` on a completed Run as a fixture, showing the store accepts it.
- Contract: api-v6.md:31-34 (terminal statuses), run-attempts.md:31-53 (legal supersede targets rely on final status), RD-001:24.
- Also `openQuestion` (store.mjs:1766-1777) sets `run.status = "waiting_user"` unconditionally, so a question opened after cancel set `stopping` regresses it (code reading only, not executed; `#waitForDecision` service.mjs:3492 then aborts, so the effect is a transient wrong status plus a stray `permission.open` event).

**F2 (major, verified by probe). Managed runtime: Host reports `cancelled` when the native root turn ended `completed` (or failed).**
- Code: `#executeRun` maps the gateway's `{status:"completed"}` to `extensionOutcome "completed"` (service.mjs:3311) but the final mapping (3370-3371) checks `entry.cancelRequested` before `extensionOutcome`. Same for `failed`.
- Scenario (`probe-cancel-vs-complete.mjs`, Agents loopback with `cancel:"ignore"`, `cancelConfirmMs` 5 s; user cancels, remote turn then completes normally): `hostStatus: "cancelled"`, `error: null`, while `remoteBinding.rootTurn.terminal = {status:"completed", evidence:"turn.event"}` is recorded in the same Run. The Host's own evidence contradicts its status. Not covered by p03d (which tests confirmed-cancel and never-confirmed, but not confirmed-completed-after-cancel).
- Contract: RD-001:81 ("cancellation request is distinct from confirmed termination"), agents-host-gateway.mjs:311 ("Only the root turn.cancelled confirms it").

**F3 (major, verified by probe). Pi path: any exception during a pending cancel is reported `cancelled` with `error:null`.**
- Code: catch block service.mjs:3328 sets `extensionOutcome = ... entry.cancelRequested ? "canceled" : "failed"`; final status `cancelled` (3371), and `run.error` is only kept for failed/unknown (3372) so the code is dropped from the record (still in a `run.error` event).
- Scenario (`probe-cancel-exception.mjs`, wrapper port whose `run()` throws `native_lost` while a cancel is pending): `cancel -> cancelled, run.error null`; identical exception with no cancel -> `failed`. This is precisely the "abort exception still returns cancelled" defect RD-001:65 records as found in v3.0 and fixed in v3.1 (there: three error injections return `unknown`). The product code does not carry the fix. Also `runtime_projection_failed` (event-persistence failure) during a cancel would be reported as `cancelled`.
- Contract: RD-001:24,65,73; runtime-foundation.md:75-79 ("persistence failure ... never a completed receipt": true for completed, but a cancelled label hides it).

### Minor / process

**F4 (minor, unverified by execution). Pi cancel has no bounded confirmation.** `cancelRun` awaits `entry.abort()` then `entry.task` (service.mjs:3577-3578) with no timeout; `close()` (2716-2717) does the same. If any tool/SDK step ignores the signal, HTTP cancel and shutdown hang; there is no path that yields `unknown` for a non-cooperative Pi run (RD-001:73 keeps non-cooperative state `unknown`; the managed gateway does, via `cancelConfirmMs`). No test uses a tool that ignores abort.

**F5 (minor). `deleteSession` drops unknown-outcome ledgers.** service.mjs:2506-2518 / store.mjs:1510-1523 refuse only for an active Run or Spark references; Runs in `unknown` (`mcp_effect_unknown`), unresolved `remoteActions`, and `repositoryWriteEffects` with status `unknown` are deleted with the Session. The doc says "removes the execution catalog record" (api-v6.md:80-90) but nowhere says unresolved effects block or are preserved; P03-D says the chat stays fenced until reconciled (p03d:50-75). Deleting bypasses that fence by destroying the evidence.

**F6 (minor). Declared capabilities are not all enforced.** Host consults only start/continue/compact/recover (service.mjs:827-833). `cancel`, `steer`, `submitToolResult` rows are descriptive; Pi advertises `steer: supported` with no route/caller/test (service.mjs:3303, pi-runtime-port.mjs:84).

**F7 (minor, doc-honest). Alternate runtimes are seams, not features.** (a) `npm start` cannot configure the managed Agents port (cli.mjs:38-42; only `startServer({managedRuntimePort})`, index.mjs:271); (b) `reconcileRemoteSession` (service.mjs:2992) has no HTTP route and no UI, so a chat fenced by `remote_unreconciled` cannot be unfenced by any product action; (c) Hermes has no Host path at all (documented); (d) local Pi child needs `localPiWorker:true`. All exercised only by tests with synthetic loopbacks; no real Agents/Hermes service has ever run.

**F8 (minor, doc gap). No answerer.** A pending permission/question never times out (deadline paused, service.mjs:3479); it ends only by cancel, Run end, or restart (`expired_restart`). No silent approval occurs (good), but RD-001:24 asks for "default deny or interrupt".

**F9 (minor, untested). Cross-Run reply refusal** (`question.runId !== runId` -> 404, service.mjs:3504) has no test; RD-001:24 lists "cross-Run reply" as a required counterexample.

**F10 (minor). Redaction gaps.** `this.logger` receives raw provider messages for compaction failures (service.mjs:913,918) although README.md:236-238 says known secrets are redacted "before it is stored or logged". Redaction of run/event errors is implemented but no test injects a key-bearing provider error (T-CRED-2 checks only the public fixture constant on events/config).

**F11 (minor). Non-provider failures are labelled `provider_error`.** `classifyRuntimeError` fallback (probe: `native_lost` exception -> `provider_error: runtime failed`), which misattributes native-runtime faults; matters once a second runtime exists.

**F12 (minor). Locks.** Second-host `LOCK_BUSY` works (my probe) but no repo test asserts it; lock loss fencing (store.mjs:970-975; service `runtime_unavailable`) untested.

## 4. Coupling of service.mjs to Pi (quantified)

Claim (architecture.md:29): "Provider/model helpers and Pi-shaped options/outcomes remain coupling". Claim (architecture.md:122): SessionManager coupling in service must still move out.
- `SessionManager`: 0 references in `app/server/*.mjs`; 4 in `runtime/pi-runtime-port.mjs` (imports, open, create, compact). Line 122 is therefore stale; line 29 is right.
- service.mjs imports 16 symbols from `runtime/pi-session-runtime.mjs` (`classifyRuntimeError, classifyVerifyOutcome, assistantMessageText, registerFakeProvider, createReasoningPayloadHook, resolveCompactionPolicy, FAKE_*x4, API_FORMATS, credentialSourceOf, register/unregisterConnectionProvider, registerCatalogExtraModels, nativeCatalogModelIds`), plus 2 from pi-runtime-port; `this.modelRuntime` (the Pi ModelRuntime) is used 14 times for credentials, model lookup and `complete()` (connection verify, service.mjs:2267).
- Pi native locator `session.hostSession {id,path}` appears 9 times in service.mjs, including the compaction journal path handed to the store (877) and the `nativeRef` given to `openSession` (3078); the remote branch calls a different `openSession` signature (`{sessionId,runId,nativeSessionId,ledger}`, 3076) selected by a duck-typed `port.remote === true` flag (5 sites: 790,811,1101,2778,3073) that is not part of RD-001's vocabulary.
- Port `start()` takes Pi-shaped options (`model` object, `reasoningEffort`, `compaction`, `maxTurns`, `beforeTool`, `beforeProviderRequest`, `onTelemetry`, `beforeInitialInput`, `beforeExtraInput`); the managed gateway ignores most of them (`maxTurns`, `compaction`, `beforeTool`, `beforeProviderRequest`, telemetry), so Host-side governance hooks that live in those callbacks do not apply to remote runs (only the pre-governed tool wrappers do). Tools are Pi `AgentTool` shaped (TypeBox `parameters`, `execute(callId,args,signal)`), and the Agents gateway imports pi-ai `validateToolArguments`.
- Outcome vocabulary is Pi's (`completed|aborted|error|unknown`, `turnBudgetExceeded`), and two executor IDs are hard-coded (service.mjs:788,806,1073; executor-choice-state.mjs:5-6).
Conclusion: the execution/journal seam is real and tested; provider/credential/model/tool/option/outcome coupling remains as documented. "Two independent replacement axes" is not yet demonstrable for Runtime replacement (no runtime other than Pi can be started from the product).
