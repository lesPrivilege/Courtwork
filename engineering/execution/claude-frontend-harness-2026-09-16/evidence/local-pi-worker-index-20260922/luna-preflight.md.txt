## What Pi actually exposes

**Wire and completion.** Pi RPC is JSON objects over stdin, JSON responses plus asynchronous agent events over stdout, with strict LF-only framing and optional request IDs for response correlation (RPC manual, lines 20-37). `prompt` success means accepted/queued/handled, not completed; post-acceptance failure arrives in the event/message stream (lines 41-76). `abort` asks the session to stop and wait for idle (lines 124-135). `agent_end` only closes one low-level run and may be followed by retry, compaction retry, or queued continuation; `agent_settled` is the session-level point after those continuations are exhausted (lines 855-910). A CW adapter must therefore settle on a verified terminal envelope/`agent_settled`, not on the prompt response, `agent_end`, fluent text, or exit code alone.

The event stream gives usable correlation facts: `tool_execution_*` has `toolCallId`, tool name, args and result/error (lines 1012-1055), while `bash_execution_update` can stream output separately (lines 1000-1010). Session state exposes native `sessionFile` and `sessionId`; append-only entries have stable IDs and a `since` cursor (lines 183-216, 719-745). These are native evidence for a later recovery adapter, not CW child identity or acceptance.

**Process precedent.** The upstream subagent example uses a separate `pi --mode json -p --no-session` process, explicit `cwd`, `shell:false`, piped stdout/stderr, JSON event parsing, exit code, stop reason, error and messages; abort sends SIGTERM and then SIGKILL after a bounded fallback (example lines 300-424). This is a strong bounded one-shot process precedent. It deliberately uses `--no-session`, so it does not prove durable child resume.

**Tools and extensions.** The locked 0.85.1 CLI source accepts `--no-tools` (all built-in and extension tools), `--no-builtin-tools`, explicit tool allow/deny lists, `--no-extensions`, and explicit `-e` extension paths (`app/node_modules/@earendil-works/pi-coding-agent/dist/cli/args.js:94-140,286-294`; `dist/main.js:414-424,616-620`). `--no-extensions` disables discovery but does not make an explicitly supplied extension safe. Pi's extension manual says extensions run with full system permissions and can execute arbitrary code, and project-local extensions load only after project trust (upstream `extensions.md:109-120`). Extensions can block/modify tool calls, but this is a native policy hook, not an OS sandbox (`extensions.md:778-793`). A prompt, cwd, tool-name filter, `--no-tools`, or project trust must not be advertised as filesystem/process isolation without Host-enforced evidence.

## Isolation, cancellation and recovery boundary

The locked package exposes explicit configuration seams: `PI_CODING_AGENT_DIR` selects the agent directory, `PI_CODING_AGENT_SESSION_DIR` or `--session-dir` selects session storage, and `--no-session` uses an in-memory session manager (`dist/config.js:405-426`; `dist/main.js:279-282,531-535`). The agent directory contains native auth/models/settings/tools/prompts/sessions/debug paths (`dist/config.js:421-462`), while `cwd` controls project-local `.pi` resources and trust resolution (`dist/main.js:452-454,559-617`; upstream `extensions.md:109-120,353-368`).

A process adapter can therefore create a disposable `agentDir` and `sessionDir`, pass an explicit cwd and sanitized environment, and omit extensions/tools for a no-tool consultation. `HOME` is useful defense-in-depth for libraries that consult it, but it is not the isolation contract; `cwd` and HOME alone are not a sandbox. Native extension code, project resources, provider auth and filesystem effects remain Pi/OS facts until CW verifies and admits them.

Pi's example client starts a child with pipes and maps process exit to an error; its `stop()` sends SIGTERM, waits one second, then SIGKILLs and clears pending requests (`rpc-client.ts:71-167,537-580`). That is transport cleanup, not evidence that an effect stopped or that a session can resume. If CW sends RPC `abort`, it should still wait for a terminal/settled observation. EOF, signal exit, lost acknowledgement, or exit after an effect-bearing tool call must become `unknown` and require reconciliation; it must not be auto-retried or treated as accepted work. A later recovery slice may use an exact native session ID/file and `get_entries(since)`, but Pi's persistence does not transfer ownership of recovery to CW.

## Fit with existing RD-005 owners

`app/harness/subagents.mjs` already persists Spark attempts before dispatch, freezes source/scope facts, rechecks grants, serializes child dispatch, and stores result hashes/consumption; the local Orchestra record maps these responsibilities at `explore/orchestra-implementation-20260919.md:24-31`. `app/harness/child-execution.mjs` is explicitly conformance-only and must not become a second scheduler. The existing `app/runtime/pi-session-runtime.mjs:133-146` uses an empty resource loader and `:178-189` uses an in-memory credential store; that intentional in-process isolation cannot be assumed for a separate CLI worker.

The adapter boundary should therefore preserve, in the existing child attempt/result owner: CW child/attempt ID, Pi revision and executable identity, mode, source revision, explicit cwd, isolated agent/session dirs, effective tool/extension policy, model/provider declaration, budget/deadline, request IDs, native session ID when observed, event/terminal evidence, process exit/signal, result/error envelope, artifact/result hashes and unknown/reconciliation state. Native Pi IDs are attributed observations; they do not replace CW child/run identity. No new scheduler, transcript ledger, permission authority or acceptance store is needed.

## Feasibility and staged first slice

**Feasible, with a narrow first consumer.** The safest first live shape is a bounded no-tool consultation/one-shot child using the upstream JSON event surface (`--mode json -p --no-session`) behind a versioned process adapter. RPC managed sessions should be a later capability, because they introduce queues, steering, extension UI requests, session switching and native persistence that RD-005 does not need for its first result packet.

1. **L0 — protocol contract and fixtures.** Freeze the JSONL parser, request/response correlation, event ordering, `agent_end` versus `agent_settled`, tool-call correlation, malformed/oversized/split frames, duplicate terminal, EOF, timeout, abort and signal-to-unknown mappings. No Pi process or model call is needed.
2. **L1 — process adapter.** Reuse the Host child admission/attempt seam and the upstream process precedent: `shell:false`, explicit executable/argv, cwd, disposable `PI_CODING_AGENT_DIR`/session dir, bounded stdin/stdout/stderr, `--no-tools`, `--no-extensions`, `--no-session`, timeout and process-group cancellation. Keep the adapter one-child-at-a-time and return a typed result/unknown envelope.
3. **L2 — authorized upstream conformance.** Against the exact Pi revision, verify no-tool prompt acceptance, event/settled ordering, malformed/late output, abort, exit, and exact native identity with a loopback/no-inference fixture. Separately test session persistence only if a real consumer needs continuation. Do not infer tool enforcement from the no-tool flags.
4. **L3 — RD-005 integration.** Attach the adapter to the existing Host/Spark child lifecycle, grants, source packet, result consumption and work owners. Keep one child per parent task, bounded output and no recursive delegation. A native Pi child remains runtime-owned; a CW-launched child receives CW attempt identity and reconciliation.

**Adopt:** Pi JSONL framing, correlation IDs, accepted-versus-settled distinction, native session/entry cursors, explicit process launch, and terminal/exit evidence. **Adjust:** use the upstream one-shot example only as transport precedent; impose CW identity, grants, budgets, source/result hashes, unknown recovery and effect reconciliation through existing RD-005 owners. **Reject:** treating prompt/cwd/HOME/tool lists, Pi extensions, exit 0, or a native session file as a sandbox, CW acceptance, or automatic recovery. **Defer:** toolful Pi workers, extension-bearing workers, live session resume/steering, ACP, and a generic runtime marketplace until L2 evidence and a concrete consumer exist.

No implementation or capability acceptance follows from this preflight. The next decision is the bounded L0 contract; it should preserve the above facts and leave unsupported operations explicitly unavailable.
