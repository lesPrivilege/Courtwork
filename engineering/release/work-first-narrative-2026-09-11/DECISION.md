# Astra · 从长期工作出发的产品定义与发布叙事

2026-09-11，产品基线 `d03b1198cc3cb3dd65388c0b55f6b02c89efbcf9`。消费[最新三轮/完整快照](../../research/chat-attention-2026-09-11/work-first/README.md)及用户随后对Court/在场的明确说明。本文裁定产品含义和本轮文案；现有架构/领域owner继续由[Runtime与Work canon](../../architecture-runtime-canon.md)和对应合同持有。

## 先从问题推导

1. 一件工作可以跨越多次对话、执行、参与者和人的决定。任何一次执行只取得局部材料，只有局部视野。
2. 下一位参与者需要知道当前以什么为准、依据是什么、还缺什么；仅有某次回答或运行成功不足以回答这些问题。
3. 因此，需要独立于某次执行维护来源、有效状态、决定与未完事项，并明确如何使一项变化生效。原始记录与协议恢复数据仍可保留，不因强调有效状态而丢弃。
4. 参与者按真实职责、权限和可用能力取得材料、提出结果；工作状态的正式变化由原owner及事务规则确认。一个模型或runtime不能因产生输出而取得全部工作权威。
5. 产品首先应说明这一持续的工作场合，再说明交谈、处理变化、持续派生三类体验；runtime/provider是支撑实现的选择维度。

结论：**CourtWork的产品重心是工作如何有序延续，核心工程投资是Work Core及其明确接缝。** 当前Pi执行集成是实际组成部分；自研最小Harness职责和外部Runtime适配属于支持工作需要的工程选项，优先级由缺口/可验证收益决定，不由品牌叙事预定某个实现胜出。

## Court的明确含义

用户裁定原话：“Court 作为抽象理念，代表有机和正式编排下的工作场合，不是角色扮演”“也不是律师工作流”。

**Court指有机协作与正式编排共同构成的工作场合。** 人、Agent、材料、工具与判断围绕真实工作需要组成关系、调整分工和完成交接；范围、来源、当前状态与变化生效条件可以说明、检查和追溯。有机不是无边界自治，正式也不要求固定剧本或全部步骤人工审批。

这是抽象理念和产品组织原则。本轮不引入新的Court领域实体、法院式管辖树、角色扮演人格、Court store/API或第二套状态owner。现有法律/NDA样例只是应用示例；不将品牌定义为律师工作流，不从英文Court推导法槌、法庭人物、庭审剧情或统一法律职业视觉。

## 从“you are there”到人在工作关系之中

用户回顾最初对比Cowork的命名意图，并明确授权Astra自由撰写。采用“人在其中，工作继续”：人是场合中的参与者，拥有意图、判断、委托与返回的路径；在场不等于持续在线、每一步亲自操作或只站在外部监督。代理执行可以继续，人的位置不因暂时离开而被抹去。

这也是品牌理念与运行状态的边界：当前App的online/presence、审批或数据权限继续使用真实事实；概念上的“人在其中”不能使离线状态伪装在线或自动授予权限。早期命名说明按用户原话存档，不编造uit的逐字母词源或Cowork功能比较。

## 最新三轮逐项裁定

| 输入 | 裁定 | 原因及后续责任 |
|---|---|---|
| Work Core优先，工作跨越Harness | 采纳产品重心 | 与现有Work Core正式状态owner一致；不声称Core自动拥有所有个人数据、账号或外部provider状态。 |
| Role ≠ Runtime ≠ Provider | 采纳分离原则 | Expert专业职责与Chat/Attention/Spark交互目的不等同；不将四者统一为同种角色对象或设置DTO。 |

| “只需UI投影”“社区证明一大半” | 不采纳为已验证结论 | 事件名称相似不证明权限、持久身份、重试和正式接受等价。来源38结果/3线与外部功能未重验。 |
| permission/question统一变AttentionItem | 不直接采用 | 执行权限归Host/runtime policy，专业成果接受归Work Core/Review；UI可协调呈现，不能抹去对象与授权差异。 |
| Spark受限推理、分类、填表标注 | 登记有界profile研究 | 继续围绕来源/派生知识定位，不宣布通用后台调度已完成。不预定短context/快模型总是更优；需固定fixture、权限、成本、有效性与恢复证据。 |

| Store→Govern→Retrieve→Compile | 作为解释线索，拒绝全系统唯一流水线 | 原始输入可以先保真登记，事实的有效性和消费权限需明确；控制/查询不必经compiler，外部原始数据不因存储即成正式工作事实。 |
| Chat/Attention/Spark三种长期工作体验 | 采纳用户目的划分 | Chat以人主导连续对话；Attention汇聚值得处理的变化；Spark围绕来源持续派生。沿Chat专门页面合同，后端未实现项继续标明。 |

## 对外叙事次序与本轮实改

先讲“长期工作跨越对话与执行”→“每次接手需要共同依据和明确边界”→“CourtWork保留来源、决定与未完事项”→“三个入口分别服务人的不同目的”。Matter、Expert、Work Core、Runtime等词随后按需要解释，不把一串内部名词当作开场理由。

- 首页Hero：`Your work. With you in it.` / `人在其中，工作继续。` 从人的讨论、委托、离开与返回讲起，来源和交接有共同记录；保留现有构图、导航和图资产。
- README：同步其真实生成源 `site/src/readme.mjs`，从问题/用途展开，再说明三个入口和当前Pi/Work Core实现边界。此前直接写README的产品段也合入生成源，避免下一构建覆盖。
- 首页Paper入口与 `PAPER.md` 导读：先问“会话结束或执行者更换后，工作应留下什么”，再解释Event/State/Context各自回答的问题。修改的是导读，不改变论文正文、标题、作者、9.6/2026-09-07采用坐标、review manifest或论文命题。
- Features/Experts相邻文案：解释共同工作和专业责任；法律内容明确为示例，不写成唯一用途。现有功能与计划仍分开，不新增虚假的Runtime连接/Chat memory状态。

内部概念定义：**Court指有机协作与正式编排共同构成的工作场合。人在其中表达意图、委托执行、作出判断，也能离开后回来，接续和改变工作的方向。** 不采用“Court拥有你全部工作”“任意runtime现在即插即用”“所有插件只是提示词”等扩大表述。
