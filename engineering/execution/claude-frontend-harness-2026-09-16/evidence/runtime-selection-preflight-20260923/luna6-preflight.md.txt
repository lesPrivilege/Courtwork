## Minimum Session → Run slice

1. Keep the default executor fixed to Pi. Add a small typed Session `nextRuntime` intent with a stable adapter ID and a capability/compatibility status derived by Host from the adapter descriptor. Treat requested, effective, and bound as different values. Mutate it through a version/precondition checked by the existing Runtime Control whole-config revision or an equally explicit existing-owner CAS; do not add a per-adapter registry, provider registry, or new per-profile version. A stale intent must refuse before command/run admission.
2. At Run admission, resolve that intent through the existing Host composition root/adapter factory allowlist. Reject unknown IDs and unavailable/unverified operations with typed reasons before creating a Run or native session. Snapshot the selected adapter ID/revision/protocol and immutable relevant config reference (hash/connection identity and credential-generation identity, never a secret) in the Run's existing adapter/binding owner. Preserve `run.adapterId` as the execution dispatch key; preserve the existing `hostSession` shape and remote-binding fields as separate native identities. Bind profile/Kit revision, profile hash, Kit pins/context reference, provider/model and permission mode as they are now; do not let selection bypass any gate.
3. Wire the chosen adapter through `openSession/start/observe/control/dispose` at the current Runtime Port seam. Do not add a parallel “executor registry”: extend the existing composition-root injection/factory and adapter descriptor. Host remains owner of Run status, tool governance, effects, source/result references, credential binding and unknown outcomes. The Agents adapter must keep functions Host-mediated and refuse native capabilities not yet proven.
4. If Session-level target intent and immutable Run binding require additional persisted fields, ownership is **Host RuntimeStore**, with strict validator and exact-backup migration from 21 to 22; Core schema 4 and bridge schema 5 remain unchanged. Keep current profile/Kit `runtimeSnapshot` distinct from executor binding so fields do not silently change meaning. Run binding is immutable history; changing Session intent affects future admissions only. Existing Runs and native sessions never hot-swap.

### Profile, Kit, permission fences

Keep the existing compatible profile composition check and Kit compiler/readback unchanged. `retainKitContext()` binds the adapter ID/revision and permits only evidence marked supported; unchecked Kit compatibility remains explicitly unchecked/refused as required by that contract. Preserve the profile's resource ceiling, Host permission intersection and current `governTools` path. Runtime capability is not a grant; a Kit/profile request cannot add executor capability, native tools, filesystem permission, hosted environment, or recovery semantics. Do not route provider/model choice into Runtime choice: Models and credential ownership stay in Provider control. No automatic fallback if the chosen executor is unavailable.

## Decisive acceptance checks (focused, synthetic first)

1. New Session defaults to the existing Pi adapter; historical Sessions/Runs decode/migrate, and their original host/remote identities and profile/Kit snapshots are byte/semantic-preserved.
2. Selecting the managed adapter persists only an allowed ID/config reference; stale CAS, unknown ID, unavailable capability, incompatible profile/Kit, and permission-denied capability all refuse before a Run/native request. No fallback or second Run/effect occurs.
3. After Run admission, mutate Session selection/profile/provider/credentials: the admitted Run still reports the original adapter+revision, source/config hash, provider-generation, profile/Kit pins, and capability snapshot; next Run sees the new state. Active Run rejects switch and native locators never cross adapter shapes.
4. Duplicate command replay returns the same Run/binding; concurrent admission with a lost response cannot open two sessions. Restart with an unresolved managed create/effect remains unknown and blocks conflicting admission; no auto-create, tool re-execution, result replay, or false terminal.
5. Adapter capability matrix proves exactly the approved path (initially one governed `repo_read` if this is the P03 consumer); denied/out-of-scope/native tool requests invoke no filesystem/helper action, and Host event/effect receipts remain sole settlement authority. Keep live-service evidence separate; synthetic fixtures do not promote runtime availability.
