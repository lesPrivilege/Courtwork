# Runtime selection R0 · concrete Host contract proposal

Baseline source: `abcd30e4965fe3d1fd5258a362718ba2835315e9`, branch `codex/runtime-selection-r0-20260923`. **No product code, schema, service, user data or live adapter was changed by R0.**

## Responsibility and decision boundary

The Host must let two ordinary Chats in one process use different *explicitly eligible* executors while each Session keeps one native lineage. RuntimeStore owns the Session choice and immutable Run identity. The composition root owns the finite configured factory allowlist and derives current availability. Runtime Control continues to own Role/profile/Kit composition; Models continues to own Provider/Model and credentials; the Runtime Port describes and executes native operations. Core and its acceptance state do not change. The nearest implemented precedents are `createRuntime`'s injected Pi port, `RuntimeService.#createRun/#executeRun`, RuntimeStore's serialized `createRun`, the P03-C remote action/binding owner, and K3's frozen `runtime.bound`/Kit context.

Pi is the product default. `agents-api` is the sole proposed managed alternate under its original P03 live gate. `pi-local-print` stays a Spark child adapter and cannot be chosen for an ordinary Chat. The already accepted P03-C/D/E native create/root/action/reconciliation records remain authoritative; R1 must not replace them. A test-injected Agents port proves offline behavior only. The current production composition has no verified live Agents configuration, so its public choice remains unavailable until that separate gate is met.

An ordinary Session means `scope: project|unassigned`, no professional `extensionBinding`, and no Spark child assignment. Choice is writable only when that Session has **no Runs, no `hostSession`, no `remoteBinding`, no remote actions, and no child/native execution history**. The first admitted Run freezes its executor lineage, even if it failed before opening a native session. A historical or active Chat cannot hot-swap through this selector. Global Attention, extension Sessions and Spark child Sessions carry a read-only choice projection for schema consistency; GET reports `locked` with `not_ordinary_chat`, PUT refuses, and their established actual-port/child execution paths do not consult the public mutable selector. A child-only `pi-local-print` Run remains governed by Spark even if its Session has an ordinary-choice placeholder.

`CapabilitySnapshot` is an exact-key object for the seven operations named above, each `{supported:boolean, reason?:string}`; unsupported rows require a bounded reason. New bound revisions are nonempty bounded strings, and new configuration refs have the form `sha256:<64 lowercase hex>` over canonical immutable executor-specific configuration plus adapter revision/protocol (for example an explicitly configured managed transport endpoint identity). No secret or Provider/Model/credential fact enters this hash; Pi key rotation and model changes between Runs do not alter its executor ref. If a managed account change alters the native namespace, the existing remote binding owner needs an explicit non-secret native account identity; the factory ref cannot silently stand in for one. The composition root rejects duplicate IDs. A different ref denotes a different configured executor instance, never an implicit update of a Session with history. The existing single-port test injection may keep its sole injected port as that test Host's default; the product path always defaults to Pi.

Use a new authenticated `GET /sessions/:id/executor-choice` for `{sessionId, choice, locked, lockReason, options}` and `PUT /sessions/:id/executor-choice` with exactly `{expectedRevision, adapterId}`. The Host derives the ref and availability; the caller never submits them. A stale revision returns 409 with no mutation; a lost PUT reply is recovered by GET of the same Session. `locked` is derived from Store history/scope, not a second persistent boolean. The option list reports unavailable reasons and known facts without inferring live availability from a fixture or boolean; unknown historical IDs remain readable in `choice` but cannot be reselected or silently mapped to Pi. Nonordinary/child GET is read-only with its reason; PUT refuses without affecting its existing run path. No 06c synthetic field becomes an owner fact through this route.

The existing Run request's `runtimeSelection:{revision,profileId,sourceHash}` remains the **profile/Kit expectation**. Add a separately named optional `executorExpectation:{revision,adapterId}` for a page that read the executor choice. A mismatch is `executor_selection_conflict` before Kit retention or Run/native/provider dispatch. Existing callers without that field continue against the persisted choice; they do not request another executor. The frontend consumer should send both independent expectations. A future UI can present requested Session choice, currently available configured option, and bound Run identity separately; R0 grants no frontend source lease.

## Atomic choice, admission and refusal

1. `PUT executor-choice` resolves an allowlisted, eligible configured descriptor, then performs revision, ordinary-scope and **no-history** checks inside one RuntimeStore `_mutate`. A same-ID update after any history still refuses; the reader may GET without mutation. Different Sessions may choose while another Session's Run is active because this action changes no running port or global provider config.
2. `#createRun` first returns the existing `commandId` receipt, before current executor/profile/provider availability checks. A changed input under the same command ID keeps `command_conflict`. For new nonchild work, resolve the saved or read-only historical choice through an explicitly matching eligible factory, check adapter revision/ref/capabilities, **selected-executor Provider/Model eligibility**, profile compatibility and Kit eligibility, and pass the pre-transaction choice revision plus descriptor to Store. Generic Provider connection readiness or a matching factory hash alone is not proof that this executor can run that model. All existing per-Run Provider and managed remote binding/configuration/credential checks still apply independently; the executor ref never waives them.
3. Inside `store.createRun`'s single `_mutate`, **after** original-command receipt lookup, validate the submitted choice's pre-transaction revision/adapter, any non-null ref, native lineage and existing unknown/remote fences before admission. If a legacy choice has `configurationRef:null`, atomically set it from the resolved descriptor, increment `executorChoice.revision` **once**, and create the Run with `executorBinding.choiceRevision` equal to that **post-pin** value. An incoming `executorExpectation` is compared to the pre-transaction revision. A new schema-22 or previously pinned choice keeps its revision and requires the exact same ref. An aborted admission writes neither pin nor Run. If public PUT wins a race first, a stale Run expectation refuses; if Run wins, PUT sees history and refuses. Duplicate command replay returns its original binding before these current checks and never increments again.
4. Existing K3 `retainKitContext` receives the selected port's descriptor. Its verified in-process Pi `reference-only-pi-unchecked-v1` policy remains valid; a nonempty Kit on managed Agents refuses before a provider/native request. A concurrent CAS loss after immutable Kit payload retention may leave an unreferenced retained object under today's K3 ordering, but must create no Run, native session, provider request, permission or visible binding.
5. The active nonchild Run entry keeps the exact selected port object and `executorBinding`. Execution uses it for native open/start/observations; cancel uses the entry's existing abort handle. Compaction and explicit remote reconciliation resolve the Session's **pinned** port and native shape, never the process default. A post-restart missing or changed factory produces an unavailable refusal without Pi fallback, while historical Run and unknown/action records remain readable. P03-D reconciliation is observation only and keeps lost-create/no-locator and no-result effects fenced.
6. Once a new `bound` Run exists, later Runs require the same adapter ID, revision and executor configuration ref. A changed executor factory ref refuses. Remote connection/credential changes may separately refuse under the existing remote binding contract; ordinary Pi key rotation or model changes between Runs retain their existing Provider behavior and do not change executor identity. For schema-21 legacy nonchild Runs, the absent factory ref remains honestly unknown: the old Pi locator and remote binding's existing checks govern continuation with an explicitly configured matching port. The first schema-22 bound Run pins Session ref/revision in the same transaction; later Runs cannot repin. No proof of historical transport configuration is claimed.
7. Spark child admission/Run creation bypasses the ordinary selector and its first-pin rule. A child Run retains its actual `run.adapterId`, local-Pi receipts or Pi journal, and existing Spark fences; Store writes `executorBinding:null` only when the existing assignment/session/run linkage proves child ownership. No null choice or ref can by itself classify a Run as a child or block the established child path.

| Trigger | Result before new execution |
| --- | --- |
| Unknown ID, child-only ID, nonordinary scope, extension-bound Session | 409 `executor_ineligible`; no saved choice |
| Configured descriptor absent/unverified, ref/revision changed before admission | 409 `executor_unavailable` or `executor_configuration_changed`; known descriptor facts may still be read, no fallback |
| Provider/Model unsupported by selected executor | 409 `executor_provider_unsupported`; existing Provider readiness alone cannot admit it |
| Stale choice PUT or Run `executorExpectation` | 409 `executor_selection_conflict`; no new Run |
| Any Run/native/remote/child history when PUT attempts a change | 409 `executor_lineage_locked` (active history may use `active_run`); existing history unchanged |
| Saved executor differs from native locator or Run lineage | 409 `runtime_mismatch`; no cross-adapter open |
| Port lacks start/continue/recover/compact, or Kit cannot bind to that port | Existing `runtime_capability_unsupported` / Kit typed refusal; no alternate routing |
| Unknown remote create/effect/root after restart | Existing unresolved/unknown fences and P03-D report; zero automatic create, local tool repeat or result resend |

## Legacy 21 → proposed 22

R1 needs a typed Session choice and Run binding, so propose RuntimeStore **21→22**. Validate all schema-21 bytes first; write an exact, exclusive `runtime-state.schema21.<sha256>.json` backup; persist the new state atomically. The pinned schema-21 reader must refuse schema 22 byte-for-byte. Core user schema 4 and bridge app schema 5 do not change. Update only the current schema entry points under `engineering/verification.md` in the later implementation lease; R0 changes no version.

Pure migration reads persisted state only and sets **every** schema-21 Session `executorChoice.configurationRef:null`, including an empty Pi-default Chat; it never consults today's factory. For a nonchild Session, retain one distinct historical `run.adapterId` only if all Run identities and any native evidence agree: Pi `hostSession` must not be mapped to Agents, and `session.remoteBinding.runtimeId` plus each Run remote binding/protocol must not be mapped to Pi or another ID. A lost remote create with no locator still retains its actual Run adapter ID and unknown fence; absence of native evidence does not authorize a guessed Pi mapping. With no Runs, a Pi locator pins Pi, an existing remote binding pins its recorded runtime ID, and an empty Session defaults to the Pi ID. Contradictory mixed ordinary history gets `adapterId:null` and stays readable but cannot admit a new ordinary Run. Unknown single historical IDs remain exact strings and fail unavailable when their factory is absent.

Every old nonchild Run keeps its Run/event/native/remote-action/Kit/Provider bytes unchanged and gets `executorBinding:{recording:'legacy', revision:null, configurationRef:null, capabilities:null, choiceRevision:null}`. A historically provable Spark child Run instead gets `executorBinding:null`; its assignment, actual `run.adapterId`, native/Local-Pi receipts and owner path stay intact. Migrated global/extension/child Sessions also have null factory ref and an excluded, read-only choice. Nonchild global/extension choice IDs reflect agreed historical adapter/native evidence or Pi default when empty; service routes those Runs to that actual port, and the internal first-pin transaction records its post-pin choice revision without opening a public selector. A child's stored Pi choice is only a schema placeholder, never its executor: Spark's assignment picks the actual child path and Run adapter. A new schema-22 Session is different: service supplies the resolved default descriptor to Store at creation, so its persisted Pi ref is known without a migration guess. No public PUT is allowed for these excluded Sessions.

Schema-22 validation cross-checks nonchild Run IDs/native evidence against a non-null chosen lineage, `bound` Run ref/revision and consumed `choiceRevision` consistency, Pi versus remote locator separation, and all existing action/Kit invariants. A migrated null choice is accepted only for contradictory ordinary history and remains fenced. `executorBinding:null` is legal only when the existing Spark assignment/session/Run reference proves child ownership, irrespective of whether that child's actual adapter is in-process Pi or `pi-local-print`. The child exception never admits null binding for an ordinary Run and never adds a child factory registry.

## Decisive R1 evidence, offline first

1. Schema-21 Pi Session with actual SDK journal and Run upgrades with an exact backup, `configurationRef:null` and legacy Run `choiceRevision:null`; it continues the same locator, preserves events/Kit context, and the old reader refuses 22. An empty schema-21 Session also has null ref; a new schema-22 Session receives the resolved Pi ref at creation.
2. One Host with two ordinary Sessions runs Pi/local fake and injected managed Agents/loopback respectively; each has its own frozen adapter, capability and non-secret ref, and no native locator crosses shapes.
3. Two concurrent first-choice PUT/admission orders exercise Store CAS: exactly one winning choice/Run lineage; stale choice and stale `executorExpectation` produce no extra Run/native/provider request. A migrated null-ref Session's first bound Run pins the descriptor and increments choice revision once; a lost reply/same-command replay returns that Run and never pins twice, and later Runs consume the pinned ref without another increment.
4. Selected Agents factory missing, unverified or ref changed at restart refuses with its reason and zero execution; Pi does not take over.
5. A nonempty v2 Kit admitted on verified Pi retains today's unchecked policy and exact context; the same declaration on managed Agents refuses with zero provider/native requests. Profile `runtimeSelection` still guards its own revision/hash independently.
6. After a Run, changes to profile/Provider or executor factory revision/ref never rewrite historical binding. Pi key rotation or model changes between Runs retain the existing Provider checks and do **not** change executor ref; a managed remote credential/configuration change still meets its existing remote-binding fence. An attempted Session switch is locked.
7. Lost Run POST reply and identical `commandId` replay return the same Run/binding before current configuration checks; changed input conflicts; one native create/one provider request at most. Global/extension nonchild Runs bind their actual fixed/historical port with read-only Session choice; Spark child Runs retain `executorBinding:null` and their established owner without an ordinary-selector refusal.
8. Reopen with unresolved remote create or retained effect: explicit observation returns only P03-D evidence, no second create/governed `repo_read`/result send; existing unknown fences remain. Synthetic loopback cannot certify account-authorized live Agents operation.
