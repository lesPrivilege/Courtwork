## Blocking exact-copy finding

markedCodeText at app/web/ui-controls.mjs:308-310 unconditionally removes one final LF from pre.textContent. That is valid for the normal marked-generated case where marked appends a terminal LF to a code token with no authored trailing line ending. It is not valid for all authored code:

- fenced Markdown with retained trailing blank lines: marked preserves the authored newline(s) in the code token; removing one loses a blank line;
- raw HTML pre/code: marked preserves authored content without synthesizing the terminal LF. An authored printf "x" followed by LF becomes printf "x" after markedCodeText; an authored two-LF ending loses one newline.

The focused source probe is in luna-boundary-probe.stdout.txt. Parent OpenAI CUA independently reproduced the same production handler behavior for fenced trailing blank and raw pre/code in copy-boundary-probe.json. This violates the author README's exact-authored-bytes claim and makes Chat/Attention's shared builder disagree with the reader's direct element.textContent path for affected content.

The existing code-block browser test only exercises a one-line fenced command and a multiline block without trailing blank/code-HTML edge cases, so its exact-copy assertions do not close this counterexample. Request a narrow correction: carry the authored/token code text into the Copy action or otherwise remove only a parser-synthesized terminal LF with an explicit provenance rule. Do not trim arbitrary authored bytes.
