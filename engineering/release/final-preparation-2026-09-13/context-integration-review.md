## Finding: conditional duplicate cache presentation

The capacity calculation does not add cache tokens to the inclusive provider input total. However, the Context Inspector can present cache observations twice when one completed row carries both raw provider cache metadata and Pi-normalized cache usage:

- `app/runtime/request-telemetry.mjs:56-71` records `cache` from the raw SSE observer and `usage.cacheRead` / `usage.cacheWrite` from the completed SDK message in the same row.
- `app/web/chat-measurements.mjs:113-117` appends `renderCacheDiagnostic(latest.cache)` and then appends the compact request-measurements disclosure.
- `app/web/telemetry-view.mjs:101-108` includes normalized “Cache read” and “Cache write” values in that disclosure. The raw diagnostic separately shows cache hit/miss and cache write at `app/web/chat-measurements.mjs:64-80`.

For example, a completed row with raw `hit_tokens: 900`, `write_tokens: 90` and normalized `cacheRead: 900`, `cacheWrite: 90` can show both “Cache hit · 900” and “Cache read · 900”, plus “Cache write · 90” twice. If the two representations differ, both numbers can appear without a source distinction in the nested usage rows. This is a source-level counterexample from the composition; no live provider response or browser rendering was used to establish how often it occurs. Disposition: choose one presentation owner for overlapping cache counts in this Inspector, or make distinct source/meaning explicit and avoid a repeated count. This finding concerns presentation, not capacity arithmetic.

## Verified integration behavior

- `app/runtime/context-capacity.mjs:13-20` reads the provider’s inclusive `prompt_tokens` or Responses `input_tokens` directly. It does not add cached tokens. Cache metadata is collected separately at lines 23-56; a hit/miss proportion is admitted only when counts agree, the denominator is request input, and the supplied rate matches the counts. Inconsistent counts remain raw diagnostics without a proportion.
- `app/runtime/pi-session-runtime.mjs:481-490` preserves `beforeProviderRequest?.()` before installing the usage observer. The integration CSS diff is additive around the existing Spark rules and appends the cache diagnostic styles.
- `app/server/service.mjs:1965` persists each telemetry event with the outer `run.id`; `app/runtime/pi-session-runtime.mjs:473-475` starts request IDs at one for each new Run. `app/web/telemetry-view.mjs:31-35` filters by Run and keys rows by `runId:requestId`. `app/web/chat-measurements.mjs:5-10` returns no request observation without a Run ID. A missing or malformed capacity projection therefore does not borrow an older Run’s reading.
- Nested projection gates remain the fail-closed boundary for the new optional v1 fields: `projectContextCapacity` requires the expected version, `request-input` scope, `provider-reported` source, recognized window source and a positive safe-integer window (`app/web/chat-measurements.mjs:13-21`). `renderCacheDiagnostic` requires an available request-scoped record with an allowed source and safe counts, and only plots a ratio after consistency checks (`app/web/chat-measurements.mjs:52-80`). `validMeasurement` in `app/web/telemetry-view.mjs:8-29` does not itself validate the optional `contextCapacity` or `cache` objects; consumers perform those gates. Thus the UI projection is guarded, while the base v1 event validator remains backward-compatible rather than a strict validator of the added nested objects.
- The default 1,000,000-token window is explicitly a display registration, not a provider capability or compaction threshold (`app/runtime/context-capacity.mjs:1-10`). Compaction requests are tagged as `purpose: 'compaction'` and ordinary requests resume as `agent` (`app/runtime/pi-session-runtime.mjs:551-565`). The ring labels its reading “latest completed request input,” and the request detail retains purpose; this does not claim the value is the current working set (`engineering/design/context-capacity-ring-2026-09-14/contract.md:7-22`).
- The integrated UI implements the latest request input reading and request cache diagnostics. It does not render a Source × Residency breakdown; that richer projection is explicitly outside this delivery (`engineering/design/context-capacity-ring-2026-09-14/contract.md:24-53`).

No tests, browser sessions, or real-provider requests were run for this review. The parent remains responsible for deciding whether the conditional cache duplication needs a follow-up before release; this report does not accept the implementation or claim product-level verification.

## Final resolution — 2026-09-14

The conditional duplicate-cache presentation finding above is resolved by the current follow-up diff. `renderChatMeasurementBody` still appends the raw cache diagnostic in the completed Context view, but now omits the nested normalized request-measurements disclosure when `kind === 'context'` (`app/web/chat-measurements.mjs:113-118`). The full request-measurements disclosure remains available from Activity. This gives the Context view one cache presentation owner while preserving the detailed request history in its existing view; capacity arithmetic and telemetry ownership are unchanged.

A new synthetic regression in `app/tests/context-capacity.test.mjs:123-145` checks the 750,000 / 1,000,000 context reading and 50% raw cache hit, asserts that Context contains neither normalized cache rows nor the duplicate request disclosure, confirms normalized input/cache-read details remain in Activity, and verifies unavailable cache metadata does not become a diagnostic claim. The parent additionally reports a browser check showing Context at 75% with 50% cache and an Inspect run action, without duplicated SDK details; I did not run a browser session myself.

Independent verification with Node v22.19.0 passed all 28 targeted tests: `app/tests/context-capacity.test.mjs`, `app/tests/request-telemetry.test.mjs`, and `app/tests/telemetry-presentation.test.mjs` (0 failures). This follow-up test run supersedes the earlier note that no tests were run for the initial static review. It closes the bounded presentation finding; it is not a claim of full-suite, real-provider, or independent browser acceptance.
