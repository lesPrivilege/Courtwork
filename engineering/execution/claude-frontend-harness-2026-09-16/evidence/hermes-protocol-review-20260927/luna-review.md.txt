## Findings requiring correction

### HPR-R1 · frozen objects are treated as provenance

`app/runtime/hermes-api-runs-adapter.mjs:164-169` returns a frozen status
record, but does not attach an adapter/endpoint provenance token. At
`app/runtime/hermes-api-runs-adapter.mjs:303-306`, `continuationIntent()` only
checks `Object.isFrozen(from)`, a string `nativeRunId`, and a truthy
`nativeSessionId`. Consequently, a status validated by adapter A can be used
to continue through adapter B at a different endpoint. The parent’s injected
transport probe (raw result in `parent-identity-probe.json`) and my rerun
(`luna-identity-probe.stdout.txt`) show `session-from-A` from
`http://127.0.0.1:1111` sent in a continuation POST to
`http://127.0.0.1:2222`.

This violates the contract’s requirement that native run/session/endpoint/
revision remain distinct and that continuation use a native identity observed
and validated by this adapter. A frozen forged record with an arbitrary
session ID is also accepted for the same reason. Small correction direction:
keep a closure-private registry/token for status records produced by this
adapter (and require it in `continuationIntent`), or carry and compare an
equivalent non-forgeable adapter/endpoint identity. Do not infer provenance
from `Object.isFrozen`.

### HPR-R2 · `admit()` accepts a forged frozen intent and arbitrary body keys

At `app/runtime/hermes-api-runs-adapter.mjs:139-145`, `admitWith()` accepts
any top-level frozen object with a `body` and string `idempotencyKey`, then
passes `admission.body` unchanged to `transport.createRun()`. It does not
verify that the object came from this adapter or that the body is exactly the
adapter’s `{input}` / `{input, session_id}` shape described by
`app/docs/hermes-api-runs.md:31-37`.

The deterministic injected transport accepted this frozen value and observed
the following wire request:

```json
{
  "idempotencyKey": "forged",
  "body": {"input": "x", "session_id": "arbitrary", "toolsets": ["all"]}
}
```

Raw result: `luna-identity-probe.stdout.txt`. This bypasses the documented
“frozen intent it builds” and can smuggle unsupported fields into a future
native request. A closure-private `WeakSet` (or equivalent private brand) of
intents created by `intent()` is the smallest provenance fix; exact-key/body
validation remains a useful defensive check before forwarding.

### HPR-R3 · caller-supplied limit overrides can remove the bounds

Both constructors spread overrides without validation:

- `app/runtime/hermes-api-runs-transport.mjs:66-72`
- `app/runtime/hermes-api-runs-adapter.mjs:122-125`

The transport accepts `maxFrameBytes: NaN`, `maxStreamBytes: Infinity`, and
`streamIdleMs: -1`; the adapter accepts `maxDiagnostics: NaN` and
`maxDiagnostics: Infinity` (all shown as accepted in
`luna-provenance-limits.stdout.txt`). NaN makes `>` checks false, Infinity
removes a cap, and a negative idle timeout fires immediately. The same issue
applies to adapter text/input/diagnostic/error overrides. This conflicts with
the explicit bounded-IO contract (`core-runtime-loop-20260921.md:62,66` and
`app/docs/hermes-api-runs.md:77-94`).

The nearest local precedent validates unknown keys and positive safe integers
against ceilings in `app/runtime/local-pi-transport.mjs:55-69`. The Hermes
constructors need an equivalent finite, positive, ceiling-checked validation
before exposing custom limits.
