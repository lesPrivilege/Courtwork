## Primary-source mechanism review

### Hermes Agent — verified mechanism, candidate maturity

Primary documentation:

- [Hermes architecture](https://hermes-agent.nousresearch.com/docs/developer-guide/architecture) (retrieved 2026-09-27) lists CLI, Gateway and ACP entry points; an `AIAgent` core; tool dispatch; SQLite + FTS5 session storage; and multiple tool backends.
- [Gateway internals](https://hermes-agent.nousresearch.com/docs/developer-guide/gateway-internals) describes the long-running GatewayRunner, `SessionStore`, platform adapters and the message path. The documented path normalizes raw platform events to `MessageEvent`; a busy session queues a message and sets an interrupt; the runner resolves a session key, checks authorization and either dispatches a command or runs an `AIAgent` (`Message Flow` section). The same page describes allowlists/DM pairing/default deny, hooks, platform adapter lifecycle, and delivery. It explicitly says cron deliveries are not mirrored into gateway session history.
- The current public docs are not the same thing as the locally exercised binary. Courtwork’s existing `engineering/research/architecture-node-2026-09-13/explore/local-cli-inventory-20260920.md` records installed Hermes `v0.21.3 / 2026.9.14`, source `d7b836ab1c0cddaafc109ed24c9a83b6191cdc88`; the pinned upstream source report records a different source pin, `345cd2b057a452236de401d3534b8502a7465e8d`. Keep those identities separate.

**Verified mechanism:** Hermes has a plausible ingress/session/runtime substrate: platform adapter → normalized event → session resolution → queue/interrupt or agent run, with native authorization and persistence. This is a source claim supported by the official docs, not a CW integration result.

**Current evidence and maturity:** CW has one bounded Hermes/Praxis consultation receipt, installed Hermes `v0.21.3`, native session/result references, exit 0 and zero tool events. The receipt says it did not test tools, enforced permissions, resume, cancellation, CW child management, Kit admission, formal acceptance or interoperability (`engineering/research/architecture-node-2026-09-13/evidence/hermes-praxis-20260920/README.md`). Therefore classify Hermes as a **candidate runtime with broad documented primitives and an unverified CW adapter**, not as a shipped Attention runtime. No percentage is justified.

### Atlas — event-driven wake/sleep reference

- [Pinned README at `ced95138d0b4e70bdb07b6d7233dea6caec9a24e`](https://raw.githubusercontent.com/unclutter-pro/atlas/ced95138d0b4e70bdb07b6d7233dea6caec9a24e/README.md) says: external event → SQLite inbox → `.wake` file → `inotifywait` → Claude resumes; after processing, a stop hook checks whether more messages exist and otherwise sleeps. It lists cron, webhook and manual triggers.
- The public repository describes itself as a containerized autonomous agent system and gives a concrete implementation layout. The repository page currently describes a small public project; no adoption or reliability claim is inferred from stars, commits or forks.

**Verified mechanism:** durable-ish inbox plus explicit wake and sleep can avoid a resident model process. **Inference for CW:** this is compatible with “always-addressable, not necessarily always-computing.” Atlas does not prove idempotent ingestion, crash recovery, authorization, notification correctness or CW Core mapping.

### AEGIS — scheduled flows, human decisions, budget/watchdog reference

- [Pinned README at `a4b11b36cf2a148270603bdf9a1e2878d929b8ae`](https://raw.githubusercontent.com/hikmahtech/aegis/a4b11b36cf2a148270603bdf9a1e2878d929b8ae/README.md) describes a self-hosted personal project, not a multi-tenant SaaS. It documents named agents, roughly 40 Temporal workflows on schedules or triggers, a watchdog for wedged flows, decision cards with Approve/Edit/Reject, and a daily notification budget.
- The same source names Postgres/pgvector, Temporal and a LiteLLM proxy, plus an admin panel and optional Slack channel. These are AEGIS design facts; they are not Courtwork requirements.

**Verified mechanism:** scheduled/event-driven flow execution, a human decision surface, bounded proactive notifications and health monitoring can coexist. **Maturity:** source-level project reference only; its own README calls it a personal forkable working example, so it is not a standard or an independent adoption signal. It does not prove a general Attention contract.

### LangGraph interrupts — checkpoint/replay reference

- [Official interrupt docs](https://docs.langchain.com/oss/python/langgraph/interrupts) state that `interrupt()` saves graph state and waits for external input when a checkpointer is configured; `thread_id` selects the persistent cursor. The examples cover approval/rejection, human edit and resume, including interrupts inside tools.
- The same page warns that resuming restarts the node from its beginning. Side effects before an interrupt should be idempotent or moved after the interrupt; changing interrupt order can break replay. This is a concrete mechanism-level constraint for any Attention obligation wait/resume design.

**Verified mechanism:** persisted pause plus explicit resume value and replay rules. **CW mapping inference:** use these as acceptance cases for idempotent observation and human handoff. LangGraph state is not CW Attention state, disclosure, permission or formal resolution.

### Temporal Durable AI — long-lived workflow reference

- [Official Durable AI docs](https://docs.temporal.io/ai) state that Temporal Workflows resume after a crash, network timeout or multi-day human approval wait. The page positions the primitives for long-running agent loops, pipelines and internal agent platforms and links approval, entity-workflow, priority/fairness and integration patterns.

**Verified mechanism:** durable execution, timers/signals/updates/retries and explicit Worker/Task Queue primitives are available in the Temporal ecosystem. **Adoption maturity for CW:** this is a substantial platform reference, but the current Courtwork contract does not require adding Temporal. Treat it as a future option for multi-day durable work, not a dependency or an immediate architecture decision.

## Missing seams before any Hermes adoption claim

1. **Pinned transport/identity.** Choose and pin the actual Hermes surface (ACP, gateway session API, API server, or another documented protocol) and executable/source revision. The local one-shot consultation is not a managed session adapter. Capture native session, activation/turn, request and approval IDs.
2. **Host adapter boundary.** Implement only the existing Runtime Port obligations needed by a bounded consumer: describe/admit, start/continue, observe/recover where actually supported, reply/tool-result where actually supported, interrupt/cancel, dispose. Preserve unsupported operations as typed refusals.
3. **Live ingress normalization and dedupe.** Reuse the existing scripted GitHub/Gmail scenarios and their contradictory/error cases as transport fixtures, then convert platform/provider events to a Host-owned typed receipt before any Core signal. Define source identity/version/digest, event idempotency, stale/late event behavior, queue-cap drops and cross-project refusal. The missing seam is live connector registration and Hermes transport mapping, not all ingress-shaped test coverage.
4. **Attention policy.** Core currently stores an observation and human status/action contract. A Hermes runtime does not supply CW’s “new information → matter → obligation → notify → owner” semantics. Those remain a CW domain decision and must not be inferred from a tool, prompt, cron or delivery.
5. **Effect and notification settlement.** Any outbound delivery, tool call, connector write or work dispatch needs Host admission, destination scope, receipt, cancellation and unknown handling. Hermes delivery/session history is not a substitute for the existing Host/Core receipts.
6. **Recovery boundary.** Decide what “resume” means for a native Hermes session versus a CW Run. If native load or event replay is unavailable, report unsupported/unknown and preserve CW state; never silently replay a private transcript or retry an effect.
7. **Security/ownership.** Hermes profiles, credentials, native hooks, memory and platform configuration remain upstream-owned unless a separately accepted adapter contract says otherwise. A Kit, prompt, cwd or tool name is not a sandbox.
8. **Dogfooding Kit boundary.** The Kit proposal can register maps, contracts, fixtures and gates as development material. Current CW’s Kit context planner is reference-only and the Orchestra ruling says there is no Kit runtime/catalog/schema today. The parent should decide whether/where to record it; this intake does not create that structure.

## Proposed bounded acceptance cases

These are proposed evidence cases for Astra’s disposition, not a new roadmap or acceptance claim. They use synthetic transport/data first and avoid paid providers by default.

| ID | Case and pass evidence | Responsible boundary |
|---|---|---|
| HERMES-A0 | **Descriptor/admission.** A pinned Hermes revision reports protocol, native identity and capabilities. Host records a binding and rejects an unsupported operation before side effects. Version/configuration mismatch is explicit. | Runtime Adapter + Host; RD-001. |
| HERMES-A1 | **Ingress and dedupe.** Feed two identical synthetic external events and one distinct event. The adapter records one accepted source receipt per unique event, exposes an explicit duplicate outcome, and creates no Core Attention row/event without the Host’s typed action. | Adapter + Host + Core. |
| HERMES-A2 | **Project/Matter scope.** A mapped project/Attention target succeeds only when the captured Session/Run and disclosure grant permit it. Cross-project, unknown-target and malformed-hidden cases return the existing unavailable/refusal semantics with no state mutation. | Host adapter + Work Core disclosure. |
| HERMES-A3 | **Signal-only semantics.** A runtime `record_signal` changes freshness/append-only evidence but cannot set `status`, `seen`, `reason`, `next_action`, grant or resolution. Human resolve/reopen still uses the Core CAS action. | Work Core + adapter contract. |
| HERMES-A4 | **Busy queue/interrupt.** While a synthetic Attention Run is active, a second event is queued with a distinct receipt; `/stop`/interrupt is mapped to the Host cancellation request. Queue-cap drop, late output and duplicate terminal are observable and do not create duplicate effects. | Hermes adapter + Host lifecycle. |
| HERMES-A5 | **Cancellation/unknown.** Test interruption during model turn, tool admission and after a remote effect request. Host closes new admission, persists partial observations, and reports confirmed cancellation only with terminal evidence; lost acknowledgement remains unknown and is not silently retried. | Host effect/recovery owner; RD-001/RD-009. |
| HERMES-A6 | **Restart/recovery.** Stop the adapter/gateway fixture at idle, while queued, and after a request is sent but before acknowledgement. Reopen with the same native/CW identities where supported. Core Attention rows/events survive; effects are exactly once or explicitly unknown; no private transcript is treated as authority. | Host + Adapter + Core. |
| HERMES-A7 | **Human wait/resume.** A `needs_you` or `waiting` item produces a typed human handoff; resume with a changed revision fails CAS; resume with the exact request succeeds once. A LangGraph-style replay fixture must prove pre-wait side effects are idempotent. | Core actions + Host reconciliation. |
| HERMES-A8 | **Notification effect.** A destination and notification budget/policy are explicit Host input. Delivery receipt, timeout and unknown outcome are retained separately from Attention status; delivery never implies `resolve`. | Future Host effect owner; no current scheduler claim. |
| HERMES-A9 | **Native-vs-CW ownership.** Hermes native session reset/profile/hook/configuration is shown as upstream-owned and does not alter CW Core rows, grants or active Run binding. CW disconnect preserves historical references and does not uninstall or delete native data. | Runtime Settings/Host boundary; local-runtime ruling. |
