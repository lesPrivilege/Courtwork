**Disposition: adopt the overall R0 direction, with two must-adjust contract clarifications before R1.** I reviewed the fixed candidate `f1641f87451546e8f424610d0aa260201f2d518a` and compared only its new contract packet with the parent contract and current Store/service, remote-binding, CDE and K3 owners. ## Must adjust before R1

1. **Keep credential generation out of `configurationRef`.** R0 lines 20–22 hash a “credential reference/generation” into the executor factory identity; line 34 then refuses later Runs when credential generation changes. Parent separately flags this. That makes key rotation/config refresh change executor identity and risks fencing an otherwise valid Pi Session or coupling execution selection to the Provider credential lifecycle. RuntimeStore already owns Run `credentialGeneration`; the managed remote action binding already pins its connection identity/hash/version/generation; `run.provider` owns Provider/Model configuration. Preserve those checks in their owners. Define the executor factory ref from adapter revision/protocol plus only immutable executor-specific config (for example an explicitly configured transport endpoint identity, where relevant), with no credential generation, key, model/provider selection, user data path or duplicate connection hash. A matching adapter factory must not waive existing per-Run Provider/remote-binding checks. If authentication material itself changes the executor's native identity, specify the precise non-secret executor-owned identity fact and its owner instead of hashing/recreating Provider authority.

2. **Make migration's factory ref honestly unknown.** R0 line 17 says an empty schema-21 Session migrates with the “configured Pi factory's non-secret ref,” but a pure RuntimeStore migration receives persisted state, not today's composition-root factory. Line 20 similarly proposes per-read current descriptors. Migration must not inspect live config or copy today's factory into old state. For every schema-21 Session, preserve the exact historically provable adapter ID and native locator/protocol/remote binding; set the migrated choice's `configurationRef:null` where schema 21 lacks that fact, including an empty Session that defaults to the Pi adapter ID. Keep this distinguishable from a new schema-22 Session whose creation can receive the resolved default descriptor. Define the first post-migration Run transaction: it must resolve the explicit matching available factory and atomically write the Run's `bound` ref, and either materialize that ref in the Session choice under the same Store mutation or define a precise rule that treats null as legacy-unpinned only until the first new binding. State whether this normalization changes `executorChoice.revision`; stale GET/PUT and admission expectations must have one answer. The proposed “first new Run records the new ref; thereafter fixed” is directionally right but does not yet say how the Session field transitions from null, so it can conflict with same-ref checks on the next Run.

## Keep / clarify in the existing packet

- **Authority/CAS:** Session selection and Run admission belong to RuntimeStore; current availability belongs to the finite composition-root allowlist. A separate Session `executorChoice.revision` is reasonable because this is new Session-scoped intent, whereas Runtime Control's revision protects profile/Kit/configuration state. Do not reuse/duplicate the profile revision. The required command receipt-before-current-check ordering and a Store `_mutate` admission recheck are correct and should be retained.
- **First-admission race:** correct in principle: PUT and first Run admission serialize against one Session choice revision; whichever commits first governs, stale intent refuses, and no native session is opened before the winning Store admission. R1 must ensure `store.createRun` cross-checks the choice's adapter ID and any non-null configurationRef against the exact descriptor passed by service, after existing command replay lookup. The route's preflight descriptor lookup alone is not the atomic guarantee.
- **Legacy lineage derivation:** retain `run.adapterId` only when it agrees with extant native evidence. For each old nonchild Session, check Run adapter IDs against Pi `hostSession` versus Agents `session.remoteBinding.runtimeId`/Run `remoteBinding.protocol`; contradictory evidence must yield an exact readable legacy state plus refusal, never a guessed Pi mapping. Session remote bindings identify `agents-api`; the protocol/native action receipts are already validated by the existing owner and should remain unchanged. Child Runs use separate assignment/session identities; explicitly preserve their current Spark continuation path while fencing them out of the ordinary selector, so the new null-choice policy cannot accidentally become a Spark regression.
- **CDE/K3:** no duplicated root/action/receipt schema is proposed, which is correct. Preserve remote action unknown semantics and observation-only P03-D reconciliation. K3 `retainKitContext` explicitly accepts only the pinned Pi adapter/revision and rejects remote/extension/Spark Kits; the proposed zero-request refusal on managed Agents is required. `runtime.bound` stays the immutable profile/Kit snapshot; new executor identity stays a distinct Run binding. The existing profile expectation remains `{revision,profileId,sourceHash}`; adding separately named `executorExpectation` is clear.
- **Availability:** correctly do not expose Agents as production-selectable from injected loopback fixtures or its synthetic transport. Its current evidence has no live promotion; the descriptor can report it unavailable with a reason. `pi-local-print` remains a Spark child, not a selectable ordinary Session executor.
- **Schema:** schema 21→22, exact backup, old-reader refusal, and unchanged Core4/bridge5 are appropriately proposals, not product authorization. The migration must preserve all schema-21 bytes/semantics except typed legacy annotations and must not rewrite the CDE/K3 records. The listed 8 offline cases fit parent R0; retain a separate live-availability gate.

The parent’s additional critique is valid and matches this review: configuration reference ownership must not duplicate credential generation, and migration cannot invent the current factory ref. No other material contradiction with the current native-binding, CDE or K3 owners was found in the bounded scope.
