## Decisions

Attention is a B0 domain within the existing WorkCoreOwner worker and SQLite database. Current state, audit events and request receipts commit in one transaction. It does not reuse Matter decision audit rows that require a Matter. Its own domain tables remain under the same owner. `app_run.matter_id` stays non-null; many-to-many Matter references and immutable execution references are stored with Attention. Ending/deleting an execution never changes its status.

The migration target is Core3/app4, leaving RuntimeStore4 unchanged. Validate complete Core2/app3 before creating an exclusive `.pre-attention-core-v3-app-v4.bak`; install Attention DDL and version markers atomically. Existing Core1/app1/app2 migration remains supported through the established file migration followed by Attention migration. Reject mismatched version pairs, malformed current tables and existing backup paths. Old Core2 hosts must refuse Core3. Restore only into a separate directory using the corresponding old host. Synthetic copies only.

Attention schema1 has stable id, project scope, revision, descriptor, status, freshness, reason, next action, source references, relation references, seen, policy and last event metadata. Status is investigating/needs_you/waiting/later/resolved. Sources retain exact version and locator; external references are unknown and never dereferenced. Core source references must belong to a Matter in the same project. Session and Runtime Run references are checked by the host on attachment and retain their observed provenance after deletion; they do not assert continued availability.

The local human API uses the authenticated host actor and an existing project selector. The selector is not a cross-user ACL. Runtime consumers receive a captured host context derived from an actual Session/Run, never actor/scope supplied by model arguments. Core enforces project isolation for every read, query, receipt and write, before existence, descriptor, counts or conflicts are exposed. Human access within the selected local project is full. Runtime access is denied by default and requires an explicit object-specific disclosure grant, limited by purpose, fields and expiry, with revocation. A registry grant alone does not permit details, source or event reads, grep or relation filtering on hidden fields.

Typed actions are version1 create, acknowledge, snooze, set_waiting, resume, resolve, reopen, attach_relation, request_disclosure and record_signal. Human resolve requires an explicit reason. Signals are only recorded under the separate authorized signal capability and never change status or grant authority. Seen is separate from resolution. Snooze records a condition; no timer runs. Unsupported actions, schemas and payload fields fail closed. Request id binds actor context, object, expected revision, action and full payload; exact replay returns the committed receipt and changed replay conflicts. A scoped request query reconciles lost acknowledgements.

Queries are typed inspect, registry, exact, bounded literal grep, relation, events, source and receipt. All are bounded and disclose only policy-visible fields; no semantic index or model search is introduced. Results carry schema/revision, disclosure and pagination/truncation metadata. Unknown object schemas are refused, not interpreted as current.
