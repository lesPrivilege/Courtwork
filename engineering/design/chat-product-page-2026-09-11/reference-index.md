1. **App:** design a complete peer Chat page with real existing navigation/session return behavior; use a clearly labelled planning/preview empty state if backend identity, provider, memory, capture or handoff is absent. Do not rename a normal coding session, invent history, or add disabled fake controls. App design is a frontend reservation and needs later capability contracts.
2. **Pages:** design a separate product showcase and, when implemented, an independent `chat.html` using the existing product-pages shell/nav/build/manifest. No `spark.html` or `attention.html` currently exists; same-level means product reason, visual quality and entry position, not route symmetry. Mark samples as samples; do not list cross-provider Chat/Memory as shipped.
3. **Order:** reuse local grammar → consume v3 ruling/ChatSpace+ChatActions members → compare v2 corrections → consult original 19-board package only for provenance/alternatives → produce App wide/narrow light/dark plus Pages showcase → record adopt/adapt/reject/defer, source hashes, exact capability gaps and independent verification.
