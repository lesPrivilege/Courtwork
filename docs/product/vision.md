# 产品定位

状态：现行定本（2026-08-18 修订）

## 一句话定位

Courtwork 当下阶段定位为**与垂类解耦的本地优先通用 Work Agent GUI**：以案件或工作区为容器，
把受控文件读写、模型 loop、人工授权、可审计账本和结构化产出组织成一条个人可维护的工作链；
Legal、PM 及后续专业场景以可加载垂类包作加法，不定义产品本体。

这是产品方向，不是成熟度偷跑。只有薄 Pi harness 的受控读写、续行和基础 GUI 经
`PI-BASE-GUI-ACCEPT` 独立放行后，产品才可用现在时声称 agent 能力已经成立；合同审查窄链、
generic 场景、scripted E2E 或 build 全绿都不能顶替该门。Work Agent 从 coding agent 做减法：
不提供 shell、edit/delete/rename、planner、subagent、skills、MCP、git/package manager 或自主不可逆
动作，只保留有明确工作价值且能由宿主 fail-closed 的最小能力。

垂类细分场景的颗粒度远超个人维护上限。Courtwork 维护的是通用 GUI、容器、授权、账本、受控
工具和包 ABI；具体垂类 schema、场景、词表、评测与专业门禁应由对应领域团队或生态维护。模型
能力会快速折旧，Courtwork 的长期价值仍是秩序——字段、来源、授权、修正与留痕。

## 用户与问题

首要用户是需要在本地文件上持续完成研究、整理、起草与交付的个人知识工作者；律师与法务是
第一条经过真实材料约束的滩头用户，而不是通用 GUI 的唯一用户。他们面对的核心问题不是
“模型会不会写”，而是：

- 文件分散，案件上下文难以连续；
- 结论与原文脱节，复核成本高；
- 自动化容易越权或静默降级；
- 产出无法直接进入 Word/WPS 工作流；
- 团队判断不能沉淀成稳定、可复用、可审计的形状。

## 产品形态

- `work`：通用 agent 主体。授权容器后以 Pi loop 读 `/case`、在 `/workspace` 写工作稿，所有 effect 先经宿主授权并进入独立 journal。
- `chat`：轻量单一对话画布，用于不值得建容器的任务；通过“存入”升格为容器。
- `scenes`：结构化快捷流。generic 基线场景随产品提供，垂类场景随包加载；它们可缺席或替换，不能成为 agent 主入口。
- 场景由用户显式触发或由系统推荐，模型不得自行决定执行不可逆流程。
- 所有结构化结论都可回到原文锚点；所有修正都成为事件；所有正式产出都经过确认或定稿仪式。

## 滩头选择

Legal 是第一条生产垂类和约束压力测试：它必须用真实材料证明“原件 → 引语 → 系统锚点 →
结构化结论 → 人工决定 → docx”整链，而不是以 demo 穿越替代产品证据。它验证包 ABI 和秩序，
不再承担产品身份；卸载 Legal 后，通用 Work Agent GUI 仍须成立。

为什么以 legal 切入，四条结构性理由：

1. **最符合人们对垂类的想象**——法律是公认最需要严谨的场景，可信秩序在此处的价值不需要解释；
2. **推理纯文本**——不依赖多模态与实时数据，所有字段可泛化，锚点 substrate 最成熟（文档坐标）；
3. **不依赖企业私有场景**——轻量包即可自足，接口与校验天然多源分级（法条/判例/工商，官方源与 web 线索分层），重度包留给真实驻场需求；
4. **文件级最单纯**——一套卷宗/项目材料就是完整容器，摄取、锚定、产出的链路闭合在文件层。

泛化不靠个人维护者继续枚举 Legal 长尾。一次企业活动会自然引入财务、招投标、产品等材料；
对应能力只有在真实维护者与评测责任人出现后才进入独立垂类包。没有相应包时，通用 agent 仍能
处理受控文件任务，并诚实缺席专业 schema 与裁决。

## 命名叙事

Courtwork 的命名承载定位：court 昭示法律垂类——最需要严谨的场景；比 cowork 多出的 urt，读作 **you are there**——用户始终在场。这是真正的协作者工具叙事，不是自主探索代理，也不是数字员工：human in the loop 是产品承诺而非限制，员工不会被取代，判断权始终在人。这与产业用户的真实期待一致。

PM 是第二垂类的 ABI 证明：先用 schema、presentation 与 catalog 验证通用底座不依赖法律语义；真实需求、确定性计算与迁移边界成立后才创建 scenario，不能用空工作流证明泛化。

PM 垂类的现行字段与交互边界见 [PM 垂类契约](pm-vertical.md)。

以下六条是 Stage 0 的 **MVP 退出标准**，不是当前能力清单。衡量标准不是场景数量，而是一个真实材料能否走完：

1. 安全摄取并生成阅读视图；
2. 模型按场景声明推理；
3. 系统为引语铸造坐标并拒收歧义；
4. 产出通过 schema 与确认门禁；
5. 用户修正被记录并投影到续行上下文；
6. 正式文书可安全编译或修订为 docx。

后续阶段只按证据条件触发，见[产品路线图](roadmap.md)；实际成熟度、阶段和阻断只认[当前基线](../status/current.md)。

## 长期资产

- 领域 schema 与渲染词表；
- 场景声明、专业门禁和确定性接口；
- 脱敏评测集与回归基线；
- 来源解析、实体对齐、文书著录和 WPS 兼容能力；
- 经真实使用确认的 RevisionEvent 与专业判断数据。

## 明确不做

- 不把通用 Work Agent 做成无容器、无授权、可自主行动的 chatbot；
- 不以模型自证代替确定性校验；
- 不让 web 线索冒充已核验事实；
- 不自动执行不可逆动作；
- 不编辑用户上传的原件；
- 不把案件内容用于训练；
- 不在没有真实数据管线时用占位内容制造“高级感”；
- 不因平台可泛化就提前做平台市场。

## 路线原则

先把通用 Work Agent GUI 的真实 Tauri 读写闭环与入口做实，再由 Legal 等垂类包证明 ABI；先做能
触红的契约和验证器，再扩场景。垂类数量不再是通用底座的完成条件；只有真实数据撞上性能或
上下文边界时，才引入 sandbox 重构、context 修剪或更重的 agent 编排。

当前阶段首先作为面向外界的作品，而不是成熟产品发布。基本功能完整与 UI 观感／品味并重：先以
一条真实可解释的 Work 纵切供给全部必要状态，再把这条纵切做到足以展示；不得以“功能尚未终局”
为由长期推迟视觉工艺，也不得以漂亮空壳顶替授权、账本、决定和工作稿闭环。

UI 心智面向成熟 agent 产品对齐（对标 Pi/Cowork/Codex/OpenWork/Lody 一类，只做减法）：控件面
不是长期竞争轴，matter 容器、材料根、逐次授权、可审计账本与工作稿秩序才是 Courtwork 的差异。
展示期的 primary chrome 只呈现已接线能力；未接线控件从主路径隐藏，只能在显式 roadmap/preview
语境出现，不以 disabled/coming-soon 占位制造“未来已经在场”的假成熟。目标不卷 coding agent，
只做 work agent 的下沉。
