- **D6 finding:** A local actor can move the exact admitted/opened `workspace/out` directory outside the workspace immediately before the helper's descriptor-relative commit rename. `ws_write` then reports success for `out/memo.md`, although the bytes are published in that moved admitted directory outside the workspace path. This is a false workspace-path success after relocation of the admitted directory; the probe did **not** redirect bytes into an unrelated pre-existing outside file. A synthetic outside control file remained unchanged.
- **Reproduction:** [Portable harness](write-move-probe.mjs), [captured before output](write-move-before.json). The harness imports `workspace-tools.mjs` from the supplied checkout and creates/removes only temporary synthetic files. The parent reviewer independently reproduced the original temporary script, then made this portable copy. The default assertions expect the defect and must not be interpreted as fixed-behavior acceptance.
- **Code boundary:** `app/runtime/repository-fs-helper.py` `commit_workspace_write` checks the opened parent descriptor against the staged parent identity before `os.rename`, but does not check parent currentness after rename. The `ws_write_commit` operation returns directly from `run_workspace_file_operation` and does not perform `verify_bound_root` after commit. A descriptor-relative rename binds the mutation to that exact directory inode; moving that directory carries the publication with it. The evidence does not show writes through an unrelated symlink or arbitrary selection of an outside file by pathname. A guarantee against same-user relocation would require a stronger OS boundary; otherwise the confinement claim must state this limit.
- **Overall disposition:** Keep D6 open for the stated local-relocation boundary or record an explicitly bounded contract. These results do not accept the architecture delivery or establish combined integration behavior.
