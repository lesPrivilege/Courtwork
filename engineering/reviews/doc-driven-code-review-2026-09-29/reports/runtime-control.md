## 2. Findings by severity

### F1 (Medium) Advisory permission endpoint disagrees with inspector/dispatch for non-`ws_write` tools
- service.mjs:1027 `const ceiling = descriptor.id === 'tool:ws_write' ? … : 'allow'` bypasses `hostToolCeiling` (control-plane.mjs:31-39), used by `inspect` (control-plane.mjs:245) and `governTools` (control-tools.mjs:108).
- Probe D (real HTTP, session `permissionMode:'ask'`): snapshot `tool:spark_explore` effect = `ask`; `POST /runtime-permissions/evaluate {resourceId:'tool:spark_explore'}` returns `allow`. Same divergence for `check_run` (always ask/deny in read_only), `repo_write` (deny in read_only), `message_other_agent`.
- Failure scenario: Settings' on-demand "evaluate" (web/runtime-view.mjs:599) tells the operator "allow" for a tool that will actually prompt or be denied. It is advisory, not a grant, but contradicts architecture.md:41 and the API table. The only test uses ws_read/ws_write (control-plane.test.mjs:102).
- Fix direction: call `hostToolCeiling(descriptor.action, mode)` in evaluateRuntimePermission; add test for `check_run`/`spark_explore`.

### F2 (Low-Medium) Selecting a narrower-scope profile at a wider scope breaks other Sessions (fail-closed, not escalation)
- control-plane.mjs:155-159 validates only that the profile is visible to the *requesting* session, not that its owning scope covers the selection scope.
- Probe A (real HTTP): workspace-scoped profile in project A; `operation:'profile'` at scope `user/local` succeeds (200). Session in project B then has `composition.status:"incompatible", missing:["local:narrow"]` and `POST /runs` → `409 profile_incompatible`.
- Impact: one API call blocks new Runs in every other project until reset. No permission gain. Frontend only selects at Session scope, so exposure is API-level. Undocumented; architecture.md:11 says only that selection is separate from exposure.

### F3 (Low) Test-title / coverage overclaims
- manual-compaction.test.mjs:181 "cancel and deadline settle without a partial summary": only user-cancel and restart are exercised; the `deadline` branch (service.mjs:910) and `too_small` mapping (pi-session-runtime.mjs:451) have no test. commands.test.mjs:184 accepts `completed` or `failed` for `/compact`.
- kit-run-binding.test.mjs:42 claims "intended context position" (kit-run-binding.md §K3-B) but only counts occurrences in the concatenated wire text; no role/order assertion relative to extension/async/Spark context.
- kit-run-binding.test.mjs:226 "Kit projection preserves the bound available Extension tool" calls `control.inspect` with synthetic extensions, not a Host Run; extension-bound Kit Runs are refused by design (kit-run-context.mjs:19), so the test does not exercise a user path.
- Kit Run-admission refusals for Global Attention, extension-bound and Spark child sessions (kit-run-context.mjs:19-21) are code-only; only preview refusals are tested.
- Profile v2 source bounds (K10), `kit_payload_budget`, `profile_uneditable`, Kit + compaction reassertion are untested.

### F4 (Low) Browser-side command contract verified only by source regex
- command-surface.test.mjs:34 asserts strings in web/app.mjs. "Refusals keep the draft / handled commands clear it" has no behavioral browser or DOM test of `sendMessage`. Attention composer path posts Runs directly (attention-conversation.mjs:79) — slash text there is sent to the model; not stated as out of scope.

### F5 (Low) MCP JSON-RPC errors are classed as effect-unknown
- mcp-manager.mjs:129-132: any `callTool` rejection (including a well-formed JSON-RPC error response, e.g. unknown tool / invalid params) → `result-unavailable` fence + Run `unknown`. architecture.md:31 says "known error results are failures; ambiguous call transport failures mark the Run unknown". Conservative but the doc split is not what the code distinguishes (tests: hpr_p02b.test.mjs:118 covers output-schema rejection as effect-unknown, so this may be deliberate; doc ambiguity).

### F6 (Info) Dead-store path
- compactSession replays by requestId *before* the store's `IDEMPOTENCY_CONFLICT` check (service.mjs:865 vs :884): same requestId with different `focus` silently returns the old record instead of 409 (docs only promise "same requestId replays the same record").
