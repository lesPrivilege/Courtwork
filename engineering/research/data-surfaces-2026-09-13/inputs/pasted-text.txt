**应当裁定，而且这轮应从“成熟系统有哪些可借鉴机制”，推进到“用户怎样使用这些机制”。** 建议明确采用：

> **资料以列表进入，工作以纲要组织，正文优先阅读，版本通过对比判断，图谱按具体问题展开；效力、权限、依据与优先级分别管理。**

前后端共同实现这些使用路径，而不是后端先暴露一套庞大的数据模型，再让前端把每个字段、关系和状态都摆出来。

已整理为可供本地消费的文稿，包含成熟谱系映射、页面与 owner 合同、版本与权重设计、实施顺序和验收场景：

**[完整裁定稿](sandbox:/mnt/data/CourtWork-data-surfaces-version-priority-2026-09-12.md)** · **[专题文档与交接包](sandbox:/mnt/data/CourtWork-data-surfaces-2026-09-12.zip)**

## 一、先确定：治理要深，日常使用不必深

你提供的附件已经建议把 Graph／Lineage 放在较深层，先回答“有什么、谁产生的、是否为正式版本”。这部分值得保留。另一方面，附件中的统一 Resource Fabric、四级 Promotion 等较宽设想，应按已入库 RD-007 收敛：**使用现有 owner 上的有界资源治理，保留、共享与正式接受分别处理，不重新建设一个统一权威中心。**

这也符合当前工程采用的 SE 9.6：总工作容量可以增长，但一次运行和一次人类判断面对的 working set 不应随之无限扩大；Human Work Surface 与 Agent Context 都是受治理工作对象的任务化投影。

因此，**“舒朗”不是把信息删除，而是把信息放到它被需要的位置。** 用户不必理解 Blob、索引 generation、协议日志和授权修订号，才能找到一份材料；但在判断来源和版本时，这些依据又应能够被追溯。

## 二、前端采用五种任务视图，不做五个独立工作台

| 用户正在解决的问题        | 默认呈现                    | 按需展开            |
| ---------------- | ----------------------- | --------------- |
| **有哪些材料，在哪里继续？** | 当前范围内的资料列表、工作纲要         | 筛选、集合、来源详情      |
| **这项判断依据什么？**    | 正文与引用                   | 精确原文、版本、范围、检查依据 |
| **新旧版本改变了什么？**   | 版本记录与对比                 | 变更原因、采用历史、受影响工作 |
| **这份资料影响了哪些东西？** | 上游来源／下游使用处清单            | 只读局部图谱          |
| **现在需要我决定什么？**   | 工作纲要中的待判断项、Attention 投影 | 证据、差异、真实可用动作    |

这些视图应共享稳定对象引用和读取合同，而不是各自维护一套资料、状态或待办。

### 纲要要分成“材料纲要”和“工作纲要”

**材料纲要**是目录、标题和原文锚点，回答“去哪里读”。它绑定当前阅读表示的版本，可以从原文重建。

**工作纲要**是任务、来源、候选、有效决定、缺口与未完义务，回答“工作到哪里”。每个条目都要能回到真实 owner，不能由模型生成的一段摘要取代。

例如：

```text
当前工作
  资料与依据
  正在形成的结果
  需要判断的事项
  已采用的结论
```

这是可能的视图分组，不是新的四态状态机；具体工作没有某类对象，就不必显示该组。用户手工编辑的纲要、顺序和分组也应保存为明确的视图资产，不能一概归为“随时可删的缓存”。

CMMN 的价值正在这里：它区分当前可用、等待手动激活的工作，与已经执行的工作；不必提前把知识工作写成一条固定流水线。CW 可以消费这种任务语义，但不必继承完整建模器和引擎。([Flowable][1])

### 图谱先服务于“出处”和“影响”

建议先区分四种图：

**内容关系图**展示引用、派生、支持、反对及版本关系；**处理 lineage**解释某次解析、抽取产生了什么；**执行编排图**表达运行依赖与触发；**概念联想图**表达主题相似或模型建议。

它们不能默认混在一张画布里。特别是：

> **有关联，不等于可以执行；一起出现，不等于存在因果；模型建议有关，不等于已经形成证据关系。**

首个图谱只做当前对象的有限邻域，先提供上游／下游清单，需要理解多跳关系时再展开图。Obsidian 的 local graph 已提供“围绕当前对象、控制展开深度”的成熟先例；我们借的是局部探索方式，不是全库节点云。([Obsidian Help][2])

图中每条重要关系应有类型、方向、端点版本和记录依据。来源版本改变时，旧边不能悄悄连接到新版；推断关系不能使用与正式记录完全相同的表达。首片拖动只调整布局，**不通过拖线改变工作依赖、权限或正式状态。**

## 三、前后端编排：共享事实，分开查询、呈现与变更

建议采用的逻辑路径是：

```text
现有对象与状态 owner
    → 获准 reader
    → 有界的任务查询／投影
    → 列表、纲要、阅读、版本、局部图

用户或 Agent 提出变化
    → 对应 owner 的明确命令
    → 版本／权限／约束检查
    → 持久回执
    → 更新投影
```

这只是职责拆分，不要求新建微服务或另一份主数据库。

### 后端负责“哪些事实成立、当前能做什么”

来源、版本、采用关系、授权、未完义务、实际执行回执，继续由原 owner 提供。查询组合器可以为页面组织这些事实，但不能在缺失时补造。

一个页面响应至少需要表达：**正在看哪个对象和版本、可读范围、部分或缺失、查询时点，以及真实动作的适用性。** 多个 owner 的读取不天然是一份原子快照，应保留各自版本和必要的时点说明；不能因为前端把它们画成一张卡，就声称它们同时成立。

图谱、搜索和纲要也必须在后端约束披露。标题、关系、计数、缓存和游标都可能暴露信息，不能把全量数据发到浏览器后再隐藏。现 RD-007 已明确这些边界。

### 前端负责“怎样判断和继续”，不负责制造状态

选择、展开、滚动、布局和临时草稿属于界面状态。保存集合顺序或个人偏好，可以有对应 owner，但不因此改变来源权限和工作效力。

采用、撤回、关联 Matter、调整共享工作优先级，则提交明确命令。预览后发生版本变化或撤权，正式动作需要重新检查，不能沿用一张过期页面的可用按钮。

DataHub 的 Aspect 确实提供了独立演化、独立更新的先例。但在 CW 中，**facet 可以独立，业务不变量不能被拆散**：同一个正式决定要求同时更新的事件、状态和 active reference，仍应由原事务边界维护。([docs.datahub.com][3])

### 不为图谱更换整套技术栈

首片继续复用现有原生 DOM、Markdown、controls、tokens 和 reader。局部图确有使用价值后，再选 renderer／layout。

Cytoscape.js 提供原生 JavaScript、ES modules、JSON 数据和独立布局机制，可以成为后续候选；ELK 可以作为分层布局候选，避免图持续漂移。它们都不要求 CW 同时迁移到图数据库或可编辑 workflow canvas。具体版本、依赖、许可和性能仍需单独核验。([js.cytoscape.org][4])

## 四、版本管理要让人理解“现在用哪一份”，而不是展示版本技术

最重要的不是先加入 branch、commit 和 merge 按钮，而是区分三个事实：

**最新保留的版本、本工作当前采用的版本、本次正在查看的版本。**

例如：

> 正在查看 r3。本工作仍采用 r2；r3 的适用性待检查。

对于尚未进入正式工作的资料，只显示保留和查看版本，不编造“已采用”。

### 至少分开四类变化

| 变化                            | 应记录什么              | 不应自动发生什么        |
| ----------------------------- | ------------------ | --------------- |
| **来源内容改变**                    | 新内容 revision、来源和时间 | 不改旧引用或旧 Run     |
| **描述或表示改变**                   | 标签／集合／解析器／阅读表示的修订  | 不伪称原文被改写        |
| **工作采用关系改变**                  | 谁依据哪个版本作了什么决定      | 不等同“最新文件覆盖旧文件”  |
| **Schema、policy、compiler 改变** | 新规则版本及适用范围         | 不按当前规则重写历史输入与解释 |

因此，版本对比也有两层：**原文究竟变了什么，以及这次变化对当前工作意味着什么。** 前者优先确定性比较；后者可以由 Spark／Expert 提出判断，但保留引用、范围和未知项。

dbt 将 definition、最近一次运行尝试和上次成功应用状态分开；Dagster 明确 observation 不等于资产已被修改。这些机制值得借鉴，不过 CW 还需要额外保留专业接受：**运行成功和观察到变化，都不自动产生正式效力。** ([dbt Developer Hub][5])

### 恢复旧版是一条新决定，不是擦除历史

“重新采用 r1”应在当前权限和适用性检查下形成新回执，可以重新引用旧 bytes，但不删去 r2、r3 和中间决定，也不能撤销已经发生的外部效果。

只有真实任务需要并行候选比较时，再增加分支／候选集。lakeFS 的不可变版本与可变引用可作为底层原则，但普通用户不必先掌握 Git 操作才能使用资料。([lakeFS Documentation][6])

## 五、权重管理应当存在，但不能只有一个“重要性分数”

**这里最需要避免的，是把来源可信度、工作优先级、检索相关性、正式效力和视觉强调压成一个 `weight`。**

建议明确以下分工。这是本轮实施建议，不是把一个新增权重模型冒称为 SE 已冻结的字段规范。

| 维度                   | 能影响什么         | 合适的用户表达                |
| -------------------- | ------------- | ---------------------- |
| **正式效力与权限**          | 哪个决定有效、哪些动作合法 | 已采用、候选、撤回、权限限制；改变走对应命令 |
| **依据质量**             | 如何理解来源、检查与覆盖  | “依据与检查”，展开出处、方法和缺口     |
| **模型置信／评估结果**        | 候选需要怎样检查或升级   | 有方法、版本和任务范围时才展示；未知保持未知 |
| **人的工作优先级**          | 获准工作中的处理顺序    | 优先处理、常规等明确意图           |
| **本次检索／Context 优先级** | 合法候选中的排序和预算分配 | 本次优先参考、本次不作为参考、恢复自动    |
| **个人收藏与视觉强调**        | 导航与个人关注       | 收藏、关注；不暗改前五项           |

**同一个“置顶”，不能既表示个人喜欢，又提升团队任务优先级，还强制进入所有模型上下文。** 首版应让一次操作只改变一个清楚的维度。

### 选择过程应是“先资格，后排序”

```text
身份、授权、目的与版本检查
    → 保证本任务必需的决定、限制、义务与冲突可见
    → 对其余合法候选按相关性、依据和用户偏好排序
    → 按预算编译
    → 记录选择、遗漏及实际披露
```

高分不能补足权限；低分不能掩盖任务的强制限制。必需信息无法放入预算时，应明确要求缩小任务或调整输入，而不是悄悄删掉后仍显示“上下文已完整准备”。

也不宜统一采用“越旧权重越低”。稳定规则、已接受结论、临时运行记录和新发现有不同的时效机制；**新鲜不等于有效，频繁被引用也不等于更可信。**

### 前端先提供可解释操作，不提供一排伪精确滑块

用户更需要看到：

> 因当前工作引用而纳入。
> 因来源版本变化，需要重新检查。
> 因本次选择，优先作为参考。

而不是不知道含义的 `0.83`、`0.67`。

这些设置默认影响下一次准备，不无声改变活动 Run。历史输入不按新权重重算；“本次优先参考”也不保证上游模型实际给予了某种 attention，更不是修改模型权重。

一个合成反例足以检验这条边界：**r1 已被采用，r2 新到且被用户提高参考优先级。下一次可以优先读取 r2，但必须继续说明当前工作依据 r1、r2 尚未被正式采用。**

## 六、“呵护人类注意力”要写成行为合同

W3C 的认知可访问性材料明确支持减少无关内容、控制打扰，以及通过标题和导航线索帮助用户恢复位置。对 CW，应把这些原则落实到可观察行为，而不是仅增加留白。([W3C][7])

**阅读占主列。** 导航和纲要可以退后，Inspector 按需展开。不要同时常驻等宽的资料列表、正文、关系图、详情和 composer。

**重要事实就地出现，工程细节后置。** 标题、出处、当前版本和真实待判断状态在主路径；hash、grant ID、索引批次、完整 trace 进入详情。舒朗不靠浅到难读的文字或极小字号实现。

**更新不抢位置。** 用户阅读期间，不自动切到新版本、不重新排列列表、不移动选中的图节点、不突然展开详情。普通更新合并成可检查提示；但即将提交的动作已经失效时，应立即说明并拒绝旧动作，不能为安静而隐藏阻断。

**Agent 不逐步打扰。** 每次解析、工具调用和索引完成不各发一个 toast。普通后台工作保持在活动详情，只有实际需要人的决定或发生阻断，才进入相应待判断位置。

**返回之后能继续。** 从引用进入详情、从详情进入关系，再返回时，保留阅读锚点、合理焦点、展开状态和草稿。宽屏与窄屏可以使用不同布局，但不能丢失这条连续性。

**不用图也能完成核心任务。** 关系清单应能完成相同的读取和跳转，不能把来源与影响信息只放在画布上。

相应验收可以直接记录：找到正确采用版本的时间、误把候选当已接受的次数、返回后丢失阅读位置的次数、识别版本影响的正确性，以及被迫关闭干扰面的数量。先与现有列表／Inspector 比较，不虚构通用的“几秒、几次点击”标准。

## 七、下一轮按小场景推进，而不是先完成治理平台

现 RG-FE-01 已规划列表与 Inspector，RG-FE-03 已规划检索与版本注释，并明确不首发大图。此次应细化这些入口，而不是另开一条同义实现线。

建议顺序如下：

| 阶段            | 前端与使用交付                              | 后端配合                        |
| ------------- | ------------------------------------ | --------------------------- |
| **第一片：找到并引用** | 资料列表、工作纲要、精确阅读与返回                    | 保留来源、稳定版本、获准 reader、真实关系    |
| **第二片：比较并判断** | 新旧版本、当前采用、引用及冲突反馈                    | 版本／表示区分、采用关系、变更与并发合同        |
| **第三片：选择与准备** | 一种明确的工作优先级或本次参考偏好，附解释                | 对应 owner、scope、策略修订、编译与预算证据 |
| **第四片：理解影响**  | 影响清单；必要时局部图                          | 类型化关系、精确版本、覆盖与权限            |
| **小闭环：继续工作**  | Spark 准备变化，Attention 呈现待判断，Expert 复核 | 原工作 owner 保有接受与关闭权          |

首轮 specimen 可以只围绕三个合成任务：**找到一份已采用材料并引用；比较新旧版本且遇到并发变化；提高新来源的参考优先级后检查受影响工作。** 每个场景同时包含缺件、拒绝或失效，不只画成功态。

这套数据工作面可以与 Harness 主线并行准备，但图谱、全部权重控制和完整治理功能，不应成为首个真实 GUI Agent 的新增前置。共享 service、store、Core 和迁移仍由原 owner 串行接收。

本轮交接包保留了上传原件，完成了文件完整性与内部链接校验；**没有修改仓库、绘制或验收生产 UI，也没有运行产品测试。**

**最终要交付的不是“用户看得懂数据治理架构”，而是“用户容易找到材料、知道正在依据哪一版、清楚哪里需要决定，并能放心离开后再接着工作”。图谱、版本和权重都应服务于这件事。**
