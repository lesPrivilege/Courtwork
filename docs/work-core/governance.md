# Governed object directory and Matter disclosure v1 · BG-01

Astra implementation contract, 2026-09-10; base `6921dbd` (Core3/app4, Runtime7). The new persistence boundary is Core4/app5; Runtime7 is unchanged. The [recognition and exploration](../../engineering/execution/2026-09-10-backend-governance/README.md) explains the consumer and source mapping. This document specifies BG-01, not Run attempts, scheduling or external effects.

## Authority and identity

WorkCore remains the single SQLite owner. Matter/domain/current sources/accepted Artifact stay in their existing tables. Three new tables store only Matter disclosure policy, append-only policy events and immutable request receipts. There is no registry state table, search cache, new model loop or implicit Expert delegation. Directory entries are rebuilt directly from their owners.

Object refs are `{project_id,kind,id}`, with kind `matter|attention`. Matter IDs remain globally unique in the existing Core; Attention IDs remain project-composite. The ref does not change either primary key. Human HTTP access uses the authenticated local host, validated project and purpose `human-governance`. This is the existing local human trust boundary, not a multi-user ACL. Runtime context is host-captured `{actor:'runtime',project_id,purpose:'attention-runtime',execution:{adapter_id,session_id,run_id}}`. The global Attention may explicitly select a project; a project Session cannot select another project. Every runtime call checks actual retained Session/Run ownership and open admission. Payloads cannot set actor or execution.

Matter defaults to undisclosed. A human may replace or revoke one object-specific grant for one runtime adapter and purpose. Fields are `registry|details|sources|artifacts`, unique and including registry. `content_scope:'current'` explicitly permits future current content until expiry, replacement or revocation. It does not permit arbitrary historical sources or candidates. Grant creation binds the human-observed object version to prevent a stale policy editor approving a different object snapshot. An exact replay returns its historical receipt without restoring a revoked grant.

Policy revision is independent of Matter version and source revision. The immutable policy event records the issued object version; later content changes do not change policy revision or extend expiry. Every read checks current policy. Every multi-step object read also carries the `object_version` observed from the directory/inspect. This version hashes the reader's permitted view plus policy revision; it is a consistency check, not authority. Hidden fields do not enter the reader's hash. A content or policy change affecting that view requires rediscovery. Returned data is authorized at the query's SQLite read snapshot; revocation cannot erase data already delivered to a caller.

## Human action and recovery

`POST /api/v5/governance/matters/:id/disclosure` takes exactly `{projectId,request}`. Request is `{schema_version:1,request_id,matter_id,expected_policy_revision,expected_object_version,grant}`; grant is null (revoke) or `{adapter_id,purpose:'attention-runtime',fields,expires_at,content_scope:'current'}`. Expiry must be timezone-qualified and future. The path must match matter_id. For a new grant, the human obtains current policy and object version through inspect. Revocation requires expected_object_version=null and only policy CAS; human query kind `policy` reads scope+policy without loading domain/source data, so over-budget or unreadable content cannot prevent revocation. Human query kind `policy_request` reconciles an exact request identity within the project/Matter.

A mutation checks scope before receipts/existence, then full request identity and CAS. Successful writes commit one policy revision, event and receipt in the same SQLite transaction. Changed request replay conflicts; failed CAS writes nothing. Replaying a committed grant after expiry/revocation returns the old receipt, not a new grant. Runtime cannot call this mutation. A policy receipt never permits Matter acceptance, external effects or tool execution.

## Discovery and bounded reads

`POST /api/v5/governance/query` takes exactly `{projectId,query}`. Private runtime adapters call the same Core query with their captured context. Every query contains `schema_version:1,kind`; unsupported fields/versions fail closed.

- `registry`: optional `object_kind`, `text` (literal case-sensitive title filter), `offset`, `limit`, `expected_collection_version`. Sorting is kind then ID. Counts, collection hashes and offsets concern visible matching entries only. Offset > 0 requires the previous collection version; concurrent visible changes refuse continuation instead of silently shifting pages. Page size 1–50; at most128 current source descriptors per Matter and128KiB per permitted view/page; at most1000 visible objects of each kind, with an explicit capacity error. This does not claim large-scale query latency.
- `inspect`: `object_ref`, optional `expected_object_version`. Returns only granted typed fields and source/Artifact descriptors. Matter supported contracts are current evidence memo, inbound NDA and file memo; unknown contracts retain minimal registry metadata and refuse decoded detail/evidence. No draft, pending Candidate, full Run history or human action payload enters runtime context.
- `source`: `object_ref`, `expected_object_version`, `source_ref` (descriptor key), optional offset/limit. Reads a current permitted source's exact bytes, checks digest, then returns up to4000 Unicode code points. Attention sources additionally require the existing Attention sources grant; Core source refs only enter this new directory when the target Matter is disclosed for sources and that exact source is current there. External refs remain unknown and are not fetched.
- `artifact`: Matter object_ref, expected_object_version, optional offset/limit/path. Reads only the currently accepted Artifact. Plaintext is paged in code points; a file Artifact without path returns an existing bounded file manifest (up to16), and with path returns the existing exact file reader. Unknown formats refuse. No new acceptance or byte store.
- `policy`: human only, Matter object_ref; returns the current disclosure policy/revision without domain or source reads.
- `policy_request`: human only, object_ref of kind matter and request_id; returns a scoped historical receipt or null.

Directory entries carry registry_version, object_ref, schema_ref/schema_version, object_revision, object_version, descriptor, state_class, updated_at, availability and disclosure_handle. Matter has no reliable general update timestamp or universal lifecycle: updated_at is null and state_class unknown. Attention preserves its domain status/time. The disclosure handle identifies policy/version and is never a bearer capability. Source/reference descriptors and details are separate permissions. Descriptor availability `retained` means a stored record was found; `integrity:unchecked` explicitly withholds byte verification until the exact reader checks its digest. Missing records are unavailable. A detected corrupt body refuses the read. Attention source coverage is only permitted current refs; omitted refs and their counts are not disclosed. Relations are not exposed by this first generic reader; existing Attention relation endpoints retain their own contract.

## Persistence, verification and limits

Core4/app5 adds only disclosure tables. Existing validated Core3/app4 receives an exclusive `.pre-governance-core-v4-app-v5.bak` SQLite backup before an atomic schema+marker transaction. Older supported pairs first pass their existing staged migrations. Existing backup paths (including symlinks), malformed/current missing tables and unsupported pairs refuse without repair. An old Core3 host refuses Core4; recovery uses a backup in a separate directory with its matching host. Runtime7 data must not be handed to an older runtime. New empty databases need no migration backup. No personal data is used in tests.

Evidence must distinguish author and non-author runs, fix the product SHA, and exercise actual authenticated HTTP/Runtime packets. Critical counterexamples are hidden fields/counts/relations, same-ID scope confusion, stale pages, revoke/expiry, changed replay, crash before commit/after commit before ACK, producer/Session absence, missing/corrupt source bytes, unknown schema and runtime attempts to mutate policy. BG-01 does not close real-provider, UI, native, Paper or G1–G5 gates.
