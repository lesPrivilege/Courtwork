# Worker-slice preflight · fixed Attention contract check

Date: 2026-09-27  
Read-only baseline: Courtwork main at 800d591  
Decision owner: Astra; proposed implementer: Sol; independent reviewer: Luna  
Scope: one small DF-04/RD-009 backend/tools/documentation slice, plus a read-only CB-D1 reference inventory

## Recommendation

Dispatch one bounded Sol task to add a second frozen Host check recipe named `node-test-attention-contract`. Its command and test paths are fixed in the code-defined catalog. The model still supplies only `recipeId`; it cannot provide a command, arguments, working directory, environment, timeout, or test selector.

The recipe would make the next Hermes/Attention dogfood case observable through the existing `check_run` seam: a private Courtwork candidate can run the existing backend and synthetic Attention contract tests, and the Host records the same `check.started` / `check.settled` facts already used by DF-04.

This is the smallest useful slice because RL-1 reached a real CW candidate but explicitly could not invoke `check_run`: the only current recipe runs the whole repository with fixed `node --test`, while RL-1 needed a narrow test selection. DS-1 independently confirms that the current dogfood path can complete a small documentation task without `check_run`; it does not solve targeted verification.

No Runtime Port, Core schema, provider adapter, UI, frontend, arbitrary command path, dynamic map generator, or general SDK is needed.

### Product/tool files in scope

1. app/runtime/check-recipes.mjs — add one frozen recipe descriptor:

   - id: `node-test-attention-contract`
   - version: 1
   - title: `Run Attention backend contract tests`
   - command: the Host’s own Node executable, exactly as node-test v1
   - argv: exactly the fixed list below
   - cwd: the existing private candidate
   - timeout: retain the existing 120000 ms limit
   - output limit: retain the existing 65536 bytes per stream
   - environment: retain the existing minimal policy

2. app/docs/check-recipes.md — add the catalog row and state that this recipe is a Courtwork candidate contract. The document must say that its fixed app/tests paths are expected to exist in a Courtwork candidate; on another candidate, a non-zero process result is an ordinary check outcome and does not become an acceptance or a Host failure.

3. app/tests/check-recipes.test.mjs — extend the existing catalog/approval tests to assert the exact recipe id, version, argv, cwd, timeout, output limit and minimal environment. Keep the existing read_only, deny, stale candidate, cancellation and restart tests unchanged and passing. Add one bounded integration case proving the approved descriptor reaches the runner unchanged; do not add a general command/argument parameter.

No app/runtime/check-tools.mjs, app/runtime/check-runner.mjs, RuntimeStore schema, server/runtime.mjs, Runtime Port, Core, provider configuration, UI module, or frontend test file should change in this slice.

### Exact fixed command

The recipe’s argv should be:

    --test-concurrency=1
    app/tests/attention-core.test.mjs
    app/tests/attention-http.test.mjs
    app/tests/attention-recovery.test.mjs
    app/tests/attention-github-fixture.test.mjs
    app/tests/attention-gmail-fixture.test.mjs
    app/tests/attention-trace-fixture.test.mjs

The bundle is intentionally backend and synthetic-source focused. It excludes attention-actions, attention-triage, attention-agent, attention-ui02 and other UI-oriented suites so the slice does not overlap Claude’s frontend lane. It also excludes live connectors and paid providers; the GitHub/Gmail files are deterministic fixtures.

The fixed catalog remains the authority. Do not add a recipe argument such as testFiles, pattern, cwd, command, argv, scope, provider. Do not turn this into a generic target selector. If the current candidate model cannot safely distinguish a Courtwork candidate from an unrelated candidate, keep the row fixed and document the ordinary non-zero missing-path result; do not invent a registry or applicability protocol in this slice.

## Failure cases and required evidence

The worker must preserve existing DF-04 behavior and show these cases in the focused checks or evidence:

| Case | Expected result | Why it matters |
|---|---|---|
| Unknown recipe id | Tool error before permission or process start | Preserves the existing catalog boundary. |
| Read-only mode | Denied with zero process starts | A new recipe must inherit the Host ceiling. |
| Ask mode | Permission payload contains exact id/version/command/argv/private-candidate/limits/environment | The person approves the real fixed action, not a label. |
| Stale or revoked candidate after approval | candidate_changed / run-closed refusal with zero new process start | Prevents a fixed recipe from bypassing candidate identity or write-revision fencing. |
| Target test failure | status: completed, non-zero exit, retained bounded output | A failing test is process evidence, not a Host failure or formal Work rejection. |
| Target paths absent in an unrelated candidate | status: completed, non-zero exit with ordinary test output | The fixed recipe must not silently claim applicability or invent a new dynamic path check. |
| Timeout or cancellation | Existing timed_out / canonical cancelled settlement, retained partial output, no duplicate settlement | Confirms the new row reuses the existing runner and Host settlement. |
| Host restart after check.started | One unknown settlement and no replay | Keeps recovery semantics independent of Attention or Hermes. |
| Current Courtwork candidate | Approved recipe records exact argv and exits 0 only when the six fixed suites pass | This is the live CW dogfood proof that resolves RL-1’s narrow-check friction. |

The live CW dogfood should use a synthetic/private candidate based on the current reviewed source and the local fake provider only. It should capture the permission descriptor, check.started, check.settled, bounded output and candidate identity. It should make no provider request beyond whatever deterministic test fixtures create internally, inspect no credential store, restart no user Host, and touch no user data.

## Checks and handoff

Recommended worker checks, run from the app directory or equivalent candidate path:

    node --test --test-concurrency=1 tests/check-recipes.test.mjs tests/control-plane.test.mjs tests/runtime.test.mjs

    node --test --test-concurrency=1 tests/attention-core.test.mjs tests/attention-http.test.mjs tests/attention-recovery.test.mjs tests/attention-github-fixture.test.mjs tests/attention-gmail-fixture.test.mjs tests/attention-trace-fixture.test.mjs

    npm run smoke

The worker should report exact exit/results and any unrun check. Parent acceptance should run the existing document-link and applicable verification checks, then one live synthetic-candidate check_run using node-test-attention-contract. A passing exit code remains process evidence only; Attention formal state and human resolution stay with Core.

Stop before any of the following:

- changing the recipe runner, Host approval schema, store events or Runtime Port;
- introducing candidate applicability metadata, a recipe registry, dynamic arguments or arbitrary shell;
- modifying Attention Core state, event normalization, Hermes transport, connector authentication, scheduler or notification effects;
- changing Claude’s UI lane or CB-D1 frontend files;
- claiming real Hermes, live GitHub/Gmail, provider, credential, deployment or formal Work acceptance.
