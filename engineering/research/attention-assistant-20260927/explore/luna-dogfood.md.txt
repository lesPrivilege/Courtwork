Decision owner: Astra. This is bounded exploration and evidence, not an architecture decision or product acceptance.

## L0 — the usable conclusion

Courtwork already has the important pieces of a bounded development harness: a short repository-wide instruction entry, a current-status owner, task and contract records, thin semantic indexes, Runtime Control’s metadata-then-load context model, profile composition, a pure Kit context planner, and immutable Run-owned context evidence. The missing piece is a discoverability view that joins those existing owners for one task; it is not a missing generic plugin system.

The four upstream practices support different mechanisms:

| Practice | Primary mechanism verified | What it does not prove |
|---|---|---|
| Aider repository map | Generates a symbol/file map, ranks dependency-connected files into a token budget, and expands detail when needed | That Aider’s ranking or output shape should become a Courtwork contract |
| Agent Skills | A portable SKILL.md directory with metadata, instructions, and optional references/scripts/assets loaded progressively | That a skill can grant permission, install code, or replace Courtwork’s Host/Runtime ownership |
| OpenHands skills | Adds keyword and deterministic path-triggered loading to Agent Skills; path rules inject guidance when a matching file is touched | That path triggers are part of the base Agent Skills specification or are available in every client |
| GitHub Spec Kit | Uses a specification → plan → tasks → implement → append-only converge loop | That Courtwork should create a second lifecycle, roadmap, or task ledger |

The smallest useful Courtwork pattern is therefore:

1. L0: read AGENTS.md, engineering/current.md, and the bounded assignment.
2. L1: resolve the semantic owner, contract, nearest local precedent, and verification entry through existing indexes.
3. L2: generate or inspect only the relevant structural map, read exact source/evidence, make the scoped change, and append findings to the existing owner/task record.

The recommendation is to adopt that hierarchy as a documentation and workflow convention, adjust it to keep semantic authority separate from generated structure, and defer any new manifest, .cw/config, executable .agents skill, generic catalog, or plugin SDK.

### Semantic map versus generated structural map

Keep two maps with different owners and lifecycles:

| Map | Contents | Authority | Update rule |
|---|---|---|---|
| Semantic map | Task trigger, responsible owner, contract, scope, nearest precedent, verification entry, governance status, and explicit “do not infer” boundaries | Human-maintained existing owner/index documents | Change only through the existing task/owner record and architecture/design governance. Never infer authority from path existence. |
| Structural map | File paths, exported symbols, imports/references, dependency edges, source SHA, and a bounded relevance ranking | Generated from the actual checkout for a given task | Regenerate for the actual HEAD and scope. Treat as a navigation aid or evidence artifact, never as a second contract. |

Aider’s map is evidence that machine-generated structural navigation can be useful: its official documentation says it lists files and key symbols, uses dependency edges and graph ranking, and adapts the map to a token budget. Courtwork should borrow that separation of “where” from “why”; it should not copy Aider’s graph, token defaults, or output format without a bounded implementation contract.

OpenHands path rules could eventually supply deterministic context for files under an owner boundary. The current Courtwork runtime does not expose path-triggered rule semantics. Runtime Control currently validates/imports Skills and loads bodies through explicit runtime_load; that is a different, owner-controlled mechanism. Path triggers should therefore remain an optional adapter capability until a specific client/runtime contract and evidence exist.

### Smallest future workflow

For one new Attention capability or a bounded front-end/backend change:

1. Identify the affected responsibility and task owner in the existing record.
2. Read AGENTS.md, engineering/current.md, and the assignment. Confirm branch, HEAD, and status.
3. Use the existing index to resolve the semantic owner: for Attention, start at engineering/product-direction.md, engineering/architecture.md, docs/work-core/attention.md, and app/docs/attention-agent.md; for Runtime/Kit context, add docs/runtime-control/INDEX.md and its linked contract.
4. Read only the nearest contract and one or two relevant precedents. Stop when the owner, scope, and accepted boundary are clear.
5. Generate a bounded structural map for the touched files, if useful. Record its source SHA and scope; do not store it as a new authority.
6. Implement or inspect against the existing owner. Keep Runtime configuration, Run binding, Work Core state, and UI projection in their current owners.
7. Run the narrowest relevant checks, then the broader required check selected through engineering/verification.md.
8. Record adopt/adjust/reject/defer with reason and evidence in the original owner/task record. A completed implementation or generated map does not become acceptance automatically.

This workflow is a dogfood loop, not a second roadmap: the same owner/index/evidence chain is used to maintain the harness while it is used to develop Attention.

## <details><summary>Primary practice verification — mechanism versus consensus</summary>

Sources below were checked as primary upstream documentation or source on 2026-09-27. A source being primary verifies what its project documents or implements; it does not establish Courtwork suitability or industry consensus. No popularity metric is used as an architectural signal.

### Aider repository map

- Primary docs: [Aider Repository map](https://aider.chat/docs/repomap.html), especially “Using a repo map to provide context” and “Optimizing the map.”
- Primary source: [Aider repomap.py](https://github.com/Aider-AI/aider/blob/main/aider/repomap.py).
- Verified mechanism: the map includes repository files and important classes/functions/signatures; Aider can use it to decide which files to load; a dependency graph and ranking select relevant map portions within an active token budget; the map may expand when the chat has little file context.
- Courtwork input: separate generated structural navigation from human semantic ownership. A map should carry path/symbol/dependency/source-SHA pointers and route back to existing contracts.
- Limits: the docs describe Aider behavior, not a portable repository-map standard. Ranking quality, token budgets, tree-sitter details, and output syntax remain Aider-specific. This is mechanism evidence, not a popularity or consensus claim.

### OpenHands skills and path-triggered rules

- Primary docs: [OpenHands Skills Overview](https://docs.openhands.dev/overview/skills) and [Path-Triggered Rules](https://docs.openhands.dev/overview/skills/path).
- Verified mechanism: Skills advertise name/description first, load the full SKILL.md on invocation, and load references/scripts/assets only when needed. OpenHands path rules use paths frontmatter and inject guidance when the agent reads, edits, or creates a matching workspace-relative file; they are loaded once per conversation and are not model-invocable. The path page also documents POSIX/gitignore-style matching and a local-conversation limitation for ACP-backed execution.
- Courtwork input: use the mechanism only as a future client-specific adapter pattern. An OpenHands path rule is not an Agent Skills base field and cannot be treated as a current Codex/Courtwork guarantee. Existing Runtime Control explicit runtime_load and host policy remain authoritative.
- Limits: OpenHands itself says other Agent Skills clients may ignore its trigger/path extensions. The deterministic promise is therefore scoped to the OpenHands loader and its supported local execution path.

### Agent Skills specification

- Primary spec: [agentskills.io Specification](https://agentskills.io/specification) and its [governance repository copy](https://github.com/agentskills/agentskills/blob/main/docs/specification.mdx).
- Verified mechanism: a skill directory contains SKILL.md plus optional scripts, references, and assets; SKILL.md requires YAML frontmatter with name and description; the body is loaded after activation; referenced resources are loaded as needed; the spec recommends keeping the body under 500 lines and using one-level-deep relative references; skills-ref validates the format.
- Important boundary: the base spec defines the skill package shape, not a universal install root, permission model, trigger syntax, registry, sandbox, or executable authority. OpenHands recommends .agents/skills for its own project skills; that is a product convention, not a reason to inspect Courtwork’s user-owned untracked .agents directory or to create one.
- Courtwork input: retain the current imported skill/resource path and Host validation. If a future adapter consumes SKILL.md, preserve resource identity, scope, hashes, exposure, policy, and Run binding through Runtime Control. Do not say Courtwork can be replaced wholesale by Agent Skills.
- Limits: the spec and client showcase document an open format and compatible clients, but they do not prove a consensus standard in the sociological sense or prove equivalent loading/permission behavior across clients.

### GitHub Spec Kit agentic SDD and converge

- Primary docs: [current agentic-sdd.md on GitHub Spec Kit main](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md), especially the command overview and /speckit.converge section; [converge command template](https://github.com/github/spec-kit/blob/main/templates/commands/converge.md).
- Verified mechanism: the documented loop is constitution → specify → clarify → plan → checklist → tasks → analyze → implement → converge. Converge compares the codebase with spec, plan, and tasks; it is append-only, does not edit/delete application code, and can only append tasks to tasks.md. A clean pass leaves tasks.md byte-for-byte unchanged; a gap pass appends a Convergence section and feeds the next implement/converge iteration. The docs also state that analyze is read-only and custom checklist approval is reviewer-owned.
- Courtwork input: borrow the convergence idea as a final L2 check against the task contract and acceptance evidence, then record gaps in the original task/owner record. Preserve Astra’s architecture/review ownership and engineering/current.md as the status authority. Do not introduce a second spec/tasks ledger or self-acceptance loop.
- Limits: Spec Kit’s commands, templates, integration modes, and current main branch are its own product behavior. A GitHub repository’s stars/forks, newsletter claims, or extension count would not establish engineering consensus and were not used here. Before any future adoption, pin a source commit and record the exact command/version.
