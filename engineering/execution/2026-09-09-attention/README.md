## Decisions

Attention is a B0 domain within the existing WorkCoreOwner worker and SQLite database. Current state, audit events and request receipts commit in one transaction. It does not reuse Matter decision audit rows that require a Matter. Its own domain tables remain under the same owner. `app_run.matter_id` stays non-null; many-to-many Matter references and immutable execution references are stored with Attention. Ending/deleting an execution never changes its status.

The migration target is Core3/app4, leaving RuntimeStore4 unchanged. Validate complete Core2/app3 before creating an exclusive `.pre-attention-core-v3-app-v4.bak`; install Attention DDL and version markers atomically. Existing Core1/app1/app2 migration remains supported through the established file migration followed by Attention migration. Reject mismatched version pairs, malformed current tables and existing backup paths. Old Core2 hosts must refuse Core3. Restore only into a separate directory using the corresponding old host. Synthetic copies only.

Attention schema1 has stable id, project scope, revision, descriptor, status, freshness, reason, next action, source references, relation references, seen, policy and last event metadata. Status is investigating/needs_you/waiting/later/resolved. Sources retain exact version and locator; external references are unknown and never dereferenced. Core source references must belong to a Matter in the same project. Session and Runtime Run references are checked by the host on attachment and retain their observed provenance after deletion; they do not assert continued availability.

The local human API uses the authenticated host actor and an existing project selector. The selector is not a cross-user ACL. Runtime consumers receive a captured host context derived from an actual Session/Run, never actor/scope supplied by model arguments. Core enforces project isolation for every read, query, receipt and write, before existence, descriptor, counts or conflicts are exposed. Human access within the selected local project is full. Runtime access is denied by default and requires an explicit object-specific disclosure grant, limited by purpose, fields and expiry, with revocation. A registry grant alone does not permit details, source or event reads, grep or relation filtering on hidden fields.

Typed actions are version1 create, acknowledge, snooze, set_waiting, resume, resolve, reopen, attach_relation, request_disclosure and record_signal. Human resolve requires an explicit reason. Signals are only recorded under the separate authorized signal capability and never change status or grant authority. Seen is separate from resolution. Snooze records a condition; no timer runs. Unsupported actions, schemas and payload fields fail closed. Request id binds actor context, object, expected revision, action and full payload; exact replay returns the committed receipt and changed replay conflicts. A scoped request query reconciles lost acknowledgements.

Queries are typed inspect, registry, exact, bounded literal grep, relation, events, source and receipt. All are bounded and disclose only policy-visible fields; no semantic index or model search is introduced. Results carry schema/revision, disclosure and pagination/truncation metadata. Unknown object schemas are refused, not interpreted as current.

## Frozen wire design

The private Core operations are `attention_action({context,request})` and `attention_query({context,query})`. Context is `{actor,project_id,purpose,execution}`. Actor is `local-user` or `runtime`; human purpose is `human-attention`, runtime purpose is `attention-runtime`; execution is null for humans and `{adapter_id,session_id,run_id}` for runtime. Only the trusted host constructs context. Runtime access is a backend adapter seam, not a public route accepting a runtime actor.

An action request is `{schema_version:1,request_id,attention_id,expected_revision,action,payload}`. Create expects revision0 and commits revision1. Every committed action, including a signal or seen action, increments revision once and emits one audit event and receipt. A conflict does not emit an event. Exact retry returns the old receipt even if current revision has advanced; it does not return a new current snapshot disguised as the old result.

Create payload is `{descriptor:{title,summary},reason,next_action,source_refs,relation_refs}`. The initial status is investigating, freshness unknown, seen false. Next action is `{kind,label,trigger,due_at}` with kinds inspect/decide/wait/follow_up/none, triggers manual/at/after/external, nullable ISO timestamp. State actions require reason and next_action except acknowledge (empty payload), resolve (reason) and reopen/resume (reason). Relations use `{kind,id,relation}` with kind matter/session/run/external and relation about/execution/origin. Host-captured execution provenance is stored separately from client-controlled relation identity. Source refs use `{kind,matter_id,source_id,version,locator,role,digest}`, with kind core/external, role supports/reports/contradicts; external matter_id and digest may be null. External references remain unknown; core references verify scoped immutable bytes and membership before attachment or source read.

`request_disclosure` payload is `{grant}`: null revokes, otherwise `{adapter_id,purpose,fields,expires_at}`. Fields are registry/details/sources/relations/events/signal. A grant is object-specific, records its issued revision and remains valid until expiry or explicit replacement/revocation. This is explicit human authority for disclosure and optional signal recording, never for resolve or external effects. Runtime signal payload is `{text,source_refs}` and cannot set status/policy/seen. Signal source refs are audited observations, not automatically promoted to the object's supported basis.

HTTP routes use the existing token protection: GET `/attention/registry?projectId=…`, GET `/attention/:id?projectId=…`, POST `/attention/query` with `{projectId,query}`, POST `/attention` with `{projectId,request}` for create, POST `/attention/:id/actions` with `{projectId,request}` for other actions. The path must match request identity. Unknown envelope fields (including actor/context) fail. A project selector is validated against the local host catalog and narrowed to one scope before Core access.

Query schema_version is1; kinds are registry/inspect/exact/grep/relation/events/source/request. Single-object kinds require attention_id. Query filters and pagination are explicit and unknown fields fail. Registry/exact/grep/relation return only visible entries and visible counts; offsets refer to that visible result, not hidden database rows. Limit1–50, at most1000 objects per project and32KiB per stored object bound local scans; no unlimited capacity claim. Source reads are code-point pages up to4000 characters; event/receipt reads remain scoped and policy-checked. No raw external retrieval or semantic search is implemented.
