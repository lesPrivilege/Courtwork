## Proposed concrete schema-22 fields and invariants for implementation

- Session `executorChoice` has **exact** keys `revision` (safe integer ≥0), `adapterId` (existing bounded ID string or null only for contradictory migrated nonchild history), `configurationRef` (null on every schema-21 migrated Session; otherwise `sha256:<64 lowercase hex>`). New schema-22 Session creation receives the default descriptor from service and stores Pi ID/ref; Store migration reads only the old file. Excluded global/extension/child choice is read-only at the public selector. A child Pi choice is a schema placeholder, never its execution owner.
- Run `executorBinding` is one of three exact forms: `{recording:'bound',revision:string,configurationRef:string,capabilities:<seven fixed support/reason rows>,choiceRevision:safe integer ≥0}`; `{recording:'legacy',revision:null,configurationRef:null,capabilities:null,choiceRevision:null}`; or `null` only when an existing Spark assignment/attempt references that Session/Run. The top-level `run.adapterId` remains the actual dispatch ID. New nonchild Runs must be bound; every old nonchild Run migrates as legacy without inferred version/ref; old/new proven Spark child Runs get null and keep their actual Pi/local-Pi receipts.
- Bound `configurationRef` is a digest of immutable executor-specific configuration plus adapter revision/protocol only. It excludes credential reference/generation, Provider/Model, remote connection hash and data path. Current Provider readiness and managed remote binding/credential checks remain separate. Pi key/model changes between Runs must not alter executor identity.
- On load and each mutation, cross-check nonchild Session choice against *agreed* historical `run.adapterId`, Pi `hostSession` and managed `remoteBinding.runtimeId`/protocol. Contradictory native/adapter history in any nonchild scope stays readable with null choice and cannot admit another ordinary Run. Proved child history is checked against Spark owner, not ordinary choice. Existing remote action/Kit validators remain strict.
- In the Store mutation for a new nonchild Run: first return the original command receipt; then check supplied pre-transaction choice revision/adapter, any already-pinned ref, native lineage, unresolved fences and existing admission rules. If migrated choice ref is null, atomically set descriptor ref, increment choice revision **once**, and write that post-pin revision in the new Run binding. A failed admission writes neither; replay returns the saved Run and does not repin. Later Runs require exact descriptor/ref and never change choice revision. Public PUT is a separate no-history CAS and cannot change any Session with Run/native history.
- Schema21→22 validates old bytes first; exact exclusive `runtime-state.schema21.<sha256>.json` backup, then atomic new state. Old schema21 reader must refuse schema22 byte-for-byte. Core user4 and bridge app5 stay unchanged. Existing legacy schema3–20 upgrades retain their prior explicit fields/backup identities while producing valid22; schema21 Kit records are preserved, never nullified.
