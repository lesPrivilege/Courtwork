---

### 对 CW 来说，这反而验证了“Runtime 必须和 Harness 解耦”

如果 Anthropic 对 DeepSeek 的具体描述成立，那么一个很重要的事实出现了：

```text
Harness
   ↓
provider API
   ↓
requested model
```

实际上可能是：

```text
Harness envelope
      ↓
Provider classifier / router
      ↓
provider-native model
      OR
third-party frontier model
```

也就是说，**provider 本身不能再被建模成一个透明的 `model()` 函数。**

尤其 Anthropic 指控的 DeepSeek 流量涉及 coding/agent 使用场景；目前二手报道进一步称，某些请求具有 Claude Code、Claude Agent SDK、OpenCode 等 harness 特征。这个更细的技术细节目前公开证据不如总体 routing 指控扎实，所以我暂时只把它列为 **Anthropic attribution，而非已证实事实**。

但它给 CW 一个很好的设计要求：

```text
Harness
  ├─ Matter / Context compiler
  ├─ Tool protocol
  └─ Runtime boundary
        ├─ requested provider
        ├─ requested model
        ├─ endpoint
        ├─ protocol / SDK version
        ├─ request envelope
        ├─ provider-returned model identity
        ├─ routing / region policy snapshot
        └─ identity confidence
```

最后一项尤其值得有：

> `model_identity: provider_asserted`

而不是假装：

> `model_identity: verified`

因为客户端看到自己连接到 `api.deepseek.com`，**并不能证明 DeepSeek 的后端没有再调用另一家模型**。

这正好属于 SE 所说的 provenance：事实是“我向哪个 endpoint 发了什么、provider 声称返回了什么”；至于后台真实 inference topology，是另一层不能无证据冻结的推断。

---

### 还有一个更值得关注的 CW 测试维度

以前 provider eval 很容易写成：

```text
same prompt
DeepSeek vs Claude vs Gemini
→ quality / latency / price
```

现在我会增加一轴：

**same semantic task × different harness envelope**

例如：

```text
plain Messages API
Claude-Code-shaped request
OpenCode-shaped request
CW-native request
tool-heavy request
long-context request
```

观察：

- latency 分布是否突变；
- token accounting 是否异常；
- capability fingerprint 是否异常变化；
- tool-call / thinking / cache 行为是否改变；
- response metadata 是否变化。

它不能证明“偷换模型”，但能够测试一个更基本的问题：

> **provider 是否会根据 harness 身份改变 routing/runtime 行为。**

这与你上午说的“DeepSeek 的 post-training 与 harness 存在耦合，应先封装自己的 DS Runtime 做技术验证”恰好合上了，而且现在理由更强：不只是适配能力，还是**隔离 provider policy**。

Anthropic 现在不是根据 DeepSeek 输出“猜 Claude”。

**Anthropic 是被指控的那个上游模型的服务端。**

它给 DeepSeek 分配了内部 case `GTG-16001`，声称：

- DeepSeek 在用户**不知情**的情况下把部分请求 relay 给 Claude Opus；

- 使用了与 reasoning/thinking signature 有关的 cross-session replay 技术；
- Anthropic 在这些进入自己系统的请求里看到了看起来明显不像 synthetic benchmark 的东西，包括：
  - 一个俄罗斯政府数据库的有效凭证；
  - 中国警务案件管理系统相关材料。
- 最新报道进一步转述 Anthropic 的调查称，DeepSeek 会识别来自 **Claude Code / Claude Agent SDK / OpenCode 等 coding harness** 的请求，并对其中部分请求作这种处理。

CNBC 对 1210 万 / 14 天的数字也做了独立新闻核实式转述；截至今天，DeepSeek 尚未对这些具体技术案例公开逐项反驳。

### 但仍然有一道关键证据缺口

Anthropic **没有把足以让第三方复核归因的底层材料公开出来**。

我们现在没有：

```text
DeepSeek request ID
        ↕
DeepSeek server / account
        ↕
proxy / transfer station account
        ↕
Anthropic request ID
        ↕
timestamp + prompt hash
```

这种一对一 forensic chain。

也没有：

- 1210 万请求的匿名化原始 telemetry；
- fraudulent account IDs；
- payment correlation；
- IP / ASN correlation；
- DeepSeek 自己的服务端日志；
- 第三方审计；
- 可公开验证的 prompt→Claude request 对。

因此需要把两个问题分开。

**“Anthropic 的服务器是否真的收到了这批请求？”**  
这是 Anthropic 最有条件知道的事情。如果它在撒谎，就是在伪造自己生产系统里 1210 万次调用级别的事件，因此我会给这一事实相当高的先验可信度。

**“这些请求确实是 DeepSeek 官方服务有意把终端用户请求转过去的？”**  
这涉及 attribution chain。Anthropic 说自己有高置信度，但外界看不到完整证据，所以不能独立验证。

这两者不是同一个证据强度。

最直接的证据恰好就是你说的“恢复模式”。DeepSeek V4 明确区分了两种 reasoning lifecycle：

```text
普通对话
user → reasoning → answer
new user turn
        ↓
previous reasoning 被清掉

带工具的 agent loop
user → reasoning → tool call → tool result
                     ↓
              reasoning 保留
                     ↓
        下一轮继续原有 reasoning
                     ↓
new user turn 后仍可继续
```

也就是说，**是否存在 tool call，本身会改变模型跨 turn 的内部状态持久化规则。**

DeepSeek 的 V4 说明甚至明确说：V3.2 在新的 user message 到来时会丢弃 reasoning；V4 对包含 tool calls 的会话则保留完整 reasoning history，而没有工具的普通聊天仍会 flush。 [V4 说明](https://huggingface.co/blog/deepseekv4)

这已经不是“给模型多加几个工具”这么浅了，而是：

> `tool presence → state transition policy`

换言之，Harness 改变了模型**如何续行**。

---

更明显的是 reasoning effort。V4 不是简单的 token budget 滑块，而是三个不同操作区：

- Non-think
- Think High
- Think Max

其中 **Max 甚至使用专门的 system prompt**；官方还建议 High / Max 给到极长的 reasoning budget。Flash 在增加 thinking budget 后，部分 reasoning benchmark 可以逼近 Pro，而 agent 难题上两者差距又重新显现。

所以更合理的抽象不是：

```text
model + more tokens = smarter model
```

而是：

```text
weights
  × reasoning policy
  × system contract
  × tool grammar
  × trajectory history
  × harness environment
      ↓
observable capability
```

其中有些变量实际上就是后训练时见过的环境。

### 再往训练侧走一步，会发现它不是偶然耦合

V4 的 post-training 本身就是先分别训练：

```text
math expert
coding expert
agent expert
instruction-following expert
       ↓
on-policy distillation
       ↓
unified model
```

其中 agent expert 又不是在纯文本 dataset 上学出来的，而是在真实工具环境里做 RL rollout。

DeepSeek 为此专门造了 DSec sandbox，统一 function / container / microVM / VM；甚至有 **preemption-safe trajectory replay**，让中断后的 rollout 能继续，而不用重新执行已经完成的工具调用。

[DeepSeek-V4 technical report](https://arxiv.org/html/2606.19348)

因此所谓“模型学会使用工具”，其实更准确地说：

> **模型学会了某一种 trajectory grammar。**

它学到的不只是：

```text
什么时候调用 bash
```

还包括：

```text
什么东西进入 reasoning
→ 如何编码 tool call
→ tool result 之后从哪里恢复
→ 哪些 reasoning state 应继续存在
→ 出错后如何 retry
→ 多步任务什么时候继续 / 收束
```

这就是 Harness coupling。

---

因此我反而会把 DeepSeek 当成一个特别好的反例，用来反驳传统的：

> Model 是 intelligence，Harness 只是 plumbing。

V4 表现出来的结构更接近：

```text

             ├─ tool grammar
Model ←──────┼─ reasoning effort
             ├─ state persistence
             ├─ error / recovery semantics
             └─ rollout topology
```

**Harness 已经进入 capability 的条件定义。**

这也解释了为什么 PI、OpenCode、Claude Code、DeepSeek 自己 Harness 上，同一 provider 可能出现明显不同的结果：它不一定是谁的 harness “写得更漂亮”，而可能是某一个 harness 恰好更接近 post-training trajectory distribution。

而这对刚才的 Claude-routing 调查有一个很重要的反向约束：**CoT 突变、能力突变、恢复方式突变本身都不能作为换模型的充分证据。** DeepSeek 自己就公开存在由 `tool × effort × message lifecycle` 引发的行为相变。

真正值得怀疑 routing 的，是除此之外还同时出现的那些**外部模型特有、DeepSeek 自身机制难以解释的条件相关性**——例如当时测试里据称与 Anthropic cyber/bio classifier 同步发生的退化，再加上后来 Anthropic 服务端 telemetry 的指控。

所以两类东西最好严格拆开：

> **Harness-conditioned behavior** 是已经公开确认的 DeepSeek 设计特征；  
> **hidden upstream routing** 则是需要额外 forensic evidence 才能成立的供应链命题。

这也恰好说明 CW 第一版 DeepSeek Runtime 不应该只是“兼容 DeepSeek API”，而应该把 **DeepSeek 的 reasoning lifecycle / tool trajectory / effort policy 当作一等 runtime semantics 去复现和测量**。否则很可能接上了模型，却没有真正接上它被后训练出来的行为分布。

## 对 CW，我会把它进一步写成一个原则

### `Work depth ≠ Projection depth`

Agent 可以在后台极深地工作，但 **projection 永远按照用户任务的最小充分表达来决定**。

于是：

```text

```

三者不能互相复制。

这与我们前面的 Event Log / Matter State / Model Context 区分其实还能再增加一面：

```text
Event Log
    ≠
Matter State
    ≠
Compiled Model Context
    ≠
User-facing Projection
```

前三个解决 Agent 如何工作；第四个解决 **人应该看到什么**。

---

### 一个非常简单的 projection rule 就能消掉大量怪行为

只有三类内部过程应该默认进入最终答案：

1. **结果会因此改变用户决策**  
   例如：“我没能验证这个数字。”

2. **存在失败、风险或重要不确定性**  
   例如：“测试通过，但迁移脚本没有在生产数据库验证。”

3. **用户明确要求过程、审计或解释**  
   例如：“告诉我你改了什么、跑了哪些测试。”

否则：

```text
checks
guardrails
deleted alternatives
rejected options
internal TODO
negative constraints
```

全部留在 trace。

尤其应有一条非常严格的规则：

> **Negative instruction should affect the artifact negatively, not appear positively in the artifact.**

比如：

```text
“不要提价格”
```

正确结果：

```text
[正文里没有价格]
```

而不是：

```text
（价格信息已省略）
```

这其实可以成为非常具体的 eval。

## 对中国大陆/主权模型，这个结构甚至更重要

这轮调研里有一个很明显的共同趋势：DeepSeek、Kimi、GLM、MiniMax 都在用更强的 **Harness co-training / preserved thinking / agent RL / tool trajectory** 弥补基础模型与最强闭源模型在困难长任务上的差距。

但副作用也很清晰。

例如 MiniMax M2.5 官方甚至明确写道，训练过程中涌现出了 **“Spec-writing tendency”**：模型在写代码之前，会主动像高级架构师一样把 feature、structure、UI 全部分解和规划。这在复杂软件工程中可能是正收益；一旦直接迁移到非 coding Work，就非常接近我们刚才讨论的：

> 明明只需要改一个表，却开始设计一套完整系统。

因此对主权模型最危险的做法反而是：

```text
Work
↓
直接给模型一整套 Claude-Code-like harness
↓
希望它自己判断什么时候不要工程化
```

小一些的模型通常更难稳定做最后这一步。

更可靠的是：

```text
Work model
负责：
任务理解 / 专业语义 / Matter / 最终 projection

             ↓ 必要时

Coding-specialized runtime
负责：
机械计算 / shell / automation / browser / conversion
deployment / executable verification

             ↓

只返回受治理结果
```

于是我们不是要求一个模型同时拥有：

> 专家判断 + 软件工程判断 + 系统权限判断 + UI 品味 + 最终写作判断

而是把 coding harness 已经高度后训练过的那部分能力**局部消费掉**。

这与 SE 的思想其实非常一致：不是让所有内部 trace 都重新进入最终 context，而是治理之后渐进披露。

### Worker 的 Coding 有三个实现候选

我不会现在裁掉其中任何一个：

## Result Capsule 应该尽量不是模型自由总结

这里我会优先考虑一个 hybrid，而不是纯 summary。

例如 Coding episode 完成后，Runtime 本身已经知道：

```yaml
status: completed

inputs:
  - source.xlsx

mutations:
  - target: report.xlsx
    kind: cell_update
    count: 17

artifacts:
  - report.xlsx

verified:
  - formula_recalculation: passed
  - row_count_preserved: true

findings:
  - id: anomaly-7
    value: ...

warnings:
  - sheet "Legacy" was not modified

temporary:
  files_created: 3
  retained: false
```

这些东西是**机械可投影的**。

然后模型只负责把真正属于 Work 判断的部分写成两三句自然语言：

> 已完成交易表核对并更新报告；共发现 7 项异常，其中 2 项需要人工判断。原始数据和 Legacy sheet 未修改。

所以：

```text
structured execution facts
        +
small semantic synthesis
        =
Result Capsule
```

而不是让模型重新读一万 token 的 coding trace，然后问它“请总结你刚刚做了什么”。

后者很容易把刚刚试错过但最终废弃的东西重新带回来。

## 但前置缓存确实是这里最需要实测的一块

你的“把 Coding Harness 拼到尾端，从而保住前置命中”的直觉是对的，但实际 API 上不一定这么简单。

因为请求通常不是单纯：

```text
system
messages
尾部 coding prompt
```

很多 provider 实际序列化还包括：

```text
system
developer
tool schemas
skills/tool metadata
messages
```

如果开启 Coding 时突然多了 Bash、Edit、Patch、Terminal 等十几个 tool schema，**工具定义很可能位于消息历史之前**。

那么即使文本 Harness 是尾部注入，真实 prefix 还是变了：

```text
Work request:
[system][work tools][history...]

Work+Code request:
[system][work tools + code tools][history...]
                      ↑
              prefix 已经分叉
```

所以这需要专门测，而不能假定 cache 一定保留。

我目前会考虑三种实现，从简单到高级：

| 做法 | Cache | 行为隔离 | 复杂度 |
|---|---|---|---|
| 两套稳定 profile：`Work` / `Work+Code` | 各自内部很好 | 好 | 低 |
| 始终保留一个稳定 `code_delegate` tool | prefix 最稳定 | 很好，详细 Coding 工具在 child 内 | 中 |
| lazy/deferred tool loading | 理论最好 | 同 Worker 能真正获得局部工具 | 高、依赖 provider |

第一版我反而最推荐 **两套 canonical prefix**。

也就是：

```text
Profile W
Work-only prefix
→ 自己形成稳定 cache

Profile WC
Work + bounded-code prefix
→ 自己形成另一条稳定 cache
```

不强求 W → WC 还能复用同一个 KV prefix。

因为如果为了省 cache，把所有 Coding schema 永久暴露给 Work 模型，很可能重新引入我们正要解决的 **agentic activation / overengineering**。

几十美分的 cache 节省不值得换长期行为污染。

## 还有一个很重要的问题：尾部 Harness 是否真的能“重新激活” Coding 能力

这个现在不能靠架构推理决定。

尤其我们刚刚讨论过 DeepSeek / Kimi / GLM 这类模型：后训练有明显的 harness-conditioned behavior，而这种 behavior 很可能对：

- system prompt 的固定形态；
- tool schema；
- reasoning mode；
- preserved-thinking lifecycle；
- 开局 trajectory；

高度敏感。

因此：

```text
稳定 Work prefix
+ 后面突然附一段
“现在你是 coding worker，请使用这些工具”
```

未必等价于：

```text
从 turn 0 就运行在 Coding Harness 下
```

可能有三种结果：

1. **很好用**：后置 overlay 足以激活 coding policy；
2. **能力下降但可接受**：适合局部 Python/数据处理，不适合复杂 repo coding；
3. **行为不稳定**：模型仍然延续 Work policy，或者在两个 policy 之间摇摆。

这必须做 trajectory eval，而不是只看最终 benchmark。

| 临时代码默认不是 Matter artifact | 哪些代码应升级成正式长期交付 |
| capability 权限由 Runtime 固定，而不是模型扩权 | Worker-native code、Code child、hybrid escalation 哪种最好 |
| Coding episode 可以被重新投影而非普通全局 compaction | 服务端 cache、KV reuse、provider-specific reasoning lifecycle 的真实成本 |

这里尤其值得避免一个实现陷阱：**不要为了“热插拔”而真的在正在执行的 tool loop 中动态改 tool registry。**

更稳定的语义应该是：

```text
Step N
Work runtime snapshot

turn boundary / admitted escalation
        ↓
new request series
Work + Code snapshot

coding episode finished
        ↓
new request series
Work snapshot
```

也就是说，“热”是对用户和 Matter 而言连续，不代表底层同一个 model request 的合同可以中途变。

这也和 DSH 的设计很协调：它本来就把 durable session facts 和 live Agent execution 分离，因此 capability transition 本身完全可以成为一个 durable event，而具体工具集合是 request compilation 时的 live projection。

我会因此把这一 PR 的目标进一步限制为：

> **证明 transient capability composition 是一个合法的一等架构概念，而不提前裁定它的最佳实现。**

PR 里甚至可以明确留下几个 `EXP-*`：

```text
EXP-01  prefix/cache behavior
EXP-02  late harness injection efficacy
EXP-03  same-worker vs delegated-child quality
EXP-04  structured reprojection vs semantic summary
EXP-05  post-episode Work-semantic retention
EXP-06  capability transition boundary
```

这样这轮不会因为想把所有问题一次解决而重新过度工程化。

真正稳定的核心只有一句：

> **Work identity is durable; execution capabilities are scoped and replaceable.**

如果最后实验证明 DeepSeek、Kimi、GLM 等模型无法可靠接受后置 Coding overlay，也没有伤害这个架构——那只是该 capability provider 最终采用 fresh child/process，而不是 same-worker overlay。反过来如果实验证明同 Worker 局部注入效果很好，就能省掉大量 handoff/context duplication。

因此这条 seam 值得现在先立，而具体 Runtime topology 应该有意保持未冻结。
