## Check against the current Chatspace and Work review UI

At the recorded HEAD, the implementation follows the proposed separation at the level of local grammar and information placement:

- **Context and activity stay in Chatspace's product conversation surface.** [`chat-measurements.mjs`](../../../../../app/web/chat-measurements.mjs) exposes a ring-only Context entry; its details retain the request estimate, serialized character count, and declared window as separate facts. [`run-activity.mjs`](../../../../../app/web/run-activity.mjs) projects Run/tool/notice events into a short activity phrase and status. The [production receipt](../README.md) records the ring beside model/effort before Send/Stop, with measurement detail on demand and no first-level TPS number. It reports 937/937 full-suite checks before the final ring relocation and reduced-motion observer, 19/19 targeted checks after those changes, then separate 390/1280 browser and lint evidence for the later geometry-only ring refinement. The local index lists `context.capacity` and `request.activity` as `reference`; real capacity and decode-TPS measurements remain deferred. This fits a quiet, task-facing projection and keeps measurement details inspectable. It is **not** a Cockpit or a historical Trace Inspector, and it does not replace Run/Telemetry inspection.
- **The Work review card is an object entry, not a Run status or approval authority.** [`work-review-summary.mjs`](../../../../../app/web/work-review-summary.mjs) reads `/sessions/:id/review-summary`, validates its Session/binding and Core summary fields, then presents the work title with pending, earlier-version, or read-only facts and opens the existing Work review. Its source comment explicitly says it sends no Work command. In [`app.mjs`](../../../../../app/web/app.mjs), the activity row is appended before the summary card; the same-Matter empty-chat path also keeps the summary discoverable. The card's final placement was recorded in commit `9672a12`; `de55674` itself only updates `engineering/current.md`. The [card delivery evidence](../../../../../evidence/work-review-object-card-20260913/README.md) records 17/17 integration checks and browser evidence, with 200% zoom and forced-colors still untested.
- **Fit is partial and bounded.** The card matches the attachment's object-first Work/review direction by naming the work and opening the existing reviewable surface. It does not implement an approvals queue, inline diff, approve/reject shortcuts, or the external ObjectOS interaction claimed in the attachment. Formal Work actions remain on the existing Core-owned review surface. This is consistent with the local `approval`/`output.review` contracts without adopting unverified vendor behavior.

The nearest implemented precedents are `runtime-view.mjs:renderContextBar` for Context composition (not a capacity meter), `telemetry-view.mjs` plus the local activity projection for request/run facts, the existing `composer` grammar for placement, and the Core Review summary opener for Work review. The specific local verification is recorded in the [Chatspace production receipt](../README.md) and [Work review card evidence](../../../../../evidence/work-review-object-card-20260913/README.md); those author checks are not independent acceptance.
