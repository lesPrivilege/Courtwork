## HPR-R1 result: fixed

`app/runtime/hermes-api-runs-adapter.mjs:156-170` now brands intents in a
closure-private `WeakSet` and records endpoint/revision. Dispatch requires
the private brand, matching endpoint/revision, frozen body, and exact allowed
keys at `:174-188`; it sends a fresh copy of only `input` and optional
`session_id`. `:214-217` brands observations, and `:353-356` requires that
brand plus endpoint identity for continuation. `settle`, `status`, terminal
stop and reconciliation records are all passed through `observe`, so the
legitimate continuation paths retain the brand. The restart test correctly
rejects an old intent object and rebuilds the same intent from Host-held key
and input.

## HPR-R2 result: one residual blocker

The constructors now validate option shapes, unknown names, positive safe
integer values, ceilings and `maxFrameBytes <= maxStreamBytes`:

- `app/runtime/hermes-api-runs-transport.mjs:72-100`
- `app/runtime/hermes-api-runs-adapter.mjs:97-150`

However, `readStatus()` still truncates native errors with the module default
at `app/runtime/hermes-api-runs-adapter.mjs:126`:

```js
error: bounded(json.error, HERMES_ADAPTER_LIMITS.maxErrorChars),
```

It must use the configured `bounds.maxErrorChars` when called by an adapter
instance. Reproduction (`luna-error-limit-probe.stdout.txt`): an adapter
constructed with `{ limits: { maxErrorChars: 1 } }` reports
`describe().limits.maxErrorChars === 1`, but a status error of 80 characters
is returned at length 80 rather than being bounded to the configured limit.
The same stale default affects terminal status/event observations. This is a
small HPR-R2 correction, but leaving it means the advertised configured error
bound is not enforced.
