## Bounded identity candidate review

The separate local candidate `4720027c13adefc1eac28f89bb3862a92fb9d9e0` preserves `observedModel` as the configured SDK/runtime identity and adds optional `providerResponse: {source:"sdk-response-metadata", model, id}` only when Pi exposes upstream response metadata. The composer labels this as a response model, rather than rewriting the old configured-model fact. The candidate bounds identifiers to 256 characters, rejects surrounding whitespace/control characters, keeps historical v1 rows readable, and makes no TPS/context changes. I independently ran `node --test app/tests/request-telemetry.test.mjs app/tests/telemetry-presentation.test.mjs app/tests/drt02-deepseek.test.mjs` at that SHA: **16/16 passed** using synthetic loopback fixtures. No material contract regression found. Astra's completed post-restart live identity probe and narrow-width/focus QA confirm the separate response identity is legible and reachable.

Separate trace note: those four Runs contain 1,391 `assistant.delta` updates, 1,093 with empty text, and 203 distinct cumulative text snapshots across seven native assistant responses. `mapSessionEvent` forwards assistant message-update text, including empty thinking updates ([pi-session-runtime.mjs](../../../../app/runtime/pi-session-runtime.mjs#L553)); this is not a token count or sampling clock. Treat deduplicating or profiling these repeated/cumulative events as a separate hypothesis until it is measured against event consumers and reliability; it is not a TPS estimate or reason to change this identity patch. Production TPS remains deferred pending the BE-42 per-request terminal-count and monotonic timing contract above.
