## Observed lifecycle

**Wakeup, polling, and heartbeat are complementary.** The daemon reconnects an authenticated WebSocket with bounded jittered backoff; the connection carries runtime IDs/capabilities and signals the poller on task availability. Teardown closes the socket, detaches pending RPCs, signals HTTP fallback, cancels the heartbeat, and only then drains the writer. The ordering prevents a queued `tasks.claim` frame from being flushed after fallback and causing a second claim ([wakeup.go](https://github.com/multica-ai/multica/blob/8c4f4328f6e3baff08394b309034463b5db9d7af/server/internal/daemon/wakeup.go#L46-L78), [wakeup.go](https://github.com/multica-ai/multica/blob/8c4f4328f6e3baff08394b309034463b5db9d7af/server/internal/daemon/wakeup.go#L99-L250)).

The WS heartbeat sends immediately and periodically, but a full write queue drops a frame; HTTP heartbeat remains the freshness backstop. The machine-level poller acquires available slots before a WS-first batch claim, starts each task under the slot, and uses a safety poll interval after an uncertain/WS claim result ([wakeup.go](https://github.com/multica-ai/multica/blob/8c4f4328f6e3baff08394b309034463b5db9d7af/server/internal/daemon/wakeup.go#L287-L376), [daemon.go](https://github.com/multica-ai/multica/blob/8c4f4328f6e3baff08394b309034463b5db9d7af/server/internal/daemon/daemon.go#L5330-L5554)).

**Claim is a database transition, not a transport acknowledgement.** `ClaimAgentTask` changes only an eligible queued row to `dispatched`, sets dispatch time and a prepare lease, verifies runtime ownership/freshness, and locks with `SKIP LOCKED`. Receipt/comment delivery and claim-failure requeue use an exact task/runtime/generation CAS. A dispatched task is reclaimed only when it has not started, its recovery age and prepare lease have expired, and the runtime remains eligible ([agent.sql](https://github.com/multica-ai/multica/blob/8c4f4328f6e3baff08394b309034463b5db9d7af/server/pkg/db/queries/agent.sql#L742-L905)).

On daemon registration/recovery, prior-incarnation dispatched/running/waiting-local-directory work is atomically marked with runtime-recovery failure; the normal failure path may then create a retry. The stale-task sweeper uses prepare-lease freshness for dispatched work and runtime-heartbeat grace for running work; local-directory waits are excluded because they are daemon-owned waits ([agent.sql](https://github.com/multica-ai/multica/blob/8c4f4328f6e3baff08394b309034463b5db9d7af/server/pkg/db/queries/agent.sql#L1303-L1395), [daemon.go](https://github.com/multica-ai/multica/blob/8c4f4328f6e3baff08394b309034463b5db9d7af/server/internal/daemon/daemon.go#L1958-L1970)).

**Execution and cancellation have a bounded handoff.** `handleTask` rejects a runtime that disappeared after claim, serializes pinned local-directory use, starts a cancellation watcher, and runs the provider with a cancellable context. A terminal server status or 404 causes cancellation; transient status errors do not. The daemon waits for the runner to return, discards the normal result on cancellation, and sends a cancel acknowledgement carrying branch/durable-workdir metadata. A failed acknowledgement is left for server sweeping, so this is cooperative cancellation with eventual settlement, not an immediate kill guarantee ([daemon.go](https://github.com/multica-ai/multica/blob/8c4f4328f6e3baff08394b309034463b5db9d7af/server/internal/daemon/daemon.go#L5626-L5869)).

Terminal callbacks are idempotent transitions: an already-terminal replay returns success, while transaction/infrastructure errors return 5xx so the daemon’s bounded retry can submit the same callback again ([daemon.go](https://github.com/multica-ai/multica/blob/8c4f4328f6e3baff08394b309034463b5db9d7af/server/internal/handler/daemon.go#L4269-L4310), [client.go](https://github.com/multica-ai/multica/blob/8c4f4328f6e3baff08394b309034463b5db9d7af/server/internal/daemon/client.go#L1124-L1165)). Retry lineage, resume session/workdir pointers, and durable worktree output are separate fields and paths: the execution options consume prior session/workdir, while `SessionRolloutMissing`/retired-session signals can clear an unusable resume pointer ([daemon.go](https://github.com/multica-ai/multica/blob/8c4f4328f6e3baff08394b309034463b5db9d7af/server/internal/daemon/daemon.go#L8550-L8675), [task.go](https://github.com/multica-ai/multica/blob/8c4f4328f6e3baff08394b309034463b5db9d7af/server/internal/service/task.go#L5945-L6035)).

## Run versus Issue status

The generic task completion path does not advance Issue status; the first-completion hook is analytics. Failure handling can reset a built-in `in_progress` Issue to `todo` only when no active task or retry remains ([task.go](https://github.com/multica-ai/multica/blob/8c4f4328f6e3baff08394b309034463b5db9d7af/server/internal/service/task.go#L4325-L4345), [daemon.go](https://github.com/multica-ai/multica/blob/8c4f4328f6e3baff08394b309034463b5db9d7af/server/internal/handler/daemon.go#L4312-L4352), [task.go](https://github.com/multica-ai/multica/blob/8c4f4328f6e3baff08394b309034463b5db9d7af/server/internal/service/task.go#L5945-L6035)).

Autopilot has explicit `SyncRunFromIssue`, `SyncRunFromTask`, and linked-issue failure methods. At this SHA, an exact search found a direct `SyncRunFromTask` call only in crash-link repair; I found no direct server call site for the Issue or linked-issue methods. Treat those methods as source-level intent until a caller/evidence path is verified, and do not infer a generic automatic Run↔Issue state machine ([autopilot.go](https://github.com/multica-ai/multica/blob/8c4f4328f6e3baff08394b309034463b5db9d7af/server/internal/service/autopilot.go#L391-L407), [autopilot.go](https://github.com/multica-ai/multica/blob/8c4f4328f6e3baff08394b309034463b5db9d7af/server/internal/service/autopilot.go#L1084-L1235)).

## CW counterexamples and adoption boundaries

Useful tests for CW would simulate: (1) a WS claim committed while its response is lost, followed by fallback polling, asserting one execution and no queued-frame replay; (2) claim-finalization failure and stale-dispatch reclaim, asserting generation/lease ownership; (3) cancellation during a slow runner, asserting no late success after cancel and eventual idempotent acknowledgement; (4) terminal callback timeout/replay, asserting one terminal record; (5) retry with a missing/retired resume session, asserting retry lineage and workdir preservation without stale-session reuse; and (6) ordinary Issue completion versus autopilot/run-only completion, asserting their distinct owners.

Do not copy WS push as the scheduler, equate claim with execution, use process-local heartbeat without HTTP/stale-lease recovery, treat retry as resume, promise immediate stop, or derive Issue status from task completion. Unknown transport outcomes should converge through idempotent callbacks and leases; they should not trigger blind re-execution. This note records behavior to compare against CW; it is not an architecture acceptance or a license decision.
