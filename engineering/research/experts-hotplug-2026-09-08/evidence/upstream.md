## Verdict

The upstream source supports the architectural direction in the index, with two boundaries that matter for the local Expert plan:

1. Cordis gives executable contributions structural ownership: a plugin/fiber owns effects, scoped registry entries, event listeners, and teardown. The same source also provides session events and projections as the durable/replayable seam. This is useful substrate evidence for the invariant **executable contribution is reversible; reviewed work state is durable**.
2. Dynamic Cordis packages are a useful lifecycle reference, not a professional-Expert security model. Definitions are process-memory state, client activation is page-local, and the host `node:vm` sandbox is explicitly not containment. A production Expert path needs a separate trust and durability contract.

The current MCP bridge is compatible with ordinary tool discovery/calls over stdio and Streamable HTTP, including a stateless Streamable HTTP fixture. It does **not** implement MCP Tasks: a tool advertising `execution.taskSupport: "required"` is rejected before `tools/call`, and there is no `tasks/get`, `tasks/update`, or `tasks/cancel` path in the bridge. Therefore the index may treat MCP as a capability ingress, but must keep a remote long-running Expert-task abstraction as an unresolved adapter boundary.

## MCP compatibility check

### Official protocol facts checked

- The official 2026-07-28 release describes a stateless MCP core, per-request self-description, Streamable HTTP changes, auth hardening, and a formal extensions framework. It moves Tasks out of the experimental core into `io.modelcontextprotocol/tasks`: [MCP 2026-07-28 release](https://blog.modelcontextprotocol.io/posts/2026-07-28/) (accessed 2026-09-08).
- The official Tasks overview describes a durable task handle that survives disconnects, progressive-enhancement capability negotiation, server-managed durable state, and polling through `tasks/get`; it defines `working`, `input_required`, `completed`, `failed`, and `cancelled`. [MCP Tasks overview](https://tasks.extensions.modelcontextprotocol.io/) (accessed 2026-09-08).
- The draft Tasks specification requires the server to make a task durable/findable before returning its handle, tells clients to persist task IDs across crash/restart, and defines `tasks/get`, `tasks/update`, and `tasks/cancel`. It also defines task-handle routing and explicit failure/TTL behavior. [MCP Tasks specification](https://tasks.extensions.modelcontextprotocol.io/specification/draft/tasks) (accessed 2026-09-08).

### Compatibility consequence for the local Expert plan

Use MCP as an optional capability provider behind the Expert's policy gate. Ordinary request/response tools can participate in the native tool pipeline. A remote long-running legal-research or review task cannot be claimed compatible with the current DSH bridge merely because the server is MCP: it needs a separate adapter that negotiates the Tasks extension, persists task IDs and state, polls/updates/cancels, and maps task outcomes into durable local Expert events. Keep the remote task abstraction independent of MCP so a private SaaS connector and another transport can share the same local state contract.

## Reuse / adapt / reject for reconciliation

| Upstream mechanism | Local disposition | Reason |
|---|---|---|
| Fiber/effect ownership and scope-derived registry layers (DSH-02/03) | **Reuse concept** | Directly supports reversible executable contributions, scope isolation, and quiescent unload. |
| Session event log, typed event map, projection, Conversation definitions/fallback (DSH-05/06) | **Reuse concept; verify local owner** | Best match for durable Expert state plus renderer-independent replay. Do not let a browser package become the canonical store. |
| Native tool registry + independent approval/guard pipeline (DSH-07/08) | **Reuse concept; add local metadata** | Keeps MCP/provider capabilities policy-governed after discovery. Add egress/principal/license/trust metadata locally. |
| Dynamic Cordis version/run/stop/undefine and host/browser split (DSH-09/10) | **Adapt** | Keep immutable versions and distinct lifecycle states, but use a stronger trust class for professional Experts and a durable store for findings/decisions. |
| DSH `node:vm` as a security boundary | **Reject** | Upstream explicitly disclaims containment and documents async timeout escape. |
| Current DSH MCP bridge as a remote durable-task implementation | **Reject / defer adapter** | It rejects required task execution and bridges only Tools; no Tasks state machine or persistence is present. |

## Unsupported extrapolations to keep out of the local plan

- DSH dynamic package definitions are not durable across a process restart; this is not a precedent for deleting Expert-produced findings on uninstall.
- A generic Chat JSON fallback proves only that a missing renderer can avoid a blank row for the covered node/event paths. It does not prove every historical Expert payload can render without a versioned fallback envelope.
- Separate host/browser runners prove independent runtime halves, not independent durable state. The host/client source and run identity must be correlated, while canonical review state remains store-owned.
- MCP tool discovery does not imply MCP Tasks support, durable remote work, or data-governance policy. Those need explicit adapters and local policy metadata.
- The upstream source review did not validate the local repository's current seam implementations, schema choices, or package build contracts; those remain the parent agent's local reconciliation work.
