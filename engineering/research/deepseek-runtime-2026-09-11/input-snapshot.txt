### 1. 官方证据：这种耦合是真实存在的

最强的三条不是社区猜测，而是 DeepSeek 自己写出来的。

第一，V4 后训练本身就单独培养 **agent expert**。V4 论文写得很明确：先分别训练 mathematics / coding / **agent** / instruction-following 等 domain expert，经 SFT + GRPO RL，再通过 on-policy distillation 合回统一模型。[DeepSeek-V4 Technical Report](https://arxiv.org/html/2606.19348)

而且这个 Agent RL 不是纯文本 RL。论文还专门有 `Sandbox Infrastructure for Agentic AI`；其训练基础设施 DSec 覆盖 function、container、microVM、VM 等真实执行环境。因此更准确的理解不是：

`Model intelligence → arbitrary harness`

而是：

`post-trained policy × interaction environment → realized capability`

第二，DeepSeek 自己公开的 V4-Flash Code Agent 成绩就**绑定了 Harness 配置**。7 月 31 日 changelog 明确注明：

> public Code Agent benchmarks 使用 **DeepSeek Harness Minimal mode + max reasoning effort**，并给出对应 sampling 设置。

[DeepSeek Change Log](https://api-docs.deepseek.com/updates/)

而官方 DSH 的 Minimal 不是一句 prompt，而是一个真实 runtime mode：**persistent bash + str_replace_editor 两个工具**；Standard 则暴露完整 coding-agent toolset。[DeepSeek Harness](https://www.deepseek.com/harness/en/)

所以 Benchmark 的结果实际上是：

`V4-Flash + Max + DSH Minimal`

而不是抽象意义上的“V4-Flash”。

第三，V4 的 continuation protocol 本身已经穿透普通 OpenAI-compatible abstraction。当前官方文档规定：

- thinking 默认开启，默认 effort=`high`
- 当前 effort 是 `low / high / max`
- thinking mode 下 temperature/top_p 等事实上无效
- **只要 request 带 `tools`，此前 assistant 的 `reasoning_content` 就必须完整回传到后续请求**
- 少了会直接 `400`
- 不带 tools 时则无需如此处理

[Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)

这正是 OpenCode 在 V4 刚上线时踩中的坑：普通 message persistence / normalization 把 `reasoning_content` 丢掉，第一轮正常，工具调用后续行直接 400。[OpenCode #24190](https://github.com/anomalyco/opencode/issues/24190)

这件事非常适合作为 CW runtime seam 的第一块试金石。

### 2. PI / DSH / OpenCode / Codex 给出的共同答案

四家路径不同，但实际上正在收敛到同一个架构事实。

| 实践 | 暴露出的事实 | CW 应消费什么 |
|---|---|---|
| DSH | DeepSeek 有独立 `llm-deepseek` adapter，reasoning effort、replay、cache accounting 都由 adapter 负责 | Provider dialect 不进入 agent loop |
| PI | generic provider 仍需 `thinkingFormat: deepseek`、reasoning level map 等 compat metadata | “OpenAI compatible”不足以描述 capability |
| OpenCode | reasoning metadata 一旦在 persistence / resume / model switch 中丢失，agent loop 就坏 | Runtime protocol state 必须可持久化、可重放 |
| Codex | DeepSeek 官方不仅配置 `base_url`，还给 Codex 写 `models.json`，描述 reasoning levels、tool format、context、apply_patch 等 | 模型需要 **runtime capability manifest** |

最后一项尤其有意思。DeepSeek 官方现在原生支持 Codex Responses API，但明确只是**部分兼容**：`previous_response_id`、server conversation/store 不支持，MCP、computer use 等内建 tools 也并不因此自动成立；同时它为 Codex 提供完整 model catalog 来声明 capability。[Responses API](https://api-docs.deepseek.com/guides/responses_api) · [Codex integration](https://api-docs.deepseek.com/quick_start/agent_integrations/codex/)

所以：

> **wire compatibility、model capability、harness behavior 是三个不同维度。**

这正好给 CW 一个很干净的抽象切口。

```text

     │
     │ domain intent / governed matter / expected artifact
     ▼
ExpertRuntime contract                  ← CW 稳定 seam
     │
     ├── DeepSeekRuntime                ← 第一份实现

     │      ├─ context projection
     │      ├─ tool-surface policy
     │      ├─ continuation/replay state
     │      └─ recovery / budgets
     │
     ▼

     ├─ Run lifecycle
     ├─ tool execution / approval
     ├─ event log
     ├─ artifact

     │
     ▼

     ├─ auth
     ├─ model catalog
```

`DeepSeekRuntime` 真正拥有的是：

**“如何让这个模型在 CW 环境里把已训练能力实现出来。”**

于是以后：

```text
ContractExpert
    ├── DeepSeekRuntime
    ├── CodexRuntime
    ├── GeminiRuntime
    └── SovereignRuntime
```

Expert 本身不需要知道这些名字。

## 4. 最重要的一刀：新增 Runtime State，而不是污染 Matter / Session

DeepSeek 的 `reasoning_content` 是最好的反例。

它：

- 必须 durable，否则 resume 后可能无法继续；
- 必须 fidelity-preserving，否则 provider 会拒绝；
- 但它显然又**不是 Matter Truth**；
- 也不应该成为换 Gemini/Codex 后默认塞回模型的工作上下文。

所以 CW 原来的三层现在可以更清晰地补一条支线：

```text
Event Log
   ├── Matter projection          durable + governed + provider-neutral
   ├── Runtime protocol state    durable + runtime-scoped
   └── Compiled Model Context    ephemeral + model/runtime-dependent
```

例如：

```text
runtimeState:
  runtime: deepseek-v4
  requestSeries: ...
  reasoningReplayRefs: [...]
  toolCallProtocol: ...
  effectiveEffort: max
  toolSurfaceHash: ...
  contextProjectionHash: ...
```

**Matter 不知道 `reasoning_content`；DeepSeekRuntime 知道。**

这样才能同时实现：

1. DeepSeek session resume 不坏；
2. Work Session 不绑定 DeepSeek；
3. 将来中途换 runtime 时，不会错误地把 DS 私有 trajectory 当成通用 memory；
4. trace 仍然完整可验。

这块其实是此次验证里价值最高的架构成果。

对应 modeltest 的实验则提示：

- V4 Pro 对首轮 tool schema surface 特别敏感；
- Flash 更受 persona 影响；
- Standard / Minimal 会产生明显不同 trajectory；
- two-stage anchor → promote 在该测试中优于一开始暴露全部工具。

这些非常有意思，但应该进入：

```text
DeepSeekRuntimeProfile
├── native
├── constrained-bootstrap
└── experimental-anchor
```

而不是：

```text
if DeepSeek:
    tools = [bash, str_replace_editor]
```

Courtwork 不是 coding agent，更不应该机械搬两个 coding tools。我们真正要验证的是更一般的命题：

> **“较小、稳定、任务相关的初始 capability surface，是否更容易唤起 DeepSeek 后训练出的 agent policy；随后渐进披露能力是否优于一次性全量曝光？”**

这与 CW/SE 自己一直采用的 progressive disclosure 恰好可以做实验性交叉验证，但两者先不要混成同一理论。

## 6. 建议第一轮直接切成一个 DS Runtime Probe

我会把施工范围压得很小：

**DS-R0 — Contract。** 定义 `ExpertRuntime`、`RuntimeCapabilities`、`RuntimeProfile`、`RuntimeProtocolState`；不出现 DeepSeek 字样。Expert 只提交受治理 ContextPack、allowed capabilities、artifact expectation。

**DS-R1 — DeepSeek native。** 官方 `deepseek-v4-flash` 为首个默认模型，Provider 处理 Chat/Responses wire；Runtime 支持 `off / low / high / max` capability discovery，而不是把枚举永久写死。完成 reasoning/tool replay、stream、usage、cache hit、cancel/error。

**DS-R2 — Resume torture test。** 强制执行：

`user → reasoning → tool → result → reasoning → tool → result → final → persist → process restart → resume`

然后证明 `reasoning_content` 正确恢复，而 Matter 中查不到这些 provider-private state。

**DS-R3 — Harness A/B。** 同一 fixture，至少比较：

```text
full tool surface × high
full tool surface × max
constrained bootstrap × high
constrained bootstrap × max
```

Flash/Pro 可以后续再展开，不必首轮组成 2×4 大矩阵。

**DS-R4 — Expert decoupling proof。** 同一个 Expert 不改代码，用一个 deterministic/fake runtime 或第二 runtime 执行。若 Expert 中出现 `deepseek-v4-*`、`reasoning_content`、`reasoning_effort`、DSML 等字段，此 gate 直接失败。

### 验收指标也应该同时固定

不只看“任务做完没有”，而记录：

`task outcome / tool-call validity / step count / reasoning tokens / visible tokens / TTFT / wall time / cache hit / schema bytes / context bytes / protocol retries / runtime error class / artifact validity`

尤其把 **tool surface hash、runtime profile hash、provider/model revision** 写进 Run trace。否则未来 V4 再 re-post-train，一次能力变化会被错认成 CW regression。

## 最终裁决

**我赞成现在做，而且时点恰好。**

DeepSeek 是比 Gemini 更好的第一个 Runtime seam 验证对象，因为它有三个罕见条件同时成立：

1. 官方明确披露了 **agent-specific post-training**；
2. 官方自己的成绩明确受到 **Harness Minimal + reasoning effort** 条件影响；
3. API 又存在足够棘手但可精确定义的 **provider-specific continuation semantics**。

因此它可以一次验证三件事：

> **Provider 能否隔离 wire；Runtime 能否封装 capability realization；Expert 能否完全不认识 Harness。**

如果这条线跑通，后续 Codex、PI-like、Gemini、主权模型就不再是“重新设计 CW”，而只是继续给同一个 `ExpertRuntime` seam 提供新的实现与 profile。对于 CW 当前阶段，这比直接继续堆第二、第三个 provider 更有架构信息量。

# 四、逐个冻结定义

## 1. Model / Provider Adapter

这是最靠近供应商的一层。

建议定义：

> **Adapter translates one provider/model protocol into the Harness model seam.**

它负责：

```text
identity / auth
model catalog
capability metadata
request serialization
stream normalization
thinking/reasoning mapping
tool-call wire format
provider-specific replay state
usage/cache/error normalization
```

DeepSeek 的 `reasoning_content`、Codex Responses 的 encrypted reasoning、Anthropic thinking blocks，全应该死在这里或紧邻它的 provider-specific runtime state。

### 注意不要只叫 `Adapter`

CW 后面还需要另一种 adapter。

建议正式区分：

- **Model Adapter**：Provider/API → Harness LLM seam
- **Runtime Adapter**：Codex/Pi/DSH → CW Harness Runtime Port

这样不会重演“adapter 到底在适配谁”的混乱。

---

# 五、Harness Core：这里最接近 Pi Agent Core

建议定义：

> **Harness Core is the minimal provider-neutral execution spine that repeatedly turns model decisions into governed actions and observations.**

它可以稳定拥有：

```text
Run / Turn / Step lifecycle
model-call loop
normalized model messages
tool registry + dispatch lifecycle
stream/event emission
continuation
steer / interrupt
retry hooks
context-input seam
basic execution receipts
```

这里甚至可以暂时不拥有：

```text
multi-agent
browser
computer use
workflow engine
specialized memory
domain review
Matter
Expert
UI
```

Pi 的 `pi-agent-core` 是目前最接近这一概念的外部实现。

DSH 的 core 略宽，但其 agent-loop 本身也遵循这一原则。

---

# 六、Harness Capability 比 “Harness Extension” 更适合作为 Canon

这里是你感觉到的“中间一层”。

建议：

> **Capability is a replaceable, discoverable facility available to a Harness Runtime. Extension is one packaging mechanism by which capabilities are contributed.**

典型：

```text
filesystem
shell / terminal
sandbox
browser
computer use
MCP
skills
subagent
multi-agent coordination
jobs
workflow
web/search
generic user question
generic approval
compaction policy
runtime telemetry
```

这也符合 MCP 2026 的思想。MCP 本质上是 capability protocol：Host 协调多个 Client，Server 只暴露 resources / tools / prompts，capability negotiation 决定本次请求可用什么，而不是让 MCP 定义上层工作 ontology。  
[MCP Architecture](https://modelcontextprotocol.io/specification/2026-07-28/architecture)

这正好支持 CW 之前的：

> **Expert owns work semantics; MCP exposes capabilities.**

---

# 七、Runtime 不应该再被定义成“一层代码”

这一点我建议现在就裁掉歧义。

以后：

> **Runtime = a resolved executable composition, not an ontology layer.**

比如：

```text
DeepSeek Runtime
=
DeepSeek Model Adapter
+ Harness Core
+ selected Harness Capabilities
+ Runtime Profile
+ Environment bindings
```

或者：

```text
Codex Runtime
=
Codex Core
+ its tool/runtime capabilities
+ App Server
+ selected config
```

所以我们才可以说：

```text
Codex is a runtime
Pi can host a runtime
DSH profile resolves to a runtime
```

而不会再问“Runtime 和 Core 谁包谁”。

---

# 八、于是你问的 “Adapter + Core ≈ DSH Minimal?”——差一个 Capability Profile

严格说：

```text
Model Adapter
+ Harness Core
```

比 DSH Minimal 还更薄。

DSH Minimal 更接近：

```text
DeepSeek Model Adapter
+ Harness Core
+ Session/Event substrate
+ Prompt/context assembly
+ bash capability
+ str_replace_editor capability
+ filesystem/execution environment
+ technical permission policy
+ Minimal Runtime Profile
```

即：

> **Minimal 是一个 Runtime Profile，而不是 Core。**

这个区别非常重要。

以后 DeepSeek 那些“Minimal trajectory”实验应写成：

```text
runtime_profile = deepseek.minimal
```

而不能让两把工具进入 `HarnessCore`.

# 九、再往外一层才是 CourtWork 真正应该自己拥有的 Work Core

这里是 CW 与 PI/DSH/Codex 分家的地方。

建议定义：

> **Work Core is the provider- and harness-independent substrate for durable governed work.**

它拥有的不是 agent execution，而是：

```text
Matter
Matter State
Work Event
Source / Evidence / Provenance
Artifact / Candidate / Revision
Review
Authority
Commitment
Open Obligation
Attention
Role
Organization Policy
Version / Freshness
State Transition
Context Projection policy
```

以及数据与组织工程：

```text
who may know
who may act
who may propose
who may review
who may commit
which source/revision governs
which evidence supports which proposition
what remains unresolved
```

这里尤其应继续坚守：

```text
execution receipt ≠ work commitment
runtime approval ≠ professional approval
session ≠ matter
trace ≠ work state
```

CW 既有 UI 研究也已经裁定：

> elicitation、permission、proposal review、commitment 必须分开。fileciteturn13file7L607-L620

# 十、Schema / Work Contract / Expert 不应该三选一

这是我这一轮最想固定的概念。

它们其实是三个不同层级。

### Schema

继续保持 SE 原义，不要膨胀：

> **Schema defines what professional state means.**

它描述：

```text
entities
fields
relations
states
invariants
evidence bindings
version semantics
```

例如 NDA：

```text
Clause
Position
Deviation
Evidence
Finding
ProposedEdit
ReviewDecision
```

Schema 是 **semantic IR**。

不是 agent、不是 plugin、不是完整 workflow。

---

### Work Contract

建议保留，而且比 Sigma 好得多。

定义为：

> **A Work Contract defines what must become true for one bounded class of professional work to count as validly completed.**

包含：

```text
required inputs
required outputs
applicability
evidence obligations
validation gates
authority requirements
review obligations
completion conditions
failure / escalation rules
```

这与近期 Anthropic 自己在 harness research 中开始使用的 `sprint contract / default-FAIL contract` 语义也天然对齐：先约定 done 是什么、需要什么证据，再执行。

而 CW 的定义会更严格，因为它包含 professional authority/commitment。

---

### Expert

Expert 是更大的发布/复用单位：

> **Expert is a versioned, governed, host-independent professional capability package composed from schemas, work contracts, policies, verifiers and capability requirements.**

即：

```text
Expert
├── Domain Schema(s)
├── Work Contract(s)
├── Instructions / Methods
├── Retrieval / Disclosure Policy
├── Capability Requirements
├── Verifiers / Eval
├── Review / Commit Policy
├── Surface Semantics
├── Compatibility / Freshness
└── Version / Provenance
```

这实际上已经与 9 月 8 日冻结结构一致。fileciteturn13file0L60-L82

所以我建议正式关系冻结为：

```text
Schema < Work Contract < Expert
```

而不是选一个名字覆盖三个概念。

---

# 十一、`Sigma` 暂时不要进 Architecture Canon

我不建议用 Sigma 作为工程层级名。

它的问题不是不好听，而是：

- 无外部共同含义；
- 一眼无法知道承担什么 contract；
- 很容易变成产品品牌、内部 codename 与 ontology 混用；
- 会遮蔽目前终于变清楚的 `Schema / Contract / Expert` 三分法。

如果以后想做产品化命名：

```text
Sigma
```

可以是 Expert ecosystem、compiler 或 package format 的品牌名。

但不要让：

```text
Sigma = schema?
Sigma = expert?
Sigma = work contract?
```

进入技术文档。

# 十二、还缺一个非常关键的中间层：Work Compiler

这里正对应你说“如果调伏 Codex 作为 runtime，只引入 Work Core 和 Contract”的感觉。

实际上不能让 Expert 自己直接向 Codex：

```text
register_tool()
mount_mcp()
set_reasoning()
add_ui()
spawn_agent()
```

否则 Expert 很快重新耦合 Harness。

中间应该有：

# **Work Compiler**

既有历史里已经出现过这个东西，只是名字曾在 `Activation Planner / Preset Binder / Expert Router / Primitive Composer` 之间漂移。

8 月 29 日版本的架构已经写成：

```text
Request + Matter + Role + Stage
              ↓
Activation Planner
├── Preset Binder
├── Expert Router
└── Primitive Composer
              ↓
Compiled Expert
+ Matter Projection
+ Permission Envelope Intersection
              ↓
Executable Run Plan
              ↓
Shared Core execution
```

并且明确 Shared Core “只知道运行、装载、退出、记录、恢复和 fail closed，不知道合同怎样审”。fileciteturn13file3L287-L316

我建议现在把它统一为：

```text
Work Compiler
```

下面三个内部机制可以继续叫：

```text
Preset Binder
Expert Router
Primitive Composer
```

# 十三、Work Compiler 的职责就是跨越 Work ↔ Harness 的唯一桥

输入：

```text
Matter Projection
+ Role
+ Stage
+ Expert
+ Work Contract
+ Organization Policy
+ Available Runtime Capabilities
+ User / Authority envelope
```

输出：

```text
Executable Run Plan
```

例如：

```yaml
run:
  matter: contract/acme-nda
  expert:
    id: legal.nda_review
    version: 1.4.0
  contract:
    id: inbound_nda_review
    version: 3

  context:
    projection: nda.review.v2

  requirements:
    capabilities:
      - document.read
      - document.patch
      - authority.search
    interaction:
      - elicitation
      - review
    execution:
      sandbox: optional

  authority:
    propose: agent
    review: legal_reviewer
    commit: legal_reviewer

  outputs:
    - finding_set
    - proposed_redline

  completion:
    verifier: nda.coverage.v3
```

注意这里没有：

```text
Codex
DeepSeek
reasoning_content
MCP stdio
Claude hooks
DSH ctx.tools
```

然后 Runtime Adapter 再把这个 Run Plan 编译为对应 Host 能理解的配置。

# 十四、因此 “Expert 注入工具、插件、MCP、权重、HITL、UI” 要稍作改写

你的直觉对，但“Expert 直接注入”会破坏刚刚取得的解耦。

更精确应该是：

```text
Expert declares requirements and work semantics.
Work Compiler resolves them.
Harness capabilities realize them.
```

比如：

| Expert 声明 | Harness 最终实现 |
|---|---|
| `document.search` | MCP / native tool / remote API |
| `browser.verify` | Playwright / Codex browser / Computer Use |
| `parallel_research` | subagent / agent team / sequential fallback |
| `human.review.redline` | CW Review Surface + runtime pause primitive |
| `private_model` | provider routing |
| `structured_output` | model native JSON / verifier / parser |
| `legal_authority_search` | private MCP / SaaS MCP / local index |

这样 Expert 热插拔的本质才真正与 DSH plugin composition 相似：

> **相似的是 composability；不相同的是 ownership。**

DSH Plugin 可以包含 executable implementation。

CW Expert 首先是 **professional semantic package**。

# 十五、“权重”尤其不要作为 Expert 直接资产

这里建议特别严格。

Expert 可以声明：

```text
preferred capability profile
minimum model capability
approved model family
eval-qualified runtime profiles
```

但不应该写：

```text
load DeepSeek-V4-Pro-Max
reasoning_effort=max
```

作为专业语义本身。

否则模型升级一次，Expert version 就无意义地跟着抖。

更合理：

```text
Expert
    ↓
Capability Requirements
    ↓
Runtime Qualification Registry
    ↓
DeepSeekRuntime v4-pro/max
CodexRuntime gpt-x/high
SovereignRuntime ...
```

这与我们此前“model-specific scaffolding 会折旧，而 semantic work contracts 会积累”的 SE 判断完全一致。fileciteturn8file3L791-L797

# 十六、HITL 同样应该拆成两半

这是个很容易混淆的地方。

Harness 提供：

```text
pause
ask
confirm
approve tool
resume
interrupt
```

这些是 generic HITL primitives。

Expert / Work Core 定义：

```text
这个 finding 是否必须律师复核？
这项偏离谁有权接受？
这个 redline 是 proposal 还是 committed version？
什么情况下必须升级 partner？
```

这些是 **professional authority semantics**。

所以：

```text
Harness approval
≠
Work review
≠
Commit authority
```

这是必须进入概念文档的硬边界。

# CourtWork Visual Compilation · supplementary intake

Status: **distilled precedent / external-practice index**, not a new architecture decision.

This note recovers the useful parts of the earlier Visual Compiler / Kami discussion that were not previously entered into the repository, and reconciles them with the newly frozen CourtWork architecture vocabulary.

The purpose is not to adopt another visual style or install a visual-generation framework. The purpose is to make diagrams, explanatory graphics, screenshots and generated illustrations **governed artifacts whose semantics, source, maturity and acceptance can survive different agents and renderers**.

## 1. Prior-chat decisions worth carrying forward

### VC-01 · Use “CourtWork Visual Compilation” as the working concept

Prefer:

> **CourtWork Visual Compilation**

over a narrow “illustration skill”.

The surface is broader than image generation. It covers:

- architecture diagrams;
- process/state diagrams;
- product explanatory figures;
- product screenshots and annotated screenshots;
- icons and stable semantic SVG;
- generated editorial illustrations;
- publication-page visual explanations.

The useful abstraction is therefore a **visual compilation pipeline**, not an image generator.

---

### VC-02 · Consume Kami's governance skeleton, not its house style

[Kami](https://github.com/tw93/Kami) is useful as precedent because it treats visual production as a constrained pipeline with source, schema, render and verification.

Do **not** inherit its visual identity wholesale:

- parchment;
- ink blue;
- serif-led hierarchy;
- print/editorial composition;
- its specific template family.

CourtWork already owns a different product/publication visual language.

What should be extracted is the process:

```text
intent
  ↓
execution / output contract
  ↓
content or semantic IR
  ↓
schema / invariant check
  ↓
layout / figure selection
  ↓
render
  ↓
deterministic checks
  ↓
perceptual visual review
  ↓
accepted artifact
```

This is the strongest reusable idea from Kami.

Kami itself now makes the same distinction explicitly: content schemas are filled and validated before layout, and maintained repo diagrams are treated as source assets rather than one-shot images.

## 2. Three visual asset classes

Do not put every visual task through the same renderer.

### A. Canonical semantic icon / SVG

Use when the visual object has stable interaction or product semantics.

Examples:

- Review;
- Matter;
- Attention;
- artifact/document states;
- stable control/icon slots.

Properties:

```text
small
repeatable
semantic
token-governed
implementation-owned
```

These belong closer to the design system / icon registry than to Visual Compilation.

They should not be regenerated casually by an image model.

---

### B. Governed diagram

Use when correctness depends on explicit objects and relations:

- architecture;
- ownership;
- state transitions;
- lifecycle;
- compilation path;
- permission / review flow;
- data flow;
- dependency topology.

Properties:

```text
semantic source
→ typed nodes / edges / groups
→ validated visual view
→ SVG / HTML / PNG projection
```

This is the preferred class for the newly frozen architecture.

A governed diagram should be reconstructible from its semantic definition and visual contract.

---

### C. Generated illustration

Use only where the claim is inherently illustrative rather than topological:

- analogy;
- editorial explanation;
- conceptual scene;
- visual metaphor;
- expressive campaign material.

Image generation is the renderer, not the source of truth.

The brief is the governed artifact.

A generated illustration should therefore begin from something like:

```yaml
claim:
placement:
smallest_display_size:
accepted_reference:
must_preserve:
must_not_show:

visual_grammar:
  shape:
  material:
  identity:
  motion:
  annotation:

composition:
  focal_point:
  reading_direction:
  complexity:
  density:

semantic_constraints:
  maturity:
  authority:
  state_distinctions:

qc:
  - ...
```

A generated image that violates the brief is regenerated or rejected; the semantic contract is not patched to explain the output.

## 3. Architecture diagrams should become a maintained asset class

The earlier chat proposed keeping maintained diagrams roughly as:

```text
semantic / prompt contract
+ editable source
+ rendered projection
```

Kami now provides a particularly useful concrete precedent:

```text
prompt.md
index.html + inline SVG
rendered PNG
```

Its important rule is not the exact file format. It is:

> Never redraw a maintained diagram from memory.

Before a visual agent touches an existing diagram it should consume:

```text
1. semantic / figure contract
2. current editable source
3. current rendered output
4. architecture / DEC facts that define its named objects and edges
```

Then update all projections together.

For CourtWork, a stronger native form could eventually become:

```text
figure.contract.*
figure source / model
SVG
optional PNG
registry entry
verification receipt
```

Exact representation should remain an implementation choice until Codex reviews current repo constraints.

## 4. Separate model from view for architecture figures

This is the strongest addition from the new Exa sweep.

[Structurizr](https://docs.structurizr.com/as-code) explicitly separates an architecture **model** from its **views**.  
[LikeC4](https://likec4.dev/) similarly keeps a textual architecture model as source and generates multiple views, with Git versioning, validation, diff and agent/MCP access.

This maps extremely well to CourtWork.

Do not let:

```text
F1 ownership diagram
F2 compile flow
F3 runtime anatomy
README compact architecture
Pages explanatory architecture
```

be five independently authored SVGs.

Prefer conceptually:

```text
Architecture Model
    │
    ├── View: ownership
    ├── View: compile path
    ├── View: runtime anatomy
    └── View: README compact
```

The model contains canonical:

- elements;
- containment;
- ownership;
- allowed relationships;
- maturity/state where needed.

A view decides:

- which elements are visible;
- reading direction;
- grouping;
- focal hierarchy;
- labels appropriate to its audience.

This is more durable than ordinary Mermaid-as-source because Mermaid normally mixes semantic structure and particular presentation into one artifact.

### Candidate external implementations

**Structurizr**  
Strongest precedent when strict C4 hierarchy and model/view discipline matter.

**LikeC4**  
Especially interesting for CourtWork because it provides:

- configurable semantic vocabulary;
- textual model;
- multiple generated views;
- validation;
- Git diff;
- interactive/static embedding;
- MCP/API surface;
- PNG / Mermaid / D2 / DrawIO export.

Neither should be adopted merely because it exists. Codex should first determine whether CourtWork's architecture vocabulary fits their model without distortion.

## 8. Visual Grammar should be governed separately from semantic IR

Earlier exploration produced a useful candidate grammar:

```text
Shape
Material
Identity
Motion
```

Retain it as **visual grammar**, not architecture ontology.

Possible interpretation:

### Shape

Geometry and silhouette:

- corner system;
- line curvature;
- container shape;
- boundary treatment;
- marker shape;
- density.

### Material

Surface treatment:

- solid / translucent;
- line weight;
- blur;
- border;
- fill;
- paper/glass/metal-like abstraction where justified.

### Identity

What makes an otherwise structurally correct artifact feel like CourtWork:

- characteristic annotations;
- line/rule use;
- sparse attention accent;
- typography;
- figure numbering;
- distinctive object treatment;
- recurring diagram motifs.

### Motion

How meaning changes over time:

- reveal;
- progression;
- state transition;
- trace;
- focus;
- compare.

Motion should explain a process or relationship, never rescue an incomprehensible static figure.

This layer can evolve substantially without changing the semantic model.

## 10. External precedent: design contracts for agents

Several 2026 projects independently converge on storing visual judgment as machine-readable project state rather than prompt folklore.

### Oh My Design

[Oh My Design](https://github.com/3x-haust/oh-my-design) is high-signal as **process precedent**, not as a dependency.

Its durable loop is approximately:

```text
brief
→ evidence
→ copy
→ typography proof
→ composition contract
→ isolated structural candidates
→ production build
→ rendered critique
→ reframe
```

Particularly relevant ideas:

- builder and visual reviewer can be separated;
- references are evidence rather than aesthetic command;
- final design inputs are hash/freshness bound;
- screenshots/renders become review evidence;
- generated cache can be deleted without deleting design intent.

For CourtWork, this reinforces:

```text
visual intent / contract = durable
render cache = disposable
```

### `.design`

[AgentsORG/DESIGN](https://github.com/AgentsORG/design) proposes a machine-readable “living visual contract” including:

- identity;
- intent;
- tokens;
- components;
- patterns;
- rationale;
- policies;
- constraints;
- examples;
- integrations.

The implementation is very early and should not be taken as a mature standard.

The useful pattern is narrower:

> **Design decisions that agents must preserve should have one inspectable versioned contract rather than being reconstructed from screenshots every session.**

CourtWork already has stronger design/governance machinery, so this is supporting evidence rather than an adoption candidate.

建议统一改成：

> **expert-operated prototype**

或在强调协作时：

> **expert-guided prototype**

这样不会让读者误以为“Expert package 的 prototype”。

---

### 2. `manual Agent loop` 改为 `expert-guided work trajectory`

旧称：

> 专家手动 Agent loop  
> repeated manual loop  
> expert manually drives the frontier Agent loop

建议统一抽象为：

> **expert-guided work trajectory**

需要强调多次迭代时：

> **repeated expert-guided work trajectories**

需要强调仍处于原型阶段时：

> **expert-operated frontier workflow**

其含义是：

```text
human expert
  identifies the assignment
  selects / rejects context
  changes search strategy
  supplies unstated assumptions
  reviews intermediate work
  redirects / retries
  judges materiality
  escalates
  decides whether work is complete
```

底层可以使用任意 Agent Runtime，但这些轨迹本身不是 Runtime。

---

### 3. `hidden human harness` 改为 `latent work semantics`

旧命题：

> **The expert prototype contains a hidden human harness.**

建议修为：

> **An expert-operated prototype contains latent work semantics that have not yet been externalized into the system.**

更完整的版本：

> **An expert-operated prototype often succeeds because the human expert manually supplies work-contract, compilation, and adjudication decisions that the system has not yet externalized.**

这样保留原洞见，同时不再把所有专家判断都叫做 Harness。

可以把旧的 “hidden human harness” 保留为历史解释性比喻，但不再作为 canonical term。

---

### 4. “author occupies the missing runtime” 应明确废止

旧句：

> The prototype works because the author occupies the missing runtime.

建议改成：

> **The prototype works because the author manually supplies missing work semantics around the runtime.**

更精确：

> **The runtime executes the work, but the expert still supplies the missing decisions about context, evidence, completion, escalation, review, and authority.**

或者更符合这轮新架构：

> **The prototype works because the expert is manually performing parts of the Work Compiler and Work Contract that have not yet been made explicit.**

其中最后一句最有解释力，但不能把所有人工判断都塞进 Work Compiler：有些最终属于 Work Core / Review / Organization Policy。

---

### 5. Prototype → Product 应从“复制 loop”改成“提取并治理工作语义”

推荐主命题：

> **Productizing an expert-operated prototype means externalizing the reusable parts of its latent work semantics without pretending that expert judgment disappears.**

展开为：

```text
Expert-guided work trajectories
        ↓ observe / classify
Domain invariants
Institution conventions
Matter-specific context
Individual preferences
        ↓ promote selectively
Schema
Work Contract
Organization Policy
Review / Authority Policy
Capability Requirements
Eval / Verifiers
        ↓ package + qualify
Candidate Expert
        ↓ held-out evaluation / review / release authority
Committed Expert Version
```

运行时则另走：

```text
Expert + Matter + Policy
        ↓ Work Compiler
Executable Run Plan
        ↓ Runtime Adapter
Replaceable Runtime
```

这两条链不能再混成一条 “manual loop → harness”。

---

### 6. Practice 文 Expert promotion 链建议修成

旧：

```text
frontier composition / repeated manual loop
→ Candidate Expert Profile
→ applicability / exclusions
→ provenance / source demonstrations
→ Work Contract and primitive dependency graph
→ held-out E2E + risk-stratified Review
→ accepted-work-product / disagreement / reversal observation
→ release Authority
→ Committed Expert Version
```

建议：

```text
expert-guided demonstrations / work trajectories
→ extracted work semantics
→ Candidate Expert
→ applicability / exclusions
→ provenance / source demonstrations
→ Schema + Work Contract + capability requirements
→ verifier / eval + review / authority policy
→ held-out E2E + risk-stratified Review
→ accepted-work-product / disagreement / reversal observation
→ release Authority
→ Committed Expert Version
```

其中：

- `primitive dependency graph` 可降为实现层术语；
- `capability requirements` 更符合现在 Expert 声明需求、Harness Capability 负责实现的边界；
- `Candidate Expert Profile` 改成 **Candidate Expert** 或 **Candidate Expert Version**，避免再造 `Profile` 本体。

### 7. 2.0 的 `Legal Work Harness` 也应重审

旧图里的 `Legal Work Harness` 同时包含：

- evidence / provenance；
- completion；
- escalation；

### 8. Proposition A 建议正式更新

旧：

> **Expert prototypes contain a hidden human harness.**

新：

> **Expert-operated prototypes contain latent work semantics.**

正文定义：

> A prototype may appear to be `Prompt → Model → Result`, while a domain expert is actually supplying task recognition, context selection, search strategy, omission detection, retry decisions, materiality judgment, escalation, and completion judgment between model calls. Schema Engineering treats these interventions not as one hidden “human runtime,” but as evidence from which reusable work semantics can be classified, governed, compiled, evaluated, and selectively promoted into durable system behavior.

产品化命题：

> **Productizing an expert-operated prototype means externalizing enough reusable work semantics that another qualified user can delegate the work without reproducing the original author's invisible orchestration, while preserving consequential expert judgment at explicit review and authority boundaries.**
:::

这也正好解释了为什么 **SE 2.0 不必推翻**。2.0 已经明确说，真正重要的不是 capture 而是 **promotion**：domain invariant、institution convention、matter context、individual habit 要进入不同位置。fileciteturn13file3L162-L171 现在只是把它进一步接到冻结后的正式架构上。
